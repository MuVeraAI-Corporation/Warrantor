2. The single defect

Four fine-tunes, four different outcomes, one cause

AdaptercontroversialRecall verdictWhat it looks like

Four adapters produced a win, two shrugs and a disaster on recall — and every single one damaged the severity field. The recall metric was reporting noise on top of a consistent underlying failure.

Why this is dangerous rather than merely disappointing

Two of these pass every review this programme has. `4b-adversarial` and `4b-weak-category` sit at p = 0.55 and p = 0.79 on recall, with per-category floors intact, while quietly losing over half their controversial verdicts. Floors measure categories. Nothing measured severity.

And when the class disappears, Controversial=SAFE becomes a silent no-op: the knob still exists, still accepts a value, and changes nothing. That is the same defect shape as a bound that reads Enforced and is Observed — the thing this product exists to refuse.

3. The mechanism, located in the config

Not a theory any more — a field with a value

The recipe notes already reasoned it out, after supervise_severity=False was run and refuted:

"LoRA adapts q/k/v/o/gate/up/down across every layer, weights BOTH output fields share, so not computing a loss on severity never held it still; it only stopped correcting it while training moved it anyway… A real fix needs SEPARATE PARAMETERS — a second adapter, or target modules that do not carry severity."

That prescription is directly expressible, and the current value is the permissive one:

lora_rank            16
lora_alpha           32
lora_dropout         0.05
lora_target_modules  None      <-- adapts EVERY module
learning_rate        0.0001
epochs               1.0
supervise_severity   True
The whole plan turns on this one line

lora_target_modules = None means every attention and MLP projection is adapted. The severity token and the category token are produced by the same weights, so any update that moves one moves the other. Restricting the target modules is the first testable form of the fix the notes call for, and it costs one config field.

4. T1 — the experiment that decides everything

One recipe, three arms, one question

Hypothesis. Severity damage is caused by LoRA adapting the shared projections. If the adapted modules are restricted, the controversial class survives fine-tuning at materially the same recall.

Refuted if: a restricted-module arm loses the class anyway, or preserves it only by learning nothing (recall indistinguishable from the base). Both outcomes are informative and both end this line.

Armlora_target_modulesTests
A — controlNone (all modules)Reproduces the known damage. Without it, nothing else is interpretable.
B — attention onlyq_proj, k_proj, v_proj, o_projWhether routing/attention alone can learn the category task without disturbing severity.
C — MLP onlygate_proj, up_proj, down_projThe complement. If B preserves and C does not, the shared representation is in the MLP, which is a mechanistic result worth publishing.

Registered before any arm runs

  • Primary outcome: is controversial still emitted, and at what count relative to the base? Binary present/absent first, magnitude second.
  • Secondary: paired McNemar on positives against the size-matched base — exact binomial, because discordance here runs to tens of pairs, not hundreds.
  • Both are reported for every arm, including arms that look bad. The whole failure mode here was a metric that hid a change.
  • Precision and lane recorded per arm. fp16-on-Kaggle and bf16-on-local are different conditions and must never be pooled.
  • Stop condition: if arm A does not reproduce the damage, the diagnosis is wrong and no further arm runs.

Recipe choice: guard-0.6b-expguard-weak. It is the only recipe with a genuine, significant recall gain to protect, so it is the one where "did we keep the gain while keeping the class" is a meaningful question. The others have nothing to preserve.

5. What follows, conditional on T1

T1 outcomeThen
An arm preserves the class and the gain That arm becomes the recipe default. Re-run the other four recipes on it — then the programme has four candidates worth gating. This is the only branch where bulk training is justified.
An arm preserves the class but learns nothing The category task and the severity field are not separable by module choice. Escalate to the second prescription: a separate adapter for severity, composed at inference.
No arm preserves the class LoRA on this architecture cannot learn the category task without disturbing severity. That is a publishable negative result and it ends the fine-tuning line — the guard stays base, and the effort moves to prompt-level or ensemble approaches.

7. The gate change, which is free

warrantor_ml.paired_analysis now exists and does this: it reports the severity distribution alongside the recall verdict, and returns VOID when a class present in the baseline is absent in the candidate.

VOID means the comparison is not automatable — not that the candidate is bad. The ExpGuard adapter is the proof: a gate promoting on recall and FPR alone would ship it, and a gate rejecting on class loss alone would discard a genuine +115. Neither is right by itself, so the tool escalates to a human instead of pretending to decide.

Adding this to the promotion gate costs nothing and would have caught all four adapters immediately.

8. What this plan refuses to do

  • Retrain the four damaged recipes as they stand. Same recipe, same damage, GPU spent to learn it twice. This is the change from v1.
  • Promote anything automatically. Including the ExpGuard adapter, whose gain is real and whose loss is real.
  • Allocate GPU to the four substrate recipes. Verified genuinely blocked: guard export-corpus returns 0 rows from 0 warrants against a minimum of 500. Product usage unblocks them; compute does not.
  • Pool fp16 and bf16 results. Different conditions. The same error as comparing two benchmarks run at different num_ctx — which this repository has already made once.
  • Set supervise_severity to anything. Refuted in both directions: False destroyed recall (0.8329 → 0.6804), True flattens the class. There is no third setting; the fix is elsewhere, which is what T1 tests.
