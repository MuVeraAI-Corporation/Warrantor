4. The Hugging Face token, in full

You asked for maximum depth. The subtlety in step 3 is the one that will otherwise cost you an hour.

Why nothing has worked so far

Three separate things must all be true to read a gated dataset. Only the first was ever the problem people described:

  1. The licence must be accepted under your account. ✅ Done 13 August, both corpora.
  2. A token must exist. ✅ Six of them.
  3. That token must be scoped to those specific repositories — and this is where fine-grained tokens bite.
  4. The token must be visible to the process as an environment variable. ❌ This is what is actually missing.
The fine-grained gotcha

All six of your tokens are FINEGRAINED. A fine-grained token does not inherit your account's gated-repo acceptances automatically — it carries an explicit list of repositories and permissions. If allenai/wildguardmix and 6rightjade/expguardmix are not in the token's Repositories permissions list with Read access to contents, the download returns HTTP 401 or 403 even though the licence is accepted.

That failure is indistinguishable from “you have not accepted the terms” unless you know to look — which is very likely how this ended up recorded as a licensing blocker in the first place.

The procedure

Step 1 — verify or fix the token scope

Go to huggingface.co → Settings → Access Tokens, and open the token you intend to use. Project AumOS is the natural choice (refreshed 20 days ago, used 6 days ago). Under Repositories permissions, confirm both datasets are listed with read access. If they are not, either add them, or create a new fine-grained token with:

  • Repositories: allenai/wildguardmix, 6rightjade/expguardmix — Read access to contents of selected repos
  • Optionally the guard models you pull (Qwen/Qwen3Guard-* and any GGUF mirrors), so one token covers the whole programme

A read classic token also works and sidesteps this entirely — it inherits every acceptance on the account. Fine-grained is the better security posture; classic is the faster unblock. Either is defensible, and the trade is worth making deliberately rather than by accident.

Step 2 — export it, in your own terminal

I never see the value. For the current PowerShell session: 

$env:HF_TOKEN = "hf_xxxxxxxxxxxxxxxxxxxx"

To persist it for your user across sessions:

[Environment]::SetEnvironmentVariable("HF_TOKEN", "hf_xxxxxxxxxxxxxxxxxxxx", "User")

Git Bash, for the current shell:

export HF_TOKEN=hf_xxxxxxxxxxxxxxxxxxxx
Two things not to do

Do not put it in a file inside the repository, even a gitignored one, without checking .gitignore first — this repository has already shipped one defect where SIGNING.md promised a .gitignore rule that did not exist. Do not paste it into chat; I do not need it, and anything in a transcript is harder to rotate than a variable.

Step 3 — verify without printing anything sensitive

python ml/run_corpus_benchmarks.py --check

This reports readiness and downloads nothing. With no token it names both gate URLs and the export line; with a working token it prints preconditions met. It never echoes the value.

A stronger check that proves the scope is right, not just that a variable exists:

python -c "from huggingface_hub import HfApi; \
print(HfApi().dataset_info('allenai/wildguardmix').id)"

Success means the licence, the token and the scope all line up. A 401 means the variable is missing or wrong; a 403 means the token exists but is not scoped to that repository — which is precisely the fine-grained trap above, and the two are worth telling apart.

Step 4 — what it unblocks, immediately

  • python ml/run_corpus_benchmarks.py — both corpus benchmarks at the pinned 8192/seed-0 configuration
  • All five guard fine-tune recipes, every one of which fails at its data step first
  • The re-measurement of every published figure in the eight paper drafts

Step 5 — rotation, since it will be used on more machines

Fine-grained tokens can be refreshed in place from the same settings page, which invalidates the old value without changing its name or scope. If a token ever reaches a log, a transcript or a commit, refresh rather than delete — the scope configuration is the part that took the thought.

5. The GPU programme — three phases in parallel

You asked for the hybrid. These are ordered by dependency, not importance, and two run concurrently.

  1. Phase A — serve the guards on managed compute

    Deploy Qwen3Guard-Gen-4B and the 0.6B to a dedicated H100 or A100 endpoint instead of local Ollama. This is first because everything else depends on it and it is the cheapest of the three.

    It also removes a measurement hazard rather than just being faster: every published guard figure currently comes from a local Ollama on a machine that has produced 2.86-second process spawns, fork exhaustion and cache corruption in a single day. A dedicated endpoint makes the serving configuration stated and reproducible, which is the exact property the num_ctx 4096-versus-8192 defect destroyed for eight releases.

    Cost shape: billed while the endpoint exists, so create, measure, delete.

  2. Phase B — re-measure every published figure, at scale

    Run the full WildGuardTest and ExpGuardTest splits through the Phase A endpoints, and the judging through GlobalBatch at roughly half the token price. Your current figures rest on a 14-case bench; the batch lane has 200M enqueued tokens sitting unused.

    Expect claims to move from “consistent with” to “measured”, and expect at least one not to survive. Better here than in review — the prior-art check already killed one paper and three claims, and a measurement check is cheaper than that was.

  3. Phase C — the three blocked fine-tunes

    Only after Phase B, because a fine-tune judged against an untrusted baseline teaches nothing. The three GPU-blocked recipes now run on H100s against a credit rather than against the Modal grant, and each is an Azure workload toward M3.

    Carry the standing constraint: supervise_severity=False was proposed, run and refuted by a 17-point recall drop. Do not spend GPU on a variable without a hypothesis worth testing.

Why H200 matters more than it looks

The H200's 141 GB — versus 80 GB on the H100 — is the difference between fitting a large open-weight guard at full precision and quantising it to fit. Since one of your papers is about whether quantisation changes verdicts, having a lane where you can run the unquantised reference is directly load-bearing for that argument rather than merely convenient.
