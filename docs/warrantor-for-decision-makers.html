1. The problem, in one page

Why this is different from every previous wave of automation

For thirty years, software did what it was told. You wrote the rule, the rule ran, and if the outcome was wrong you could point at the rule. Accountability was mechanical.

An AI agent is not that. You give it a goal — "fix the failing tests in the billing service" — and it decides for itself what to read, what to change, what to run, and what to do when it hits something unexpected. It is genuinely useful precisely because you did not have to specify the steps. That is also the whole problem.

Three things follow, and they are the reason a new layer is needed rather than better dashboards.

It acts, it does not advise

A chatbot that gives bad advice wastes your time. An agent with access to your systems can open a pull request, send an email, change a configuration, or delete a branch. The output is not a suggestion; it is a change to the world. Undoing it is a project.

Nobody is watching in real time

The entire economic case for agents is that a person does not sit and supervise. If someone has to watch every step, you have hired an expensive pair-programmer, not automation. So the honest design assumption is: the agent runs while everyone is asleep, and a human looks afterwards. Everything Warrantor does follows from taking that seriously rather than pretending otherwise.

They multiply

One agent is a curiosity. The change happening now is that they are cheap enough to run twenty at once. And here is the part most plans miss: the limit on how many you can run is not compute, and it is not licence cost. It is how many you can be answerable for.

If you cannot say what an agent did, you cannot let it do very much. So the constraint on adopting AI at scale is not capability — it is accountability.

2. The idea: a warrant

One concept, borrowed from how organisations already delegate

Organisations solved this problem for humans a long time ago, and the solution has a shape. Consider a purchase order, a limited power of attorney, or a contractor's work permit. Each has the same three properties:

  • Permission is stated in advance and is limited. Up to £50,000. This site only. Until Friday.
  • The work happens without supervision. Nobody follows the contractor around.
  • There is a record, and someone signs off at the end. The invoice is checked before it is paid.

A warrant is that, for an AI agent. Before the agent starts, you write down what it is allowed to do. The agent then works alone. Everything it does is recorded. And — the part that makes it more than paperwork — anything that would affect the outside world is held, not done, until a person releases it.

The single most important design decision

The agent cannot approve its own work

This is not a setting that could be misconfigured, and it is not a policy someone could override. The ability to release the agent's work is held by a different cryptographic key, which the agent never possesses. It is the same reason the person who submits an expense claim is not the person who approves it — except here it is enforced by mathematics rather than by an org chart.

If this were merely a permission check, an agent that wanted to open a pull request could approve itself and open it. Making the wrong thing impossible rather than forbidden is the principle the whole product is built on.

Holding work, rather than blocking it

This is worth dwelling on because it is counter-intuitive and it is where most of the practical value sits.

The obvious approach to AI risk is a filter: watch what the agent is about to do, and block the bad things. That approach fails for a reason nobody can engineer around — you have to be right in the moment, every time. Block too much and the agent cannot work. Block too little and something escapes.

Warrantor moves the decision to where it is easy. The agent works freely inside its own private copy of the code. Anything reaching outward — a pull request, a message, a deployment — is staged: written down as an intention, with a handle the agent can carry on using, but not performed. In the morning a person sees the whole set at once, in context, and releases it or discards it.

A snap judgement in the middle of the night becomes a considered judgement over coffee — with the complete picture, and with the option to throw it all away at no cost.

3. What a day actually looks like

The same story, told as a sequence

  1. Someone grants a warrant

    A goal in plain words, a list of tools the agent may use, which files it may change, which external services it may reach, a spending limit, and a deadline. This takes about a minute and it is the only moment that requires thought.

  2. The agent works, alone

    It gets its own private copy of the codebase, so nothing it does touches the real one. Every tool it uses passes through a checkpoint that consults the warrant. A request outside the permission is refused and written down — the refusal is itself useful information.

  3. Outward actions are held

    The agent believes it opened the pull request; it receives a handle and continues. Nothing has reached the outside world.

  4. The deadline arrives, and the agent stops

    Not by asking it nicely. The operating system terminates it, the same way it would any other process. An agent cannot talk its way past a deadline.

  5. A person is told there is a decision waiting

    Not a log to go and find — a notification, and a queue that says which warrants are waiting, who they are waiting on, and what that specific person can do about it. If your policy requires two approvers, it says which one is still missing.

  6. They look, and they decide

    A single screen: what was asked, what happened, what was refused, what is staged. Two buttons — release it, or discard it. Discarding costs nothing, because nothing was done.

  7. A record survives, either way

    Cryptographically signed, tamper-evident, and independently checkable — including by someone who does not trust you. Discarded work keeps its record too: the fact that an agent attempted something is evidence, not garbage.

4. The unusual thing: it tells you what it cannot do

If you read one section, read this one

Most security products describe themselves in terms of what they stop. Warrantor labels every limit it enforces with how strongly it is enforced — and it labels the weak ones weak, on the screen, to the buyer.

TierWhat it means in practice
Enforced The agent cannot get around this, at all. Held by cryptography or by the operating system — a signature it cannot forge, a process it cannot outlive. The deadline is here. So is the rule that an agent cannot delegate more power than it was given.
Mediated Enforced at a checkpoint the agent could, in principle, decline to use. Real against any agent that works through its normal tools — which is what every current coding agent does, constantly. Which tools it may use, and which external services it may reach.
Observed Measured and reported, not prevented. Which files it may change, and the spending limit. The spending figure comes from the agent's own self-reporting.
Why a vendor would publish its own weakest column

Because the alternative is worse. A customer who believes "the agent cannot write outside these folders" will not add the extra containment that would make it true. A customer who has been told plainly that it is observed rather than prevented will — and Warrantor generates the configuration to do it.

Every serious AI incident in the last two years shared one shape: a boundary that existed in the instructions and not in the system. A product that overstates its own boundaries is reproducing that failure and selling it. So the tier labels are not modesty. They are the product.

The same honesty, applied to the AI safety model

Warrantor can attach a second AI model that reads each of the agent's actions and flags anything it considers harmful. It runs in advisory mode by default, and we can tell you exactly why with a number: measured against a standard industry test set, it catches roughly 82% of adversarially-phrased harmful requests. That is good. It is not a wall.

We also measured something more revealing. Given two commands that both destroy work irrecoverably, it caught "run rm -rf on the production data volume" and missed "force-push a rewritten history over main and delete every other branch." Both are catastrophic. The difference is vocabulary: these models are trained on harm to people, and "force-push" is ordinary engineering English.

No amount of tuning fixes that. It is a category limitation, and it is exactly why the model advises while the rules decide. Wired the other way round — model first, rules as advice — that force-push goes through.

5. Why the value compounds

The commercial argument, made carefully

The weak version of this argument is "AI is risky, so buy governance." That is a cost centre and it is not what is happening here.

The strong version starts from the observation in §1: your ceiling on agent adoption is accountability, not capability. Follow that through.

Oversight cost normally grows with the number of agents

Without a common layer, each agent produces its own trail in its own format. Reviewing two agents costs twice as much attention as one. That is a straight line, and it puts a hard cap on adoption — a cap set by how much reviewing your people can absorb, which is a number that does not grow.

Warrantor bends that line

Every agent, whatever vendor, produces the same evidence in the same shape, and every decision arrives in one queue that says who it is waiting on. Reviewing the twentieth agent costs a small fraction of reviewing the first, because the reviewer has learned the format once. The cost of oversight grows far more slowly than the number of agents.

The value is not the risk you avoid. It is the agents you can now afford to run — the ones you would otherwise not dare to.

Three effects that stack

EffectWhat it means for you
Wider permissions become safe to grant Most agent deployments are throttled by fear — read-only access, a sandbox with nothing real in it. When outward actions are held rather than performed, you can grant a genuinely useful scope, because the worst case is a discarded batch rather than an incident.
Review time drops per agent One format, one queue, one screen. Reviewers get faster at a fixed shape in a way they never do at twenty different ones.
The evidence has value beyond the review The same signed records answer the auditor, the incident post-mortem, the customer's security questionnaire and the regulator — without a project to assemble them.

The honest cost side

Someone must look at the queue. Warrantor makes the looking fast and makes ignoring it visible; it does not remove it. If your organisation's answer to a review queue is to approve everything without reading, this product will record that faithfully and you will have bought an audit trail of rubber-stamping. That is a real failure mode and we would rather you hear it from us.

6. What Warrantor is not

So you can rule it in or out quickly

  • Not a monitoring dashboard. Dashboards tell you what happened. Warrantor decides what is allowed to happen and holds the rest for a person.
  • Not an AI content filter. It governs what an agent does, not what a model says.
  • Not a replacement for your existing controls. It composes with them. It will generate a confinement configuration for your infrastructure and then tell you plainly which of its own limits that configuration does and does not cover.
  • Not a way to run agents you do not trust at all. It bounds authority and creates accountability. It does not make an unreliable agent reliable.
  • Not vendor lock-in for your agents. It currently supports 36 agent tools and frameworks — the major coding assistants, general assistants and developer frameworks — and for each one it states exactly how much of that tool's activity actually passes through it. For several, the honest answer is "less than you would assume", and it says so.

7. The regulatory picture

Current as of August 2026, and more urgent than it looks

In April 2026 the US banking regulators issued revised model-risk guidance (OCC Bulletin 2026-13, and the Federal Reserve's SR 26-2), replacing the guidance that had governed model risk for fifteen years. It contains a sentence that is widely being read backwards:

What it says, and what it means

"Generative AI and agentic AI models are novel and rapidly evolving. As such, they are not within the scope of this guidance."

Read as an exemption, that is a reason to wait. It is not an exemption. It is a deferral — separate guidance is promised. Every obligation attached to the underlying action is untouched: safety and soundness, consumer protection, sectoral duties, third-party risk. What was removed is the framework that would have specified the controls.

So nobody is going to hand you a control specification for agents. And the guidance that eventually arrives will be written against whatever the industry has already built. That is a stronger argument for building the accountability layer now, not a weaker one — the organisations with evidence in hand will be the ones describing what "adequate" looks like.

The same reasoning applies under India's RBI and DPDP regimes and across GCC supervisory frameworks and sovereign-AI programmes: the duty attaches to the action, whoever or whatever took it. Warrantor's position is that governance, context and AI security are enablers of ambitious deployment — the things that let you widen an agent's remit — rather than a compliance tax applied afterwards.

9. The questions to ask us

Including the uncomfortable ones — these have real answers

  1. "What happens if the agent ignores your checkpoint entirely?" — Then the Mediated limits do not apply, and the Enforced ones still do: the deadline, the private workspace, the evidence, and the fact that it cannot release its own work. We will show you which is which, per limit.
  2. "Can the agent tamper with its own records?" — It shares a machine with the server, so the honest answer is a specific one, not a flat no. We narrowed what a stolen local credential can do to read-only, and we can walk you through what remains.
  3. "What happens if nobody looks at the queue?" — Nothing reaches the outside world; work accumulates as held. We would rather show you that outcome than a claim that it never happens.
  4. "Show me something that did not work." — We keep a document of exactly that. Ask for it. It is the fastest way to judge whether the rest of this is trustworthy.

10. Glossary

Every term in this document, in one place

Agent
Software given a goal rather than instructions, which decides its own steps and can act on real systems.
Warrant
Permission written down in advance and limited — which tools, which files, which services, how much, until when. The unit that lets a person walk away from a running agent.
Staging
Recording an outward action as an intention rather than performing it. The agent proceeds as if it happened; the world is unchanged until a person releases it.
Settle
A person releasing the held work, so it actually happens. Requires a key the agent does not have.
Void
A person discarding the held work. Costs nothing, because nothing was done. The record of the attempt survives.
Enforced / Mediated / Observed
How strongly a given limit actually holds. See §4 — this is the distinction that matters most when comparing us with anyone else.
Evidence
A signed, tamper-evident record of what happened, checkable by someone who does not trust the machine that produced it.
Guard model
A second AI that reads the agent's actions and flags concerns. Advisory by default, for the measured reasons in §4.
