Integrations Inventory

Every integration surface a developer can reach in the Warrantor platform today — what is wired, what is built but unreachable, and what is honestly missing.

aumos @ integration/end-to-end · 11 August 2026 · measured from source, not from docs

This inventory was produced by measuring the repository, not by reading its own documentation. Every claim below carries evidence: line counts from source, test counts from test files, and — the measure that matters most — whether anything in the codebase actually calls the component. A well-tested module that nothing invokes is not an integration; it is a library waiting for one.

Why "referenced by" is the load-bearing column

During this survey the mcp-gateway package turned out to be 913 lines with 53 passing tests and zero runtime callers — every reference to it was in a design document. That is the failure mode this inventory exists to catch. A component can be complete, correct, and completely unreachable at the same time, and only the reference count distinguishes it from a shipped feature.

wired reachable by a developer today, end to end cli only works, but only from the command line partial reachable, with a stated limit unwired built and tested; nothing calls it

The headline: two generations of integration

The repository contains two distinct bodies of integration work, and conflating them produces a misleading picture in either direction.

Generation 1 — broad and wired. The AumOS component surface: an MCP server exposing 15 tools to any MCP-speaking coding agent, a session harness for Claude Code / Codex / Cursor, framework adapters for LangChain and vLLM and Hugging Face, incident forwarding to Jira and Linear, SIEM export in OCSF 1.9.0, a Kubernetes admission webhook, and twelve Go services orchestrated by a single docker-compose.yml. This layer is genuinely reachable. A developer can install it and use it today.

Generation 2 — deep and unwired. The Warrant primitive: grant → run → status → report → settle / void, with staged effects, git-worktree isolation, OS-enforced process supervision, and a detached daemon. This is the newest and most consequential work in the repository, and a search for any reference to it outside its own crate returns nothing. No MCP tool exposes it. No LangChain callback uses it. No compose service runs it. It is reachable only by typing warrantor.

The single most important gap

The Warrant primitive — the thing that actually solves the babysitting tax — has no integration surface. Everything Generation 1 integrates with is a component; the Warrant is the product, and it is currently CLI-only. Closing this is worth more than any new adapter, because every existing adapter becomes more valuable the moment it can issue and settle warrants rather than merely emit receipts.

A. Coding-agent integrations

This is the entry point that matters: how a developer's existing agent starts talking to Warrantor.

A1. MCP server — @warrantor/mcp-server

wired   1,500 lines · 56 test cases · binary warrantor-mcp · shipped as compose service aumos-mcp

The broadest integration in the platform. Any MCP-compatible client — Claude Code, Codex, Cursor, Windsurf, Zed, or anything else speaking the protocol — registers this server and gains fifteen tools. It is a stdio server with a bin entry, so registration is a one-line config change on the client side; no HTTP endpoint, no port, no auth to configure.

Connected vs standalone — and why the distinction is handled honestly

The server runs in one of two modes. Connected (the default when no flag is given) shells out to the real Rust binaries and real Go services; if a binary is missing or exits non-zero, the tool returns a typed failure naming the missing dependency. Standalone returns deterministic stand-ins so the server is usable with nothing else installed.

The important property is that standalone mode does not lie. A signature produced there comes back tagged algorithm: "ed25519-mock" and source: "mock" — the response is structurally valid but self-identifying. This was the fix for audit finding AUD-001 ("MCP returns success-shaped mocks when controls fail"), and it is the correct resolution: the mock is still there, because a zero-install demo is worth having, but it can no longer be mistaken for enforcement by a caller reading the response.

Gap: the shipped compose file defaults to the demo

docker-compose.yml sets AUMOS_MODE: standalone on the aumos-mcp service — even though trust-core, agent-identity, flight-recorder, kill-switch and credential-vault are all defined in the same file and healthy. A developer who runs docker compose up and registers the MCP server gets labelled mocks while real enforcement sits one environment variable away. The responses are honest, so nothing is wrong; but the default is the demo rather than the product.

A2. Session harness — warrantor-harness (Python)

wired   941 lines · 32 tests · three agents supported

Where the MCP server integrates at the tool boundary, the harness integrates at the session boundary: it wraps the whole agent process. It supports three agents explicitly, and for each it can both read and generate the agent's native config file:

AgentConfig fileFunctions
Claude CodeCLAUDE.mdparse_claude_code_config() · generator in cli.py
OpenAI CodexAGENTS.mdparse_codex_config() · generator
Cursor.cursorrulesparse_cursor_config() · generator

Within a session it enforces a tool allowlist, tracks every file access, scans output for secrets, emits receipts, and — since the W0 work — holds the agent process under an OS-enforced lifetime link so it cannot outlive its supervisor. That linkage has since been ported to Rust (see A5); the Python implementation remains in place so the orphan hole never reopens during the transition.

A3. Agent SDK — warrantor-agent (Python)

wired   1,281 lines · 60 tests · the largest Python package

For developers writing their own agent rather than driving a vendor's. The headline is a decorator that wraps any function in the full security envelope:

from warrantor_agent import AumOS

agent = AumOS(mode="standalone")   # or "connected" against running services

@agent.action(tool="github.create_pr", side_effect="write")
def create_pull_request(repo: str, title: str, body: str):
    return {"pr_number": 42, "url": f"https://github.com/{repo}/pull/42"}

A decorated action issues or verifies an agent identity, runs an eval-guard pre-flight, brokers scoped credentials through credential-vault, and emits the receipt before the action commits — the ordering being the point, since a receipt written afterwards cannot prove anything about an action that failed halfway.

A4. MCP gateway — @warrantor/mcp-gateway

unwired   913 lines · 53 test cases · zero runtime callers

Authority-aware MCP middleware with confused-deputy protection and an explicit empty-aud bypass check. It is complete and it is tested. Every reference to it in the repository is in a design document, a threat model, or a tracker file — nothing imports it, nothing runs it, and no compose service starts it. It is the clearest example of the gap this inventory measures.

A5. The Warrant CLI — warrantor (Rust)

cli only   crate warrantor-warrant · 79 tests · verified end to end against real processes

The newest and deepest work, and — as stated above — reachable only from a shell. The full lifecycle:

warrantor grant --goal "fix the token refresh bug" \
                --tools git,cargo,github.create_pr \
                --write 'src/**' --egress api.github.com --deadline 8h --repo .

warrantor run    <id> -- claude --dangerously-skip-permissions
warrantor status                 # what is running, what stopped and needs a decision
warrantor report <id>            # diff, staged effects, denied requests
warrantor settle <id>            # release staged effects in dependency order
warrantor void   <id>            # discard the worktree and branch; keep the log

What it provides that nothing else in the repository does:

  • Git worktree isolation — the agent works in its own worktree on its own branch; the main checkout is untouched until settle.
  • Staged effects — irreversible actions are never performed speculatively. The agent receives a typed synthetic handle (pr://, comment://, review://, label://) and the real call happens at settle, addressed by the number the API actually returned.
  • Topological release — staged effects settle in dependency order, so every prefix is a coherent state and partial failure is survivable. On partial settle the warrant goes to Held, not Settled, and reports exactly where the boundary is.
  • Settle-authority separation — the agent holds an act-scoped capability token with no settle field; the settle key is separate and named inside signed claims.
  • Detached supervision — run starts a daemon detached from the terminal, so closing the terminal ends your view of the run rather than the run. The daemon holds the agent under a Windows job object (or setsid + PR_SET_PDEATHSIG on Linux), so the agent cannot outlive its supervisor either.

Verified against real processes rather than mocks: a run survived the launching shell exiting; killing only the supervisor killed the agent and a grandchild it had spawned; a 15-second warrant stopped its agent at 15 seconds; and status then reported the interruption with the decision it needed.

A6. GitHub adapter (Rust)

partial   5 integration tests · injectable transport

The only external-service adapter behind staged settle. It creates pull requests, posts comments, requests reviews and applies labels — resolving each staged handle to the real number GitHub returned. The transport is a trait, so tests drive it without a network. Reachable only through warrantor settle, which inherits the CLI-only limitation above.

B. Framework integrations

B1. LangChain — warrantor-langchain

wired   456 lines · 17 tests

Provides AumOSCallback (a BaseCallbackHandler that records receipts and scans for secrets), AumOSTool, SecuredAgent, and a wrap_agent() helper. The notable engineering decision is the optional import: if langchain_core is absent the base class degrades to object and has_langchain() reports false, so the package installs and imports cleanly in an environment with no LangChain at all.

C. Model and serving integrations

C1. vLLM — warrantor-vllm

wired   497 lines · 27 tests

AttestedVLLMServer wraps a vLLM process with an attestation envelope: the server will not serve until the model's identity is verified against a quote. Includes a QuoteCollector protocol for pluggable attestation sources and an explicit AttestationUnavailable error rather than a silent downgrade.

C2. Hugging Face — warrantor-hf-plugin

wired   243 lines · 10 tests

Signs models on upload and verifies them on download by writing a provenance block directly into the safetensors header — meaning provenance travels with the file rather than alongside it, and survives any transport that preserves the file. Provides sign_model_for_upload(), verify_model_on_download(), batch_verify() and an HFCallback.

C3. Ollama

wired   compose service with a named volume

Local inference, fronted by the inference-proxy service so prompts and completions pass a policy boundary before reaching the model.

D. Incident and ticketing

D1. Jira and Linear — warrantor-jira

wired   588 lines · 25 tests

Despite the package name it ships three forwarders behind one TicketForwarder protocol: JiraForwarder, LinearForwarder, and MockForwarder for tests. Incidents are mapped to labels and priorities by type and severity, with title and description built from the incident record. The protocol boundary means a third tracker is a new class, not a fork.

E. SIEM and telemetry

E1. OCSF export — warrantor-ocsf

wired   561 lines · 37 tests · OCSF schema 1.9.0

Converts Agent Action Receipts into OCSF 1.9.0 events — class_uid 6003 (API Activity) in category_uid 6 — which is the format Splunk, Sentinel, Chronicle and the rest of the SIEM market already ingest. Two sinks ship: FileSink and HTTPSink, both behind a Sink protocol, with ForwardStats for delivery accounting. The conversion is defensive by construction: a malformed receipt still produces a structurally valid event rather than dropping the signal.

G. Protocol contracts — the cross-language substrate

wired   four languages generated from one protobuf source

Under proto/warrantor, with generated bindings and validators in Rust, Go (1,278 lines), TypeScript (1,053 lines) and Python. Two Makefile targets keep them honest: check-proto lints the protobuf and rejects breaking changes against main, and check-protocols rejects drift between registry.json and every generated artifact. make conformance runs a shared test-vector matrix across all four languages.

This is the reason a receipt emitted by the Python SDK verifies in the Go service and renders in the TypeScript console — the integration nobody notices because it never breaks.

A property worth stating explicitly: zero runtime dependencies

Every one of the twelve warrantor-* Python packages declares an empty [project].dependencies. Third-party libraries — LangChain, responses — appear only as optional imports or test dependencies. Installing any Warrantor package adds no transitive supply-chain surface to a developer's environment. For a security product this is not incidental; it is the difference between being an assurance layer and being another thing to audit.

What a developer can actually do today

1. Give any MCP-speaking agent the fifteen tools

cd typescript/mcp-server && npm run build
# register the built ./dist/index.js as an MCP server in your client's config
# default mode is "connected" — it will use real binaries and fail loudly without them

2. Run an agent under a warrant, and walk away

cargo build -p warrantor-warrant
warrantor grant --goal "fix the flaky auth test" --tools git,cargo \
                --write 'src/**' --deadline 8h --repo .
warrantor run <id> -- claude -p "fix the flaky auth test"
# close the terminal; the run continues
warrantor status      # in the morning
warrantor report <id> # then settle or void

3. Secure a hand-rolled Python agent

pip install -e python/warrantor_agent
# then decorate your actions with @agent.action(tool=..., side_effect=...)

4. Ship receipts to an existing SIEM

pip install -e python/warrantor_ocsf
# convert_aar_to_ocsf() → HTTPSink → your OCSF 1.9.0 ingest endpoint

5. Bring the whole platform up locally

docker compose up          # 17 services
make demo                  # sign an action, log it, verify the proof
make test                  # Rust + Python + Go + TypeScript
make conformance           # cross-language vector matrix
