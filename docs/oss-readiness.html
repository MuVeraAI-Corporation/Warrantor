Open-Source Readiness

An adversarial pass over the repository, asking what would embarrass us on launch day and what would make a capable stranger give up. Findings are measured, not asserted — including the ones I introduced myself.

aumos @ integration/end-to-end · 11 August 2026

Open-sourcing changes who the audience is. Internally, a half-wired component is a known to-do. Publicly, it is a stranger's first impression, and they have no way to tell a deliberate stub from an abandoned one. Everything below is judged by that standard.

Fixed during this pass

py.typed markers on all 12 Python packages · README rewritten as a front door · docs index for 200+ files · SUPPORT.md, GOVERNANCE.md, MAINTAINERS.md, NOTICE created.

1. A defect I introduced an hour earlier fixed

While preparing the packages for release I added the Typing :: Typed classifier to all twelve Python packages. None of them had a py.typed marker.

Under PEP 561, a package without that marker is treated by type checkers as untyped — its inline annotations are ignored entirely. So the classifier was advertising a capability the package did not deliver: someone would install it, expect their type checker to see the types, and get nothing, with no error explaining why.

Fixed by adding the marker and the [tool.setuptools.package-data] entry, then verifying the marker actually appears inside the built wheel rather than only on disk. The second step matters: without it the file exists in the source tree, is absent from the artifact, and the claim stays false in exactly the place it is read.

Worth naming as a pattern

The defect was created by a step whose whole purpose was to improve quality. Metadata additions are unusually prone to this because they are assertions about the code that nothing compiles or tests. A classifier is a promise with no enforcement behind it.

2. The README was a maintainer memo, not a front door fixed

The single most-read file in any open-source project opened like this:

# AumOS — Open Defense Stack for AI (Unified)

AumOS is the unified implementation ... It reconciles four source portfolios
that previously lived as separate strategy documents in this project folder:

| Source portfolio | Originating documents |
| DefStack (36-component, 8-phase) | DefStack_Implementation_Plan.pdf, ...

Twenty-five lines in, a visitor had learned how four internal strategy portfolios were merged, been pointed at PDFs they do not have, and been told there are "54 implementable components" — and still did not know what the software does or whether it would help them.

Rewritten to answer, in order: what it does, why the design is shaped that way, where to go for your specific role, how to run it, and what does not work yet. The reconciliation history is still available, relabelled as maintainer history rather than the opening argument.

The seventeen: agentsec_lab, attesta_flow, bias_sentinel, bridge_rt, comply_gate, crypto_audit_ai, data_provenance_kit, dp_crate, fed_core, metr_bridge, nooa_ext, open_harness_spec, policy_compiler, red_team_cloud, retro_spec_kit, tamper_scan, train_guard. Together roughly 6,600 lines. Each has a pyproject.toml, so each was intended to be a package. Six have no README at all.

At least one is load-bearing by implication rather than by wiring: the console's own docstring refers to "OPA Rego policies compiled by R5 policy-compiler", and policy_compiler is in this list — so a component the design depends on is invoked by nothing.

Why this matters more publicly than internally

A stranger cannot distinguish "deliberate standalone library" from "abandoned". Seventeen packages that nothing calls and nothing ships reads as a project that started many things and finished few — which is a harsher judgement than the code deserves, and entirely avoidable.

Each one needs a decision, and only three are available: wire it (it is a component and something should call it), ship it (it is a product — give it a README and put it in the release pipeline), or move it to a clearly-labelled research/ or incubator/ directory that sets the expectation honestly. Leaving them where they are is the only option that misleads.

The decision was Warrantor everywhere. The repository root directory is aumos, the README title was Warrantor, the compose service is aumos-mcp, the CI workflow is aumos-security.yml, and the packages are warrantor-*.

I have not done the sweep. It touches build identifiers, Docker image names, CI workflow names, Go module paths (muveraai.com/go/*) and published package names, and doing it incrementally is worse than doing it once — a half-renamed project is more confusing than a consistently misnamed one. It needs to be a single deliberate change with the repository name settled first. In the meantime the README states plainly that the three names mean the same thing, which costs nothing and removes the confusion for a reader.

5. Two hundred documents with no index fixed

161 Markdown files and 65 HTML files under docs/, no docs/README.md, and no statement of which are current. A newcomer had no way to tell a live architecture document from a wave-3 verification report written months ago.

Added an index organised by task, which names the four documents that matter, explains what each remaining directory is for, and states three things plainly: the RFCs describe intended designs and some were never built, where docs and code disagree the code wins, and decisions/ is empty because the ADRs were planned and never written.

6. Missing files that consumers look for fixed

README, CONTRIBUTING, CODE_OF_CONDUCT, SECURITY, LICENSE, CHANGELOG and RELEASING were all present and substantial. Absent: GOVERNANCE.md, MAINTAINERS.md, SUPPORT.md, NOTICE.

Now written. Two deliberate choices in them:

  • GOVERNANCE names the areas requiring two reviewers — authority semantics, cryptographic code, the staging engine, process supervision — because those are where a plausible-looking change can be wrong while tests still pass. It also encodes the test discipline used throughout this work: delete the mechanism, confirm the test goes red, put it back. A test that passes without the thing it tests is worse than no test, because it manufactures confidence.
  • MAINTAINERS lists the areas with no maintainer — frontend, Go services, Python SDKs, security response. Pretending coverage exists is how a contribution sits unreviewed for three weeks and the contributor never returns.

Needs you before launch

MAINTAINERS.md contains a placeholder instead of a GitHub handle. A maintainers file that names nobody is worse than none — it tells a prospective contributor there is nobody to talk to.

What I checked that was fine

Recording these so the list above reads as a survey rather than a complaint:

  • CI is real. DCO enforcement, protobuf lint plus breaking-change rejection against main, cargo fmt, clippy with warnings denied, tests across all four languages. Plus separate coverage, fuzz, SBOM and provenance workflows. This is stronger than most projects at this stage.
  • .gitignore is thorough and commented, including a reasoned note on why Cargo.lock is committed and nested ones are not. No cache directories are tracked.
  • Zero runtime dependencies across all twelve Python packages, with optional imports where a third-party library is involved. For a security tool this is a real asset.
  • Cross-language conformance is enforced by make check-protocols and make conformance, not merely intended.
  • SECURITY.md exists and is substantial — 3.4 KB with an actual process.

A correction

An earlier pass in this session reported that attesta_flow shipped a pyproject.toml with zero lines of Python. That was wrong. The package has 156 lines; my file-count command excluded the directory because the glob *test* matches "attesta". The measurement was broken, not the package.

Noted rather than quietly dropped, because a readiness audit that silently revises its own findings is not one you can rely on. The other counts in this document were re-derived after finding that bug.

What to do next, in order

  1. Make the repository public once MAINTAINERS and the rename are settled. It exists and is private; the org question is already settled by the configured git remote (MuVeraAI-Corporation). Publishing does not wait on this, but working metadata links do.
  2. Fill in MAINTAINERS.md. One line.
  3. Decide the seventeen. Wire, ship or move to research/. This is the finding most likely to shape a stranger's opinion of the project.
  4. Claim the registry names, which requires 1 and closes a real dependency-confusion window.
  5. Do the rename in one pass, after the repository name is settled.
  6. Then the console, which is the largest remaining gap and the only one that is purely additive work rather than a decision.

Every count in this document was produced by measuring the repository at the commit named in the header. Where a number is a judgement rather than a measurement — such as which orphans are legitimately standalone — it is labelled as one.
