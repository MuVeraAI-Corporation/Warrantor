Deploying on AWS

A reference architecture for running Warrantor on AWS — grounded in what the codebase actually contains, which turns out to change the shape of the answer considerably.

Warrantor v1.0.0 · 12 August 2026 · measured from source, not from the compose file

Before any architecture, a measurement — because "deploy the entire platform on AWS" assumes the platform is a fleet of services, and most of it is not. Getting this wrong produces a beautiful diagram for software that does not exist.

The finding that reshapes this whole document

docker-compose.yml defines 17 services. Checking each for an actual network listener:

  • Five are real HTTP servers — all Go: agent-identity, open-serve-kit, tee-serve, fleet-marshal, edge-sentinel. And all five are stateless, in-memory — not one touches a database.
  • Three are command-line tools, not services: trust-core, kill-switch, credential-vault. Their containers run a CLI and exit. You cannot put a CLI behind a load balancer.
  • Two are health stubs — flight-recorder and inference-proxy run a hand-written listener that answers every path with a fixed {"status":"ok"}.
  • The warrant core has no network surface at all. No TcpListener, no HTTP framework anywhere in the crate. It speaks MCP over stdio and stores warrants as JSON files under ~/.warrantor.

So there is no server-side product to deploy for the thing Warrantor actually is. That is not a defect — it is a design choice, and a good one for a tool that supervises a developer's own agent on a developer's own machine. But it means an AWS deployment is answering a different question than "where do I host Warrantor".

Most people asking this question want D — a place where a team's warrants live, where a compliance officer can look, where approvals happen. That requires code that has not been written. B is the posture that delivers value on AWS today and is where this document spends its detail.

Posture B — the supervised CI fleet

This is the one worth building first, because it is where unattended agents actually earn their keep: a build fleet that can run an agent against a repository for hours, with the warrant enforcing what it may touch and staged effects meaning nothing irreversible happens until a human settles it.

Why ECS on EC2 rather than Fargate

This is the decision that matters most, and the obvious answer is wrong.

Fargate cannot give the supervision guarantee

Warrantor's core promise is that an agent cannot outlive its supervisor, enforced by the kernel: a Windows job object, or setsid plus PR_SET_PDEATHSIG on Linux. That link is a property of the host's process tree.

Fargate gives you a managed container with no host access, no control over the init process, and no ability to reason about what happens to descendants when the task is stopped. The mechanism may still work inside the container — but you cannot verify it, and Warrantor's own doctrine is that a guarantee you cannot verify should be reported as absent. On EC2 you own the host, can confirm the process tree, and can run the same verification used in development: kill the supervisor, assert the agent and its grandchildren are gone.

Fargate remains the right choice for posture C, where the workloads are ordinary stateless HTTP services with no supervision semantics.

Task sizing and isolation

One agent per task, never several. The warrant bounds one agent; two agents in one task share a filesystem and a process namespace, and the write-path bound stops meaning anything. The isolation model is per-worktree, and a worktree assumes it is alone.

ResourceRecommendationWhy
Instance familym7i / m7g (Graviton)Agent runs are memory- and IO-bound, not CPU-bound. Graviton is cheaper and the Rust CLI cross-compiles to aarch64 cleanly — the release already ships that target.
Memory≥ 8 GB per taskLearned the hard way: the Rust workspace exhausts memory under parallel builds. If agents compile, budget for it or pin CARGO_BUILD_JOBS=1.
StorageEBS gp3, ≥ 50 GB, one volume per hostGit worktrees plus build artifacts. ~/.warrantor must survive a task restart or in-flight warrants are orphaned.
Task timeoutWarrant deadline + 10 minLet the warrant expire the agent, not ECS. The warrant terminates cleanly and writes a report; a task kill does not.

Egress control — where the warrant's allowlist becomes real

Warrantor's egress bound is enforced at the tool boundary: the proxy refuses a call whose URL host is not allowlisted. That stops an agent asking to reach an unapproved host. It does not stop a subprocess the agent spawned from opening a socket directly, because nothing in the warrant sits between that process and the network.

AWS is where that gap actually closes

This is the strongest argument for running agents on AWS rather than laptops. Put runners in a private subnet with no internet gateway, and force all egress through a controlled path:

  • VPC endpoints for S3, ECR, Secrets Manager, CloudWatch — traffic never leaves the AWS network, and no NAT charge.
  • AWS Network Firewall with an FQDN allowlist for what genuinely must reach the internet: github.com, crates.io, registry.npmjs.org, pypi.org, and your model API endpoint.
  • Security group egress denying everything not on that path.

The warrant's egress_hosts list and the firewall rule should be generated from the same source, or they will drift and the tighter one will be a surprise. Warrantor reports egress as Enforced; with the network layer behind it, that word finally covers subprocesses too.

Secrets and the settle key

Warrantor uses two keys, and the separation is the whole security model: the issuer key signs warrants, the settle key authorises releasing staged effects. Putting both in one place undoes it.

KeyWhereReachable by
Issuer keySecrets Manager, task role readThe runner, to grant and supervise
Settle keyKMS asymmetric, or a separate accountNever the runner. Only whoever approves
Model API keysSecrets Manager, injected at task startThe agent process
Registry tokensNot on the runner at all — OIDC at publish timeCI publish job only

The mistake that would quietly void the design

Giving the runner's task role read access to the settle key. It is the convenient thing to do — everything then works without a second step — and it means the agent's host can release its own staged effects. Every other control still appears to function; the property that made staging worth anything is simply gone, silently.

The runner role should have an explicit Deny on the settle key ARN, not merely an absent Allow. Absent permissions get granted later by someone solving a different problem; an explicit Deny makes them argue with it.

Evidence storage

Receipts and staged-effect logs are the audit trail, and an audit trail that can be edited is not one. S3 with versioning plus Object Lock in compliance mode makes them write-once — nobody, including the account root, can alter or delete an object before its retention expires.

s3://warrantor-evidence-<account>-<region>/
  receipts/dt=2026-08-12/warrant=wrt_.../*.ocsf.json
  staged/  dt=2026-08-12/warrant=wrt_.../queue.jsonl
  reports/ dt=2026-08-12/warrant=wrt_.../report.json

Partitioned by date so Athena can query it without scanning everything, and by warrant so a single run's evidence is one prefix. Receipts are already emitted as OCSF 1.9.0 (class_uid 6003), which Security Lake ingests natively — that is a genuinely short path from "we run agents" to "agent activity is in the same SIEM as everything else".

Posture C — the five stateless services

Worth stating plainly: deploying these gives you identity issuance, an inference proxy, a TEE serving sidecar, fleet coordination and an edge agent. It does not give you warrant supervision, which is the product. Deploy them if you need those components; do not expect them to add up to Warrantor.

Because all five are stateless and in-memory, they are unusually easy to run — and unusually lossy. Anything they hold disappears on restart, so treat them as pure request/response and put real state in RDS or DynamoDB when the components grow it.

Images are already published to ghcr.io by the release workflow. Either pull from there or mirror into ECR — mirroring is worth it for pull-through caching and for keeping runners in a private subnet with no internet route.

What has to be built for posture D

This is the honest gap, and it is the same one the non-developer platform document identifies. Multi-user oversight on AWS needs three things that do not exist:

  1. A warrant service. Today the store is JSON files under ~/.warrantor on one machine. A team needs a service — and the moment it is a service it needs identity, which is where agent-identity and the SPIFFE work stop being adjacent and become load-bearing.
  2. A read API. The console library expects one; nothing serves it.
  3. The console itself. There is no UI anywhere in the repository.

The sequencing matters: on AWS, a warrant service is the natural home for the settle key, and the approval step becomes an API call from a console rather than a CLI command on a laptop. That is a better security posture than today's — but it is a build, not a deployment.

Data residency, which is a first-class requirement in these markets

The platform's primary markets make region choice a design input rather than an afterthought.

MarketRegionsWhat drives it

The residency hole most architectures leave open

You can pin every AWS resource to one region and still send the agent's entire context to a model API in another country on every call. The model endpoint is the residency boundary that matters most and the one least often drawn on the diagram.

Options, in descending order of assurance: Bedrock in-region with a model available there; a self-hosted open-weight model on g5/p4d instances in the same VPC (which is what open-serve-kit and tee-serve are for); or a third-party API with a contractual residency commitment. Warrantor's egress allowlist is where you make that choice explicit and enforceable.

Observability

Three signals matter, and only one is conventional:

  • Refusal telemetry. What agents attempted and were stopped from doing, with counts. A run with twenty refusals of one tool means the warrant was drawn wrong; a single refusal means an agent reached beyond its grant. Ship these as CloudWatch metrics with dimensions on tool and bound, and alarm on a rate change rather than a threshold.
  • Warrants left Open with no live supervisor. This is the interrupted-run state, and silence is its failure mode. A scheduled reconciliation task publishing a metric for interrupted warrants catches the case where a host died and nobody noticed.
  • Settle outcomes, split by complete versus Held. A rising Held rate means external effects are failing partway, which is exactly when someone needs to look.

Receipts go to S3 as OCSF and into Security Lake. CloudWatch is for the operational signals above; do not duplicate the evidence trail there, because two records of the same event with different retention rules is an audit problem rather than redundancy.

Phase 0 is the one people skip and should not

Every guarantee in this document is downstream of the process-lifetime link working on your host. It has been verified on Windows and on Linux with setsid + PR_SET_PDEATHSIG — but not on your AMI, your kernel, your container runtime. The verification is three commands: start a run, kill the supervisor, check the agent and a grandchild are gone.

If it does not hold, Warrantor tells you so at startup rather than pretending. Read what it reports before building six phases on top of it.

What this document deliberately does not include

  • Terraform. Writing modules for an architecture nobody has run once produces code that looks authoritative and has never been executed — the same failure this project has spent a day removing elsewhere. Phase 0 first, then generate IaC from what actually worked.
  • A multi-account landing zone. Correct at scale, and premature before a single agent run has succeeded in one account.
  • Autoscaling policies. Meaningless without observed run durations. Measure a week of real runs first; the distribution is bimodal in practice and generic policies handle that badly.

Architecture facts here were measured from the repository at v1.0.0: which services have HTTP listeners, which are CLIs, which are stubs, whether the warrant store has a network surface, and what state each Go service keeps. AWS service capabilities are as of August 2026 and should be re-checked against current documentation before committing to a design.
