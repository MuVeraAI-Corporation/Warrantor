Fine-tuning on Modal: what it buys, and what it does not

You asked what benefit you get from fine-tuning three models on Modal before you approve the spend. The short answer is that the spend is not the binding constraint, and approving it today would buy you nothing at all — because every one of these runs fails at its data step before a GPU is touched.

17 August 2026 · every figure below read from this repository, not estimated

The recommendation, up front

Do not approve Modal spend yet. Two things must happen first, and neither costs money:

  1. Accept the two Hugging Face corpus licences and export a token. Every guard recipe in this repository is blocked on it. Without it the run fails with HTTP 401 at the data step — before any GPU time is billed, but also before anything is learned.
  2. Measure the 0.6B's severity exposure. It is recorded nowhere. Without that number, a rejected run cannot be attributed between "the adapter did not learn" and "the adapter flattened severity" — which is precisely the ambiguity that made the two previous runs cost time and teach less than they should have.

After those, the honest case for Modal specifically is wall-clock and reliability, not capability: 1.8 hours instead of 4.6, on a machine that is not the one you are working on.

All five fit the development box. Kaggle is unsuitable for all five — its T4 (sm_75) and P100 (sm_60) predate native bf16, so the free tier is not an option here regardless of its 30 hours a week. Modal is roughly 2.6× faster and nothing more.

The one real argument for Modal

The planner attaches this warning to every 0.6B run on the local lane: "LoRA over an unquantised base leaves very little margin on a 16 GB card and will OOM when the desktop compositor spikes." A 4.6-hour run on the machine you are also using is a run that can die at hour four because something opened a window. That is a reliability argument, and it is a legitimate one — but it is an argument about where to run, not about whether the runs are worth doing.

2. Why approving spend today buys nothing

Every guard recipe carries the same blocking warning, emitted by the planner itself: 

wildguardmix is GATED on Hugging Face. Accept the form and export a read
token before this run, or the data step fails with HTTP 401.

And for the ExpGuard recipe, the same for expguardmix. This is the identical credential you deferred in the earlier question — and it turns out the Modal decision is downstream of it, not parallel to it. There is no ordering in which the spend comes first.

Sequencing

A Modal approval granted today would be spent on a job that downloads nothing, trains nothing, and exits non-zero. The token is free, takes about ten minutes, and unblocks the local lane as well — at which point you can run the first candidate on the 5080 for nothing and decide about Modal with a result in hand.

3. What the fine-tunes would actually buy, per recipe

These are the measured weaknesses each recipe targets, taken from the baselines this repository has already recorded. This is where the real benefit lives, and it is specific.

The adversarial gap — the most valuable one

The guard's recall falls from 0.8886 to 0.8152 under adversarial phrasing, and its false-positive rate rises 0.0224 → 0.0923, four times higher. That is the single number that most limits what this product can claim: an agent's tool call is exactly the kind of text an attacker phrases carefully. Closing part of that gap is what would let the guard move from advisory toward something an operator could weight more heavily.

The weak categories — three reachable classes

On WildGuardTest the measured weak classes are social_stereotypes_and_unfair_discrimination at 0.7237, fraud_assisting_illegal_activities at 0.7833, and others at 0.7857. The recipes train on these three with a benign ratio of 1.0 — deliberately, because training on missed positives alone buys recall by manufacturing false positives, and the gate rejects a candidate whose FPR regresses.

Unqualified Professional Advice — the weakest class, and the most constrained

UPA is the weakest measured class on both sizes: 0.3719 on the 0.6B and 0.4298 on the 4B. It exists only in ExpGuardMix. The bar for promotion is already computed: ≥ 942 caught (recall ≥ 0.7500, i.e. +44 rows) and fewer than 116 false positives (FPR below 0.1138). The minimum detectable delta is 0.0353 — anything smaller is within_noise and is a reject.

ExpGuardMix is not cleared for commercial use

Its licence is CC-BY-4.0 but its gate form requires affirming research-only use, and the click-through is the narrower agreement — it is the one that was signed. Its corpus was GPT-4o-generated upstream. A promotion from this recipe is a quality verdict and never a clearance for a shipped vertical pack. If your intent for these models is commercial, this recipe cannot serve it whatever it scores.

4. What the two previous runs cost, and what they taught

This is the part that should temper any expectation of a clean win. Two runs have been executed and both were rejected by the gate.

RunChangeResult
weak-2026-08-13a Severity supervised Taught the adapter a binary Unsafe/Safe vocabulary and extinguished the third severity value, Controversial: 49 verdicts to 0 over 1,699 samples. Recall 0.8488 → 0.8329 with the false-positive rate falling — a more permissive gate — and it silently made the Controversial=SAFE policy knob a no-op.
run 2 supervise_severity=False The proposed fix, refuted. Recall 0.8329 → 0.6804 overall and 0.7947 → 0.5572 adversarial — far worse than the flattening it was meant to prevent.

The root cause is worth understanding before funding a third attempt, because it rules out a whole family of cheap fixes. LoRA adapts q/k/v/o/gate/up/down across every layer — weights that both output fields share. Not computing a loss on severity never held it still; it only stopped correcting it while training moved it anyway. The field came unmoored and filled with its neighbour's vocabulary: the 0.6B began emitting category names — violent, others — into the severity slot.

The repository's own conclusion, recorded in the recipe notes: a real fix needs separate parameters — a second adapter, or target modules that do not carry severity — or a corpus that can supervise all three severity values. It is not a third setting of this flag.

5. The risk that is still unmeasured

Severity exposure on the 0.6B

On ExpGuardTest, the 4B's Controversial verdicts carry 235 of 954 true positives. Losing them drops recall 0.7596 → 0.5725 — four times what flattening cost on WildGuard. The 0.6B's equivalent exposure is recorded nowhere: no ExpGuard result document is committed in this repository.

That matters for your money specifically. Without the number, a rejected run tells you only that it was rejected — you cannot separate "the adapter did not learn" from "the adapter flattened severity", which are different failures with different next steps. You would be buying a result you cannot act on.

6. The honest expected value

Setting the blockers aside and assuming they are cleared, here is what a third run is actually worth:

  • The gate is strict, and that is the point. Promotion needs a measurable improvement on the target slice and no regression on six per-category floors. Two of those floors — Fraud/Scams/Deception (603 positives) and Criminal Planning (356) — are not trained for by the ExpGuard recipe and can only fall. An aggregate that improves while a class collapses is exactly what the floors exist to refuse.
  • A reject is a real outcome, not a wasted run — provided you can attribute it. That is what §5 is about. Both previous rejects were informative; the second was informative because someone had a specific hypothesis to refute.
  • The upside is bounded and known. For the ExpGuard recipe: 127 recoverable misses across four classes (UPA 76, Privacy Violation 13, Violence & Incitement 19, Self-Harm 19), of which about a third clears the bar. This is not a run that might transform the guard; it is a run that might move one slice above a threshold that was computed in advance.
What is already true without spending anything

The guard works end to end today. A live Qwen3Guard-Gen-4B classifies real tool calls in observe mode and refuses them in enforce mode; warrantor guard bench measures the running configuration at recall 0.875 [0.529, 0.978] and FPR 0.000 [0.000, 0.390], both consistent with the published figures. None of the decisions below block the product.

7. What I recommend, in order

  1. Accept the two licences, export HF_TOKEN. Free, ~10 minutes, unblocks everything including the local lane. Then python ml/run_corpus_benchmarks.py --check tells you it is clear.
  2. Measure the 0.6B's ExpGuard severity exposure and commit the result document. This is a scoring run, not a training run — cheap, and it is the difference between an interpretable reject and an uninterpretable one.
  3. Run one candidate on the RTX 5080 for free — guard-0.6b-adversarial is the one I would pick, because the adversarial gap is the most valuable and the recipe is not encumbered by ExpGuardMix's research-only clause. Expect ~4.6 hours; run it when you are not using the machine, or with technique=qlora to widen the margin.
  4. Then decide about Modal with a result in hand. If the local run is rejected for a reason you can attribute, Modal buys you faster iteration on the fix. If it is promoted, you have your answer for free. Either way you will be deciding with evidence rather than in advance of it.
