2. Three blockers, verified one by one

Two were wrong. The third is real, and it is the only one that stops work.

Verified real — the substrate cold start

warrantor guard export-corpus, run today: 0 rows from 0 warrants, 0 labelled, against a recipe minimum of 500. The tool's own words: “this number grows by USING the product, not by exporting more often.”

All four substrate recipes are genuinely blocked, and no amount of GPU changes that. They are excluded from every run below and appear only in §4's last item.

Wrong — Kaggle is usable

I recorded Kaggle as unsuitable because its T4 (sm_75) and P100 (sm_60) predate native bf16. That was my inference, not the planner's reason. The planner actually says: “estimated 12.3 h exceeds kaggle-t4x2's 12 h session cap and no --resume-from was given” — and names the remedy in the same sentence.

With --resume-from, every guard recipe fits Kaggle: 12.3 h on T4×2, 15.3 h on P100, at fp16. That is 30 free GPU hours a week I had written off.

Wrong — the corpora were never licence-blocked

Both gates were ACCEPTED on 13 August, and a working token has been in the credential store all along. The preflight that said otherwise checked only environment variables. Corpus access is not a blocker and has not been one for weeks.

The local lane is blocked right now, and not by VRAM

Measured on this machine: committed memory 84.4 GB of an 87.5 GB limit — 96.5%, with 10.0 GB available. VRAM has ~11.5 GB free and the recipes need 6.15–8.57 GiB, so the GPU is fine.

Commit pressure is also the diagnosis for this session's CreateProcessW failed, fork exhaustion, cranelift STATUS_STACK_BUFFER_OVERRUN and clippy OOM. Training on top of that would page heavily. Free memory first — unloading the Ollama model alone returns ~8.8 GB.

fp16 on Kaggle versus bf16 elsewhere is not a detail. Two adapters trained at different precisions are two different experiments, and comparing them without saying so is the same error as running two benchmarks at different num_ctx.

4. The work, in dependency order

Verification before training, because a run judged against an unproven baseline teaches nothing

  1. W1 — Prove the winner, or find out it is not one no GPU

    guard-0.6b-expguard-weak clears every stated bar: 982 caught against 942 required, 56 false positives against a 116 ceiling, +0.0668 against a 0.0353 minimum detectable delta, and an FPR that improved from 0.0873 to 0.0550. Both untrained floors rose.

    Three checks before anyone calls it promoted:

    • Run the real parity_gate, reconstructing the lane, precision and manifest digest the result documents do not carry
    • McNemar on paired item-level outcomes — this is what converts +0.0668 from a delta into a result
    • A severity-distribution check. The recipe warns that flattening the third severity class can look like an aggregate win; the 4B's Controversial verdicts carry 235 of 954 true positives on this corpus, and losing them drops recall 0.7596 → 0.5725. If severity flattened here, the win is an artefact.

  2. W2 — Post-mortem the eleven-point regression no GPU

    guard-0.6b-weak-category fell 0.8488 → 0.7374. That is comparable to the 17-point drop that refuted supervise_severity=False, and nothing records it.

    Diagnose from the existing artefacts first: per-category recall against baseline, the severity distribution, and whether Controversial verdicts collapsed. Do not retrain until there is a named cause — the standing lesson is that running the next one without a hypothesis worth testing repeats the last mistake with a different variable.

  3. W3 — Resolve the three unresolved adapters no GPU

    Paired McNemar for 4b-adversarial (+0.0053), 4b-weak-category (−0.0013) and 0.6b-adversarial (−0.0119) against their baselines. Cheap, and it converts three ambiguous rows into three verdicts — most likely three within-noise answers, which is a real result and stops anyone treating +0.0053 as a win.

  4. W4 — Retrain, only where W2 produced a hypothesis GPU

    The first genuinely new training. Scope depends entirely on W2's cause, which is why it cannot be specified further here — and specifying it anyway would be the error this plan exists to avoid.

  5. W5 — The untried variants GPU

    Two exist and have never run: the 4B ExpGuard-weak variant, because the 0.6B version is the programme's only clear success and the same recipe at 4B is unexplored; and a second attempt at 0.6B weak-category once W2 explains the first.

  6. W6 — Substrate models blocked

    All four wait on warrant history. Zero rows exist. The unblock is product usage, not compute, and the corpus exporter already exists to capture it the moment there is any. No GPU time should be allocated to these.

6. Every run needs a hypothesis

The rule this programme learned the expensive way

What happened last time

supervise_severity=False was proposed as a fix, run, and refuted — recall fell 0.8329 → 0.6804 overall and 0.7947 → 0.5572 adversarial. The reasoning was wrong in a way that could have been reasoned about first: LoRA adapts weights both output fields share, so not computing a loss on severity never held it still; it only stopped correcting it while training moved it anyway.

Before any W4 or W5 run is submitted, it registers:

  • The hypothesis, in one sentence, and what would refute it
  • The statistic and the test — not just the direction. “Is it better” is not a statistic.
  • The precision and lane, because fp16-on-Kaggle and bf16-on-Modal are different conditions
  • The severity-distribution check, since flattening is this programme's most repeated failure mode and it presents as a win
  • The stop condition — what result abandons the line rather than extending it
