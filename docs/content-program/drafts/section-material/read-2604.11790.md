# Read note — arXiv:2604.11790 (ClawGuard)

**Source read:** full text, v2 [cs.CR] 11 May 2026 (v1 13 Apr 2026), HTML render of the
complete paper including Appendices A–G. Not read from the abstract.

**Citation:** *ClawGuard: A Runtime Security Framework for Tool-Augmented LLM Agents Against
Indirect Prompt Injection.* Wei Zhao, Zhe Li, Peixin Zhang, Jun Sun (Singapore Management
University). arXiv:2604.11790v2. Artifact: `github.com/Claw-Guard/ClawGuard/`. Built on and
evaluated inside the OpenClaw agent framework.

**Why it is in the sample:** it is the strongest runtime defense against indirect prompt
injection in the corpus, and it sits directly on the content-control boundary the survey's
scope excludes.

---

## 1. What it establishes

It establishes, with the largest injection-defense evaluation in the corpus, that a rule
check placed at the harness's own tool-dispatch boundary raises defense success far more on
the injection channels that model alignment handles worst — poisoned skill files and poisoned
MCP tool descriptions — than on the channel alignment already handles well, ordinary web and
document content.

Three results are load-bearing and should be treated as established:

1. **Channel asymmetry.** Undefended, the five backbones already reach at least 92.78% DSR on
   web/local injection (AgentDojo, InjecAgent, ChatInject) but only 56.67% (SkillInject),
   62.10% (MCPTox) and 75.86% (MSB) model-averaged on the skill and MCP channels. The same
   adversarial objective is roughly thirty points more effective when it is placed where the
   harness reads its own configuration rather than where the harness reads data. The paper's
   explanation is the right one: in the skill and MCP channels "the harmful action is no
   longer presented as abrupt external content, but instead appears to the model as part of
   the tool's intended semantics."
2. **A chokepoint recovers most of that gap.** ClawGuard lifts the model-averaged DSR to
   86.67% / 89.50% / 94.21% on the three hard benchmarks, beating MELON by 18.72 points and
   Task Shield by 10.57 points averaged across them. On the easy channels every defense
   saturates at or near 100% and the comparison carries no information.
3. **The residual failures are not action failures.** Six attacks survive on every backbone.
   All six achieve their objective *without issuing a suspicious tool call at all* — a
   corrupted SEO rubric, a relaxed safety-scoring rubric, ideological paragraph deletion in a
   document-editing task, a biased health rewrite. The paper's own words: the malicious
   behavior "appears as biased scoring, distorted comparisons, or unsafe content framing."

## 2. Method and interposition point

**Interposition point:** in-process middleware inside the agent harness, at the tool-call
dispatch boundary, evaluated *before* tool execution. It is not below the harness. There is no
kernel, seccomp, cgroup, network-namespace, proxy, or hypervisor component anywhere in the
design, and the paper does not claim one.

**Mechanism — four components at every call, plus a one-time induction step.**

- *Content Sanitizer* `S_in` / `S_out`: a regex pattern library `P` redacts credential-shaped
  spans from outgoing tool arguments and from incoming tool returns before either enters the
  conversation history. The default library covers cloud keys, tokens, cryptographic material
  and database connection strings (Appendix D).
- *Rule Evaluator* `V`: matches attributes extracted from the sanitized call `a* = (t_j, q*)`
  against a blacklist/whitelist pair over three domains — `cmd` (native tool names and shell
  strings issued via `exec`), `file` (resolved paths), `net` (outbound destinations). Verdicts
  are `⊥` deny, `⊤` allow, `amb` otherwise (conservative default). Blacklist beats whitelist;
  most-restrictive-wins across attributes. An obfuscation normalizer (hex/octal/unicode
  escapes, `$(...)`, backticks, base64 pipelines, `${IFS}`, quote mixing, backslash runs,
  `eval`) scores a command and escalates medium/high to `amb`.
- *Skill Inspector* `I`: an LLM judge returns a binary verdict on a skill's full content
  before its **first-ever** execution; approved skills enter a persistent allowlist `Ψ` and
  are never re-inspected until the content changes.
- *Approval Mechanism*: `amb` calls queue for explicit user authorization with timeout `τ`;
  reject or timeout blocks. All events append to a local Audit Log as
  `⟨a*, V(a*,R), verdict, ts⟩`.

**Rule set** `R = R_base ∪ R_task`. `R_base` is operator-fixed, MITRE-ATT&CK-organized, with
`deny`/`queue` actions that `R_task` cannot override (Appendix E: `rm -rf /`, fork bombs,
reverse shells, `~/.ssh/` `~/.aws/` `*.pem` `~/.env`, the agent's own config directory,
private IP ranges, `.onion`, URL shorteners, paste sites, tunneling services; `sudo`, package
installs, `crontab`/`systemctl` are `queue`). `R_task` is **generated by the LLM backbone
itself** from a synthesis prompt over `H_0` — the conversation containing only the user's
stated objective — before any tool runs, then shown to the user for review and edit.

**Scale.** Six attack benchmarks / 1,734 attack scenarios (AgentDojo 194, InjecAgent 544,
ChatInject 194, MCPTox 438, MSB 280, SkillInject 84) × five backbones (DeepSeek-V3.2,
MiniMax-M2.5, Qwen3.5-397B-A17B, GPT-5.4, Claude-Sonnet-4.6) × four arms (undefended, MELON,
Task Shield, ClawGuard). Utility on WebArena (812), AgentBench-OS (166), SWE-bench Lite (300):
87.4% utility retention at zero approvals, 95.1% at up to three, 5.0% average token overhead.
Real-world arm: 23,794 SkillHub skills scanned, 283 flagged malicious or suspicious, three
generated prompts each. GPT-5.4 serves as the automated judge for ASR/DSR/RR throughout.

## 3. Where it lands on the two-column rule

**Tier of acceptance: A-T3.** The claim ClawGuard verifies is *"this proposed call lies inside
the user-confirmed scope."* Verification is a pattern match plus, for skills, an LLM verdict —
both executed in-process by the same runtime whose behavior is in question. Nothing is signed,
attested, or independently checkable: the confirmed rule set carries no authenticator, the
authorization decision produces no receipt, and the Audit Log is a local append with no
tamper-evidence and no third-party verifiability. Part of the acceptance decision is not even
deterministic — `R_task` is model output and the skill verdict is model output. A defensible
alternative coding is **A-NONE for the induced half of `R`**, since no verifier independent of
the attacked model exists for it; A-T3 is the charitable reading, on the ground that the check
itself, given a rule set, is a deterministic application-level evaluation.

**Tier of action: B-T3.** Bounding is at an application chokepoint and only there. Every
effector reached by a path that does not traverse the harness's dispatcher is outside the
bound, and the rule set does not propagate into anything the harness starts.

**Score: A-T3 / B-T3.** Notably this is *not* an instance of the modal A-T1/B-T3
authorization–execution gap: ClawGuard makes no cryptographic acceptance claim at all, so it
does not exhibit the gap between a strong acceptance tier and a weak action tier. It is the
honest floor of both columns — and it is the best-performing action-bounding system in the
sample. That is itself worth stating: the corpus's strongest empirical result on bounding
actions is produced by a system with no cryptography in it anywhere.

**Binds lower than advertised: yes.** Two advertised phrases outrun the mechanism.
"Deterministic, auditable" is true of the evaluator and false of the policy it evaluates
against — the paper's own RQ3 concedes that "ClawGuard itself relies on the same underlying
model and therefore inherits its limitations," and that residual failures cluster where "the
task-specific rule induction during the planning stage become[s] less precise." And
"intercepts adversarial tool calls before any real-world effect is produced" holds for the
call that is evaluated, not for the effects of a call that was permitted.

**Derived mediation coverage (seven effectors).** No cell reaches *covered*.

| Effector | Coding | Basis |
|---|---|---|
| File write | partial | native `write` path-checked against `W_file`/`B_file`; a write performed by a permitted subprocess is unseen |
| Subprocess spawn (incl. descendants) | partial at spawn, **not covered** for descendants | `exec` string evaluated with the obfuscation normalizer; no process-tree tracking, no cgroup, no ptrace — the child and its children inherit full ambient user authority |
| Network egress | partial | destination string checked and unlisted endpoints queued, but egress from inside a permitted `exec` (curl, a script, an installer) traverses no dispatcher, and no netns, proxy or firewall exists |
| VCS push | not covered | no push-specific rule; reachable as `exec git push` wherever `R_task` admits `exec` |
| Package install | partial | `apt/pip/npm install` are `queue` in `R_base` as literal command strings; an install driven by a Makefile or a vendored script inside a permitted `exec` is unseen |
| Credential use | partial | strongest cell — `S_in`/`S_out` redaction plus `R_base` denies on `~/.ssh/`, `~/.aws/`, `*.pem`, `~/.env`, browser profiles; credentials already in the process environment, or read by a child process, are unbounded |
| Sub-agent spawn | not covered | not modeled as an effector; skills are inspected once per content version and thereafter cached in `Ψ` across all future sessions |

**Adversary placement.** Primary **A2** (in inputs — adversarial instructions in tool-returned
web pages, documents, search results). Secondary **A3** (in policy — poisoned skill files and
poisoned MCP tool-description metadata are read by the harness as its own configuration, not
as data). The defense itself sits at **A4**, inside the harness. This places ClawGuard's whole
evaluation in the **A2×A4 cell**, the cell in which every composition failure in the survey
falls, and its Table IV is empirical confirmation from inside that cell: an in-harness
mediator whose acceptance decision is computed by the same model the adversary is attacking
fails exactly where the adversary attacks the decision rather than the call.

Worth carrying into the placement section: the paper's own numbers show the A3-placed variant
of an identical objective defeats the same models by roughly thirty points of DSR more than
the A2-placed variant. Placement, not payload, is the dominant variable.

**Enforceability: split.** The advertised objective — "blocks all three injection pathways" —
is not monitorable: no finite execution witnesses that no injection pathway remains. The
surrogate actually enforced — "the attribute string of this call matches no deny pattern and
matches a whitelist pattern" — is monitorable and is enforced. A clean instance of the split
coding, with a monitorable surrogate sitting beneath a non-monitorable advertised objective.

## 4. Weakest attackable point

**The security result is measured under a different enforcement policy than the utility
result, and the difference is exactly the mechanism's discriminative power.**

`amb` is the conservative default for everything not explicitly whitelisted. The security runs
use "a non-interactive approval policy: whenever OpenClaw would normally request human
approval for a sensitive action, the request is denied by default." The utility runs report
their headline retention (95.1%) under "up to three approvals allowed," and the zero-approval
utility figure is 87.4%. So the reported DSR is the DSR of *deny everything not whitelisted*,
while the reported usability is the usability of *ask the user three times*. Nothing in the
paper isolates how much of the DSR gain comes from the induced rules being *accurate* versus
from the default verdict being *deny*. A deny-by-default chokepoint with an empty `R_task`
would score well on the same metric. The comparison that would settle it — DSR under the
three-approval policy, or DSR with `R_base` only and `R_task` empty — is not run.

Three secondary attackable points, in descending force:

- **The policy is generated by the attacked artifact.** `R_task = M(ρ, H_0)`. The model the
  adversary is trying to redirect also writes the rules that constrain the redirection. The
  user-confirmation step is the only independent input, and it is a review of machine-written
  rules by a user who did not author them. The RQ3 failure analysis states the consequence
  plainly for weaker backbones.
- **`exec` is a string check in front of a shell.** The obfuscation normalizer is a heuristic
  denylist of known shell evasions operating on the pre-execution string. It cannot see a
  payload assembled at runtime, resolved from the environment by the shell, written to a file
  in an earlier permitted step and then run, or fetched by the child. And once `exec` returns
  `⊤`, the entire subtree runs unconstrained: the rule set has no representation in the
  operating system.
- **Skill approvals are cached indefinitely.** `Ψ` persists "across all future sessions" keyed
  to content version. A skill that is benign at inspection and fetches its instructions at run
  time is inspected once and trusted permanently.

## 5. What it FORECLOSES for this paper

- **Any novelty claim over pre-execution, task-scoped tool-call mediation.** It exists, it is
  implemented in a production-grade harness, and it is evaluated at scale. Language asserting
  that no one bounds actions at the tool-call boundary is false.
- **Any claim that skill-file and MCP-tool-description injection are unmeasured.** SkillInject,
  MCPTox and MSB are established benchmarks and are re-run here across five backbones.
- **Any claim that the utility cost of mediation is unknown.** 87.4% / 95.1% retention and 5.0%
  token overhead are on the record with a method attached. Cost arguments must engage them.
- **Any claim that authorization decisions go unlogged.** An audit log of `⟨call, verdict, ts⟩`
  exists — the survey's complaint must be about the *verifiability* of that log, not its
  absence.
- **The framing "these systems bound nothing."** Eleven of fifteen bound at an application
  chokepoint; ClawGuard is the best of them and the number it produces is real. The claim has
  to stay precisely where it is — bounded at T3, not unbounded.

## 6. What it LEAVES OPEN

- **The entire A column.** No signature over the confirmed rule set, no receipt over the
  authorization decision, no anchoring, no attestation, no externally verifiable log. The
  strongest action-bounding system in this literature offers acceptance that a third party
  cannot check at all. This is the survey's opening.
- **Everything below the harness.** No kernel, sandbox, netns, seccomp, cgroup, egress proxy
  or hypervisor bound appears anywhere. The authors scope out an adversary who "can directly
  modify the user's instructions or the system configuration itself," and note that real
  deployments "expose agent ports to the public Internet." A5 is untouched, and a defense at
  A4 has nothing to say about it.
- **Descendants, VCS push, sub-agent spawn.** Three of the seven effectors have no mechanism
  here at all. The descendant case is the sharpest: the central mechanism is a check on a
  command string that is then handed to a shell.
- **Composition.** A single framework, a single mediator. The authors name transfer across
  harnesses with different tool abstractions and approval semantics as future work. The A2×A4
  composition question — what happens when the mediator's own decision procedure is the target
  — is raised by their Table IV and left unanswered.
- **The relationship between deny-by-default and rule quality.** Unmeasured, per §4.

## 7. Is the content-control exclusion defensible?

**Yes — and this paper is the evidence for it, not the threat to it.**

The six residual failures that survive on every backbone (Table IV) are exactly and only the
cases in which the adversarial objective is achieved **without any effector being reached**:
an SEO review returns a high score it should not; a safety rubric is relaxed; a document is
rewritten with pharmaceutical skepticism; paragraphs matching "climate", "sustainability",
"diversity", "inclusion" are deleted during a routine edit. The paper diagnoses these as
attacks that alter "the evaluation or judgment criteria embedded in otherwise legitimate user
tasks," producing "subtle output-level effects [that] generate weaker signals that are harder
for task-scope authorization to catch at runtime."

That is not a gap in ClawGuard's rule coverage. It is a category boundary. The two-column rule
scores *at what tier a claim is verified* and *at what tier an action is bounded*. Where the
harm is realized entirely in the content of a response, there is no action to bound and the
B column has nothing to score; the A column can still score whether the *output* was
authenticated, but authenticating a corrupted output does not uncorrupt it. So the exclusion
follows from the instrument's domain rather than from convenience — which is the strongest
form the exclusion can take, and it should be stated that way in the scope paragraph, with
this paper's failure table cited as the demonstration.

**Two conditions the exclusion must carry to stay honest:**

1. **State it as a boundary, not a dismissal.** The excluded class is real, it is where the
   best runtime defense in the corpus still fails, and the failure rate is not negligible —
   six of eighty-four SkillInject scenarios, consistently, on every backbone including the two
   strongest. The survey should say the class exists and that its instruments do not reach it,
   rather than implying it does not matter.
2. **Do not let the exclusion leak.** The moment corrupted content is *written* — the `docx`
   cases end in an edited file — a file-write effector has been reached, and that write is
   inside the coverage table whether or not its contents are. The boundary is "the harm is
   realized without crossing an effector," not "the task involved text." Draw it on the
   effector, not on the subject matter, or the exclusion will be attacked as a way of defining
   away the hardest cases.

## 8. Suggested related-work paragraph (third person)

> The closest runtime system to the action column of this survey interposes middleware at the
> tool-call boundary of a production agent harness, evaluating every proposed call against a
> rule set whose task-specific half is induced from the user's stated objective before the
> first tool is invoked, and it reports the largest injection-defense evaluation in this
> corpus: six attack benchmarks, five backbones, and a scan of 23,794 public skills. Under the
> two-column rule it scores A-T3/B-T3 — acceptance is decided by pattern matching and an LLM
> judge running inside the same process the adversary is attacking, with no signature, receipt
> or externally checkable log, and actions are bounded at the harness's own dispatcher, so a
> permitted `exec`, its descendants, and any egress they perform leave the mediated set
> entirely. Its own residual-failure analysis is the sharper result: the six attacks that
> survive on every backbone succeed without issuing a suspicious tool call at all, corrupting
> an evaluation rubric or filtering a document instead. That marks precisely where an
> action-bounding instrument stops applying and content control begins, and it is why this
> survey excludes content control by construction rather than by convenience — where no
> effector is reached, there is no action to bind and the two-column rule has nothing to score.
