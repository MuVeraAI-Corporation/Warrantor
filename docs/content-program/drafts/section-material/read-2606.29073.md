## 1. What it establishes

HCP argues that the Model Context Protocol standardizes *connection* and leaves *execution* authority
scattered across clients, servers, prompts, approval dialogs, OAuth deployments and optional logs. It
names eight execution-layer invariants, implements them in a reference broker runtime, and benchmarks
that runtime against two self-constructed baselines on ten cases.

### 1.1 The eight invariants (verbatim from Table 1)

| ID | Invariant | Expected runtime behavior |
|---|---|---|
| **I1** | Tool metadata is not policy authority. | Tool descriptions and prompts cannot grant permission or override policy. |
| **I2** | Approval cannot bypass grant. | High-risk actions require both a matching grant and approval. |
| **I3** | Caller resource cannot override provider canonical resource. | Policy uses provider-resolved resources. |
| **I4** | Principal is bound to grant, task, handle, and audit. | Wrong principals cannot invoke or inspect owned handles. |
| **I5** | Scoped capability invocation is grant-backed. | Required scopes trigger principal, resource, and capability matching. |
| **I6** | Data pipe authorizes source and target. | Source ownership and target capability policy must both pass. |
| **I7** | Deny paths are auditable. | Failed invocations, peeks, pipes, and policy decisions leave evidence. |
| **I8** | Session and protocol state are explicit. | Missing initialization, wrong versions, and stale sessions fail predictably. |

The runtime object model is Principal, Resource, Grant, Capability, Policy Decision, Handle, DataPipe,
Audit Entry. Ordering carries the argument: the invocation path runs principal → provider-canonical
resource → grant match → approval gate → provider invoke → owned handle → audit allow/deny → stable
failure reason. Approval is explicitly a *second* gate placed **after** grant matching, never a
substitute for it. Denial reason codes are part of the contract (`INSUFFICIENT_SCOPE`,
`RESOURCE_DENIED`, `MISSING_GRANT`, `HANDLE_ACCESS_DENIED`, `INITIALIZATION_REQUIRED`, plus expired or
revoked grant, capability mismatch, missing principal).

I7 is held apart from the other seven and scored on a separate axis. It prevents nothing, and the
paper says so: a runtime can block a bad call by raising an exception, but that does not by itself
establish forensic evidence.

### 1.2 The headline claim

Across 10 cases: the naive connection-layer baseline (B0) permits 10 of 10; the practice-informed
connection-layer mitigation baseline (B1) permits 6 of 10 and blocks 4; the HCP runtime (B2) blocks
10 of 10 and records complete audit evidence on all 10. The stated claim boundary is narrow and
repeated: this is an *invariant-coverage* benchmark, and the value of the result is "not that HCP
blocks all possible attacks, but that each claimed invariant is executable, testable, and fails under
targeted ablation."

## 2. Method and scale

**Corpus of cases: 10, in five classes of two.** Tool poisoning (2), confused deputy (2), excessive
permission and approval fatigue (2), context poisoning through data pipes (2), transport-session
confusion (2). Every case is a JSON fixture. No third-party MCP server is executed, no credential is
collected, no live exploitation is attempted.

**Three execution modes, not two.** B0 is a declared lower-bound control. B1 adds metadata linting,
warning banners, per-call approval prompts, an identity field, and session and version checks — the
author states plainly that B1 exists to avoid a strawman comparison. B2 is HCP. Table 2 enumerates
the enforcement-surface differences honestly: B1 and B2 both have linting, session checks and
per-call approval; only B2 has provider-canonical resource resolution, a runtime grant store,
capability-bound scope checks, owned-handle checks, DataPipe source-and-target policy, and deny-path
audit.

**Per-class result — the diagnostic, and more informative than the aggregate.** B1 blocks 0/2 tool
poisoning, **2/2 confused deputy**, 0/2 excessive permission, 0/2 data pipe, **2/2 transport-session**.
B2 blocks 2/2 in every class. Connection-layer mitigations reach identity and session state; grant,
handle and data-flow boundaries require runtime objects.

**Counterfactual ablation (Table 5), one component disabled at a time.** Grant matching → 6 of 10
cases exposed. Approval gate → 2. Handle-owner check → 1. Data-pipe target policy → 1. Protocol
initialization gate → 2. Protocol version check → 2. Deny-path audit → 0 cases exposed but **audit
loss in all 10**. The ablation harness bypasses the runtime rather than editing its source.

**Overhead.** Local in-memory microbenchmark, 50 iterations per operation, same Node.js process,
after warm-up. Mean latency: policy explanation 0.021 ms; task-start read 0.101 ms; preview peek
0.004 ms; data-pipe write 0.118 ms. The run produced 888 audit entries and 371,179 bytes of JSON
audit data. Explicitly disclaimed as not a production throughput number.

**Four auxiliary experiments, each labeled auxiliary.**
- *Developer-effort proxy* (§7.4): a configuration-surface count, not human hours — 195 non-empty case
  configuration lines, 60 policy-relevant fields, 12 grant edges, 6 approval gates, 4 handle bindings,
  7 protocol-state fields.
- *MCP-compatible coverage* (§7.5): 18 coverage items, 18 with checked evidence; 7 primitives, 6
  transport and session, 5 notification and task; 15 stdio-backed, 17 HTTP-backed, 1 SSE-backed. The
  denominator is defined by the reference shim, not by the MCP specification — stated as such.
- *Operator-governance surface checks* (§7.6): 10 local fixtures comparing a plain configuration
  surface against the HCP governance layer. Governance gaps 10 → 0; approval summary fields 1 → 10;
  audit explanation entries 0 → 8. Explicitly not a user study.
- *Ecosystem measurement* (§7.7): GitHub README keyword screening, snapshot 2026-06-22 — 90 raw rows,
  80 deduplicated, **40 retained**. 12 risk-flag categories; top flags are unclear audit story (40),
  repository or code authority (15), browser control (7), external network authority (7), cloud
  infrastructure authority (6), credential requirement (5), persistent memory or profile behavior (5).
  Adjudicated labels across 95 flag instances: 29 README-confirmed authority surfaces, 22 audit-story
  absences, 15 explicit counter-evidence items, 11 not supported, 18 ambiguous. Labeled a
  "README-visible signal under the bounded rubric," not a confirmed vulnerability.

**Scale summary for the SoK's purposes: n = 10 adversarial cases, 3 modes, 7 ablations, 4 latency
operations, 18 compatibility items, 10 governance fixtures, 40 screened repositories.** Nothing runs
against a real deployment.

## 3. Does it operate inside one enforcement tier, or across tiers?

**Inside one, and the paper concedes the boundary in its own threat model.** This is the finding that
matters most for the two-column rule.

All eight invariants are predicates evaluated by a single component — the broker — and that component
is trusted by assumption: the runtime, policy engine, grant store, data vault and audit log are
declared trusted for the purpose of the paper. The security boundary is drawn a sentence later: the
benchmark does not model an attacker who compromises the trusted runtime process.

Three consequences follow.

1. **No cryptography appears anywhere in a construction.** No signature, no MAC, no nonce, no
   attestation, no anchoring, no key. §9 lists provider attestation, sandbox isolation, cryptographic
   signing and persistent policy stores as outside scope. A grant is an in-memory record; an approval
   is a flag; an audit entry is an in-memory object with no integrity protection and no durability.
   Nothing HCP asks a relying party to accept is bound by a primitive.
2. **No operating-system mechanism appears anywhere.** No namespace, no seccomp, no cgroup, no uid
   check, no network policy. The paper says outright that it does not claim the reference provider
   sandbox is sufficient for arbitrary shell, browser or network workloads.
3. **The invariants are capability-control predicates, not tier boundaries.** I1 through I6 all take
   the form "the broker must consult field X before dispatching." They are good predicates. They are
   defeated in one step by anything that reaches dispatch without traversing the broker, or by
   anything running in the broker's own address space — which is the same Node.js process as the
   providers it mediates.

HCP is therefore a *within-tier* discipline. It partitions authority cleanly inside the application
tier and makes the partition testable. It never establishes a fact that survives a party the paper
declines to trust, and it never binds an effect by a mechanism outside the deciding party's control.

## 4. Where it lands on the two-column rule

**Score: A-T3 / B-T3.** Both columns land in the application tier, independently, and neither is a
close call.

**Column A — tier of acceptance: A-T3.** Verification exists (grant match, principal binding, resource
canonicalization, approval state), so this is not A-NONE. But every fact a relying party is asked to
accept — that a grant exists, that an approval was given, that a handle has this owner, that this
denial occurred — is in-process application state with no cryptographic binding and no external
verifier. Forging acceptance requires no primitive break of any kind; it requires writing to a map in
the process that also runs the providers. Under the weakest-link rule, A-T3.

**Column B — tier of action: B-T3, application chokepoint, with a documented residual beneath it.**
The broker is a genuine chokepoint for capabilities routed through it, which is what earns T3 rather
than B-NONE. But the effect itself is performed by a provider the runtime does not confine: no
sandbox, no namespace, no egress filter. The paper states this residual itself. A provider that opens
a socket or spawns a child never traverses the DataPipe check at all.

**HCP therefore joins the A-T3/B-T3 cell** — the cell that currently holds six works (SEAgent,
CaMeL-NOVA, Arbiter-K, AgentCgroup, SandScope, TDX) and that the single-column rule was right about.
It is *not* an instance of the authorization-execution gap: the gap is A-T1/B-T3, and HCP never
reaches A-T1. That is worth saying in the paper, because HCP is the clean demonstration of the
alternative failure — **tier uniformity achieved by leveling downward**. A system can be perfectly
consistent across both columns and still bind nothing. Consistency is not the property this corpus
lacks.

**Derived mediation coverage over the seven effectors** (scoring HCP as if it were a corpus row):

| Effector | HCP | Basis |
|---|---|---|
| File write | **partial** | `excessive-permission-001` gates a workspace write on grant plus approval at the broker; the provider performs the write with no OS bound. |
| Subprocess spawn (incl. descendants) | **not covered** | No shell mediation is claimed. §7.6 *surfaces* risky local server commands as governance evidence — visibility, not mediation. Descendants never appear in the text. |
| Network egress | **partial** | Reached by an external-send capability in three cases (`tool-poisoning-002`, `excessive-permission-002`, `context-poisoning-datapipe-001`) and gated on grant, approval and data class at the chokepoint. Not bounded beneath the application; a provider can egress directly. |
| VCS push | **not covered** | Never appears. |
| Package install | **not covered** | Never appears. |
| Credential use | **partial** | Server-held credentials are a named protected asset and both confused-deputy cases target them, but the bound is in-process grant matching, not credential isolation from the agent. |
| Sub-agent spawn | **not covered** | Never appears. |

Three partials, four not covered, **zero covered** — consistent with the corpus result of 2 covered
cells in 105.

**Adversary placement.** Primary **A2 (in inputs)**: the tool-poisoning, data-pipe and
context-poisoning cases all place the adversary in tool metadata or tool output. Secondary **A1
(outside)**: the confused-deputy cases place a second principal outside the trust boundary. A3 is
touched at the margin (a compromised MCP-like server), but the server is *partially* trusted by
construction rather than modeled as policy-bearing. **A4 is excluded by the paper's own words**, and
**A5 never appears.** HCP therefore contributes nothing to the A2×A4 composition cell where all 20
composition failures sit — it is defined out of that cell.

**Enforceability coding.** This is close to a clean **split**, but a split of a distinctive kind, and
it should be flagged rather than coded silently. The monitorable surrogate is the invariant set:
eight predicates with reason codes, all decidable at dispatch, all measured. The advertised objective
— that MCP-style agent systems need an execution-control layer, and that the runtime is responsible
for enforcing principal, grant, approval, handle and data-flow checks around the provider boundary —
is not monitorable, because the provider boundary is exactly where the runtime stops. Whether that
counts as the same split observed on 50 of 50 codings, or as a fourth category in which the surrogate
is honestly disclosed *as* a surrogate, is a coding decision. **Recommendation: code it split, and use
it in the discussion as the case where the split is declared by the authors rather than discovered by
the coder.** That is the strongest available evidence that the split is structural and not an artifact
of adversarial reading.

## 5. Weakest attackable point

**The trusted computing base is the thing being mediated.** The broker, the policy engine, the grant
store, the vault and the audit log are all in-memory objects in the same Node.js process as the
reference providers whose behavior they are supposed to constrain. Every invariant is a check the
attacker's own address space performs on itself. The paper handles this by declaring the runtime
trusted and the in-process attacker out of scope, which is honest and is also precisely the
assumption that decides the result. The A2 adversaries actually modeled are content in inputs, and
content in inputs is exactly the class most likely to end up executed by a provider that shares the
broker's process.

**Second weakest: the benchmark, the baselines, the oracles and the runtime were authored together.**
B1 is not a deployed system; it is the author's model of practice. The case oracles define what
"blocked" means, and each case is constructed to cross exactly one boundary the runtime owns. Ten out
of ten is therefore not a measurement of defensive coverage — it is a check that the implementation
matches its own specification. The paper concedes this, and the concession should be quoted rather
than argued against, because a reader who misses it will read 10/10 as a security result.

**Third: nothing is durable and nothing is exercised live.** Grants, handles and audit entries do not
survive the process. The forensic claim in I7 rests on a log that an attacker with process access can
rewrite and that a crash erases. The ecosystem section is README keyword matching over 40
repositories with a 90-character snippet radius; it establishes that projects describe authority
surfaces and rarely describe audit, which is a claim about documentation, not about systems.

**Not attackable, and should not be attacked:** the claim discipline is unusually good. The paper
disclaims production readiness, MCP certification, real-user evidence, third-party exploitability and
exploit prevalence, each in its own sentence. Attacking it for overclaiming would be inaccurate and
would cost the SoK credibility. The correct critique concerns the tier the claims live at, not the
honesty of the claims.

## 6. What it FORECLOSES for our paper

1. **Any claim to be first in separating approval from authorization.** I2 — approval cannot
   substitute for grant — is a named, implemented, ablated invariant, and the ablation quantifies it
   (removing the approval gate exposes 2 of 10; removing grant matching exposes 6 of 10). This is a
   near-neighbor of the authorization-execution gap expressed at one tier, and it must be cited where
   the gap is introduced, not only in related work.
2. **Any claim to be first in treating data movement as a fresh authorization event.** I6 requires
   both source-handle ownership and target-capability policy, with data-class compatibility, and is
   argued explicitly against content filtering. The contribution has to be framed as tier of action,
   not as flow awareness.
3. **Any claim that runtime-invariant work in this literature is unfalsifiable or unablated.** §7.2 is
   a per-component counterfactual ablation with numbers. The methodological complaint must be sharper
   than "these systems are not tested."
4. **Any claim to be first in scoring evidence separately from prevention.** §6.4 scores attack
   success, blocked outcome and audit completeness as three fields, and §4 argues the separation on
   principle. The enforceability split is about *objectives*, not about prevention versus evidence,
   and the difference must be stated or a reviewer will read the two instruments as the same one.
5. **Any claim that no reference runtime exists for MCP-layer execution control.** One exists, with a
   public artifact.

## 7. What it LEAVES OPEN

1. **The entire cross-tier question.** HCP has no cryptography and no OS mechanism. It cannot land in
   the A-T1/B-T3 cell, cannot exhibit the authorization-execution gap, and offers no instrument for
   detecting it. The two-column rule is exactly what this paper lacks — and, more useful, HCP is an
   existence proof that a system can be internally consistent across both columns while binding
   nothing that survives its own trust assumption.
2. **A4 and A5 adversary placement.** Excluded by the threat model in a single sentence. The 20 A2×A4
   composition failures are untouched by anything here.
3. **Effector enumeration.** Effectors are never enumerated. Subprocess descendants, VCS push, package
   install and sub-agent spawn are absent from the text; network egress is named as a capability and
   never bounded beneath the application. The 105-cell coverage table has no counterpart.
4. **The corpus-scale adjudication.** This is one system with two self-built baselines. It ranks
   nothing, compares nothing across published work, and never asks whether a system's advertised tier
   matches its verified tier — the 12-of-14 result has no analog here.
5. **Anchoring, receipts and durability.** The audit story is in-memory and unprotected, and §9 lists
   durable storage, retention policy, signature verification and attestation as future work.
   Everything the acceptance column is about is named as unbuilt.
6. **Whether the invariants survive a real deployment at all.** No third-party server is executed, no
   live workload is run, and the overhead measurement is in-process.

**Decision for the SoK.** HCP is not one of the 15 scored works and does not appear in the corpus
documents. It is a strong candidate either for a 16th row or for a related-work paragraph.
**Recommendation: keep the corpus frozen at 15 and cite HCP in related work.** Adding it would move
A-T3/B-T3 from 6 to 7 and change no headline number, while re-opening a frozen corpus this close to
submission costs more than the row is worth. If a reviewer asks why it is absent, the honest answer is
that it is a preprint with no venue, appearing after the corpus cutoff, and that scoring it changes
nothing — a better answer than a rushed sixteenth coding.

## 8. Suggested related-work paragraph (third person, US English)

> The closest single-system precedent is a reference runtime for MCP-style agent execution that
> defines eight execution-layer invariants — metadata non-authority, grant-backed approval, canonical
> resource resolution, principal binding, scoped capability invocation, source-and-target data-flow
> authorization, deny-path audit, and explicit protocol state — and benchmarks them across ten
> adversarial cases against a naive connection-layer baseline and a practice-informed mitigation
> baseline, blocking ten of ten where the mitigation baseline blocks four. That work independently
> reaches one half of the distinction developed here: its second invariant holds that approval cannot
> substitute for authorization, which is the authorization-execution gap observed within a single
> process. It does not reach the other half, because it has no instrument for comparing the tier at
> which a claim is verified against the tier at which an effect is bounded — its runtime, policy
> engine, grant store, data vault and audit log are trusted by assumption and share an address space
> with the providers they mediate, so every invariant is a predicate the application tier evaluates
> about itself. Scored on the two-column rule it lands at A-T3/B-T3, which makes it the clearest
> available demonstration that tier consistency across the two columns can be obtained by leveling
> downward rather than by binding anything, and that consistency is therefore not the property this
> literature is missing.

*(Four sentences. Third person throughout; no first-person plural, and no repository or product names
belonging to the authors of the present work. US English forms used throughout: authorization,
behavior, analyze, defense, license, judgment, modeling, toward, gray.)*
