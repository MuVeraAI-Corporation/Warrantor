**Citation.** Shenghan Zheng (Dartmouth College), Qifan Zhang (Palo Alto Networks), Zheng Zhang
(Meta), Haonan Li (UC Riverside), Christophe Hauser (Dartmouth College). *Formal Security Analysis
of Agent Protocol Composition.* arXiv:2606.28690v1 [cs.CR], 27 June 2026. 11 pages, CC BY 4.0.

## 1. What it establishes

AgentThread is a source-linked assurance pipeline that carries agent-protocol security claims from
specification prose through formal model checking to executable SDK tests, and then asks who owns
each control. Three things it establishes, in descending order of how much they constrain the
present work.

**(a) Composition failures in agent protocols are real, formally witnessed, and structurally
unowned.** Across eight composed protocol pairs the authors instantiate 43 security-oriented
composition obligations (31 boundary-risk, 12 bridge-contract preservation); **30 of the 43 admit
counterexamples**. A separate set of 40 bounded model-validation invariants all pass and is
excluded from that denominator, so 30/43 is a rate over security obligations, not over all TLC
checks. The conclusion drawn is that "the most security-critical logic often sits in the bridge,
conductor, relay, or agent runtime that connects two protocols, yet these components are typically
outside the normative security scope of either protocol."

**(b) Enforcement of agent-protocol controls is essentially absent in practice.** From 35
Responsibility IR records across four protocols (MCP 14, A2A 9, ANP 5, ACP-Client 7; ACP-Cap
archived): **exactly one security-relevant control is both owned and enforced** — ANP's DID-based
identity verification. Every other control that counts as enforced is a structural wire-format or
session-lifecycle check. **18 of 32 total gaps are enforcement gaps**: responsibility is assigned
in the specification and no SDK mechanism exists to discharge it. Composition is described as
"universally orphaned" — no protocol owns bridge security for chained MCP servers, A2A conductors,
or MCP tools inside ACP-Client.

**(c) Specification-level gaps are pervasive but must be read against an evidence taxonomy.** Over
a 5x11 matrix (55 protocol-check cells) the authors report **35 spec-level findings, of which 12
are confirmed by implementation tests, 23 are specification-only, 10 cells pass, and 10 are N/A**.
Two gaps appear in all five protocols: audit completeness and credential/registry integrity. The
taxonomy that governs how a failure may be described — Spec-Mandated (non-conformance),
Spec-Recommended (recommendation gap), Framework hardening (design gap), Layer completeness
(architectural gap) — is a genuine methodological contribution and is more disciplined than most
adjacent work. Only MUST-backed failures are called violations.

A fourth result deserves separate mention because it is the hook (see section 5): **"even DID-based
identity verification provides no mechanism to bound content integrity or delegation scope."** The
paper's one positive enforcement result is a cryptographic bind on identity claims that the authors
then report as having no consequence for what the agent may do. They observe the phenomenon and do
not name it.

## 2. Method and scale

**Object of analysis.** Five public agent protocols: MCP, A2A (Agent-to-Agent), ANP (Agent Network
Protocol), ACP (Agent Communication Protocol, written "ACP-Cap"), and ACP-Client (Agent Client
Protocol). Plus their production SDKs and three official MCP reference servers.

**Pipeline.**
1. *Source collection (manual).* Prose specs, role-specific docs, schemas, examples, SDK docs,
   reference implementations, with a declared precedence order (normative spec text > schema >
   SDK/reference code > example) and unresolved disagreements recorded as ambiguities.
2. *Normative clause extraction (machine-assisted, validation-gated).* Each clause stored with RFC
   2119 modality, a source reference (URL + anchor), an actor binding, and an explicit ambiguity
   flag. Records are rejected if the source span is absent from the document or the enums are
   ill-formed.
3. *Typed IR construction (machine-assisted, validation-gated).* Three record families: clause
   records (provenance), transition records (behavior), property records (taxonomy labels). A
   parallel **Responsibility IR** records governing clause, modality, security-policy clause,
   claimed principal, observed SDK enforcement, gap type, and evidence level. Gap types are
   *ownership, split-duty, enforcement, scope, composition-orphan*. Explicitly framed as extending
   NIST OSCAL from fixed control catalogs to protocol-derived clauses.
4. *IR-to-TLA+ compilation (automated).* Actors become quantified principals; triggers and
   preconditions become guarded actions; MUST becomes a safety invariant, SHOULD an annotated
   hardening invariant, NOT_SPECIFIED an under-specification finding; `ambiguity: true` becomes
   nondeterministic branches so TLC explores both readings. Action kind is preserved as Protocol /
   Environment / Adversary.
5. *Phase 1 — spec checking.* TLC v2.19, one configuration per invariant (deliberately not
   conjoined, so each violated check yields its own shortest counterexample). Triage as Spec-Fail /
   Model-Fail / Ambiguity-Fail.
6. *Phase 2 — implementation replay.* Counterexample traces are lowered through hand-written
   per-target protocol adapters into SDK or reference-server calls; the generating IR property
   supplies the oracle. Where no executable path exists, source/type-level evidence is recorded
   instead. Outcomes are Impl-Fail or Both-Fail. Behavioral evidence (B) and source/type-only
   evidence (S) are reported separately and never merged.
7. *Composition.* Pairwise only (triples rejected as state-space explosion that would obscure which
   bridge action caused the failure). A composed model is namespaced IR transitions of protocol 1 +
   namespaced transitions of protocol 2 + bridge actions + composition safety invariants. Each
   bridge action is guarded by a **finite capability contract** naming which context, credential,
   tool, consent, delegation, or audit rights the runtime may read, write, or exercise. So a
   counterexample identifies not only that state crossed the boundary but which bridge right
   permitted the crossing.

**Scale.**
- Protocol IR clause counts: MCP 37, A2A 17, ANP 16, ACP-Cap 12 (Table 3) / 8 (section 6.1), ACP-Client 15.
  Transitions/properties (section 6.1): MCP 11/7, A2A 6/6, ANP 11/7, ACP-Cap 7/6, ACP-Client 9/7.
- **80 implementation tests**: 18 MCP SDK, 13 A2A, 16 ACP-Client, 8 ANP, 9 ACP-Cap, 9 composition,
  7 MCP reference-server proof-of-concept (fetch 2, sqlite 2, git 3).
- **8 composed models**: MCP+A2A, MCP+MCP chained, MCP+ACP-Cap, A2A+ACP-Cap, A2A+A2A federated,
  MCP+ACP-Client, ANP+MCP, ANP+A2A.
- Pinned versions: TLC v2.19; MCP SDK v1.26.0, A2A v0.3.25, ACP-Cap v1.0.3, ANP v0.7.2,
  ACP-Client v0.9.0.
- **TLC bound: operation count = 12**, with tiny constants (e.g. MCP S=3, T=3, M=8; ANP A=3, M=6),
  justified on the grounds that the observed incidents turn on one tool per server rather than
  large deployments.

**Threat model — verbatim.** "We assume a protocol-level Dolev-Yao adversary [Dolev and Yao, 2003]
augmented with agent-specific capabilities. The adversary can inject instructions through tool
outputs, webpages, or peer-agent messages; forge or inflate capability metadata; and amplify
authority through delegation or tool chains."

**Security scope — verbatim.** "We treat transport security as an assumed substrate and focus on
the security obligations visible at the protocol and agent layers." The layered scope is L1 message
/ wire-format integrity, L2 session lifecycle, L3 identity / capability binding (these three the
"RPC layer"), L4 semantic operation controls, L5 audit / accountability (the "agent layer").

**Modeling boundary — verbatim.** "We model protocol effects of semantic content and delegated
authority, not full LLM internals."

## 3. Adversary placement: does it go below the protocol layer?

**The prior claim was that it does not, and that an adversary-placement axis occupies that ground.
That claim is verified in substance and needs one correction in wording.**

*Verified.* There is no adversary beneath the protocol layer anywhere in the paper. The exclusion is
by explicit construction, not omission: transport security is an *assumed substrate*, and the layer
stack begins at L1 message/wire-format integrity. There is no compromised operating system, no
compromised host or kernel, no compromised supply chain for the SDK binary, no adversary in model
weights or in a policy artifact, and no adversary in the process or filesystem beneath the agent
runtime. The words *kernel*, *sandbox*, *seccomp*, *namespace*, *supply chain*, and *weights* do not
appear in a threat-model role anywhere in the text. Section 9 confirms the boundary directly: LLM
internals are out of scope.

*Correction to the wording.* AgentThread does place one adversary *inside* the harness. Bridge
actions may be declared `kind=Adversary` "when they model a bridge-level compromise (ADV-1 through
ADV-3 acting through the bridge)." The bridge, conductor, or agent runtime is, in the vocabulary of
the present work, the harness. So the defensible statement is **not** "no adversary at or inside the
runtime" but the two narrower and stronger statements:

1. **No adversary beneath the protocol layer.** Ground beneath L1 is assumed sound and never varied.
2. **Placement is a fixed assumption, not a variable.** AgentThread has *one* adversary with three
   capabilities, and those capabilities are locations in a *state machine* (Protocol / Environment /
   Adversary action kinds), not locations in a *deployment*. The paper never asks how a finding
   changes when the adversary moves, never scores a system by where its adversary sits, and never
   reports a result of the form "these two placements compose badly." ADV-1 through ADV-3 are
   referenced exactly once and never enumerated as a taxonomy.

Mapped onto the present work's five placements: **A2 (in inputs)** is AgentThread's entire operating
story — indirect prompt injection through tool output, webpage, or peer-agent message. **A4 (inside
the harness)** is touched exactly once, in one sentence, as bridge compromise, and is treated as a
protocol-layer participant rather than as an execution substrate. **A1 (outside)** is implicit in the
Dolev-Yao inheritance but never exercised as a distinct placement. **A3 (policy or weights)** and
**A5 (below the harness)** are absent, A5 by declared assumption.

## 4. Weakest attackable point

The arithmetic is *not* the weak point, and it should not be attacked. Table 5 was recounted cell by
cell for this note: 35 findings + 10 pass + 10 N/A = 55, and the BOTH cells total exactly 12,
reproducing both headline splits. The evidence discipline (behavioral B vs source/type S; MUST-backed
vs SHOULD-backed vs framework-derived) is better than most of the adjacent literature and should be
credited rather than contested.

The real weakness is that **enforcement is recorded as a binary-plus-partial property of an SDK, with
no notion of what kind of bound an enforcement mechanism is.** The Responsibility IR's whole
enforcement vocabulary is `sdk_enforcement: absent` / enforced / "partial" ("mechanism exists in the
SDK but its enforcement is incomplete"). Every control the paper certifies as enforced is a check
performed by the same SDK through which the adversary's content already flows. The paper's single
positive result — ANP's DID identity verification — is a cryptographic bind on an *identity claim*,
and the paper itself then reports that this bind constrains nothing about what the agent may do.
AgentThread has no way to say that, because it has no scale on which a cryptographic bound, an
operating-system bound, and an in-process application check are different kinds of thing. This is
precisely the gap the two-column tier rule fills, and it is visible *inside their own results*.

Three secondary weaknesses, in order of usefulness:

- **A live internal inconsistency.** Table 3 reports ACP-Cap Protocol IR = 12; section 6.1 reports
  ACP-Cap clause/transition/property counts as 8/7/6. The other four protocols' Table 3 numbers match
  their section 6.1 clause counts exactly (37, 17, 16, 15). Use sparingly and only as a footnote —
  it is a typo-class defect, not a substantive one, and leading with it looks petty.
- **Extraction fidelity is validated structurally, not semantically.** Clause extraction and IR
  construction are machine-assisted and gated only on source-span presence and enum well-formedness.
  There is no second coder, no inter-rater agreement statistic, and no reported extraction error
  rate. A paper whose subject is what happens when model output is trusted uses model output as its
  front end and validates it by type-checking.
- **The findings are counted against a denominator the authors built.** The 11 layer-derived checks
  are the framework's own construct, conceded in Threats to Validity: they "may not always correspond
  to explicit design goals of every protocol." Only 12 of 35 findings carry implementation evidence,
  and TLC runs at an operation bound of 12 with three-principal constants. The counterexamples are
  existence proofs about a hand-built abstraction, which the authors concede: results "should not be
  read as prevalence estimates or proofs for unbounded systems."

## 5. What it forecloses

Five claims that can no longer be made, and one vocabulary hazard.

1. **"Nobody has formally modeled agent-protocol composition."** Dead. TLA+ invariants, TLC
   counterexamples, per-pair bridge capability contracts, eight composed models, 43 obligations,
   30 counterexamples, replayed against production SDKs.
2. **"Nobody has done ownership or responsibility allocation for agent-protocol controls."** Dead.
   The Responsibility IR does exactly this, is explicitly positioned against NIST OSCAL, and yields
   a five-way gap taxonomy.
3. **"Specifications delegate enforcement to applications and nobody has noticed."** Dead, and
   published in the abstract: "only one protocol enforces a security-relevant control in practice
   and no protocol assigns enforcement for cross-protocol behavior." This sits uncomfortably close to
   the present work's "eleven of fifteen bound actions only at an application chokepoint." The two
   findings are about different corpora (five protocol specs and their SDKs vs fifteen systems) and
   different questions (is the control enforced anywhere vs at what tier is the action bounded), and
   the paper must make that separation explicit rather than assume a reader will infer it.
4. **The motivating attack chain is now standard.** Untrusted fetch enters model context, steers a
   local file read, egresses through a network-capable server. It is theirs from Snyk Labs, drawn as
   a figure, and carried through the whole paper. It cannot be presented as a novel framing device.
5. **"Composition failures are unowned."** Theirs, stated as a headline conclusion, with the phrase
   *composition-orphan* as a coined gap type.

**Vocabulary hazard — act on this.** AgentThread's gap taxonomy already contains **split-duty** and
**enforcement gap**. The present work's finding that enforceability is "split" on 50 of 50 codings
means something different — a monitorable safety surrogate enforced beneath a non-monitorable
advertised objective — but a reviewer who has read AgentThread will read the word "split" as
theirs. Either define the term at first use with an explicit contrast to their split-duty, or rename
it. The same caution applies to any use of "composition failure": their composition is between two
*protocols*; the present work's failing 20 of 105 pairs are compositions of two *adversary
placements* (A2 x A4). Same word, different objects.

## 6. What it leaves open

Everything the present work's three instruments are actually made of.

**The acceptance/action separation.** AgentThread's L3 (identity/capability binding) and L4 (semantic
operation control) sit adjacent to the two columns, but the paper never separates *at what tier a
claim is verified* from *at what tier an action is bounded*, and never scores the two independently.
Its unit of analysis is a protocol-check cell, not a system with two columns and a weakest link in
each. The consequence is that the authors observe the phenomenon and cannot state it: their one
enforced control is an acceptance-tier cryptographic bind whose action-side consequence they report
as null, in the sentence "even DID-based identity verification provides no mechanism to bound content
integrity or delegation scope." That is the authorization-execution gap, witnessed by an independent
group, in their own data, unnamed. It is the strongest single piece of external corroboration
available and should be quoted.

**Enforcement tiering.** No T1/T2/T3 analog exists. Cryptographic bounds, operating-system bounds,
and in-process application chokepoints are all "the SDK enforces it or does not." Nothing in the
paper distinguishes a bound that holds against a compromised runtime from one that does not.

**Effectors.** AgentThread never enumerates what an agent can do. There is no effector taxonomy and
therefore no mediation-coverage grid. File write appears only inside the ACP-Client fail-secure
finding; network egress appears only as narrative in the motivating figure and is never scored;
**subprocess spawn, descendant processes, package install, VCS push, credential use, and sub-agent
spawn do not appear at all.** Descendant-process spawn is the specific mechanism by which an
in-process chokepoint is escaped, and its total absence from a paper about protocol-mediated
authority is the clearest indication that the mediation-coverage instrument is unoccupied ground.

**Adversary placement as an axis.** See section 3. Placement is a fixed assumption in AgentThread,
never a variable, never scored, never composed. The five-placement axis, its primary/secondary
scoring, and the composition-failure result over placement pairs have no counterpart.

**Corpus.** Five protocol specifications and their SDKs. Not deployed agent systems, not defenses
from the research literature. There is no corpus overlap with a fifteen-system adjudication, so the
two studies are complements, not competitors — and saying so plainly is the strongest available
framing.

**Enforceability of the objective.** AgentThread checks conformance of an implementation to a
specification. It never asks whether the advertised security objective is monitorable at all. The
question of a monitorable surrogate standing in for a non-monitorable advertised objective is not
posed.

## 7. Suggested related-work paragraph (third person, US English)

> The closest formal treatment is AgentThread [Zheng et al. 2026], which compiles normative clauses
> from five agent protocol specifications into TLA+ invariants, model-checks them with TLC, and
> replays counterexamples against production SDKs through per-protocol adapters — 35
> specification-level findings, 80 implementation tests, and 30 further failures that appear only
> across eight composed protocol pairs. Its Responsibility IR reaches a conclusion this work
> corroborates from a different direction: exactly one security-relevant control across those
> protocols is both owned and enforced, and no protocol assigns enforcement for cross-protocol
> behavior. That work and this one differ in unit and in axis. AgentThread adjudicates protocol
> specifications against their SDKs under a protocol-level Dolev-Yao adversary, with transport
> security taken as an assumed substrate and the layer stack beginning at message integrity; this
> work adjudicates deployed systems and published defenses, separates the tier at which a claim is
> verified from the tier at which an action is bounded, derives mediation coverage over seven
> concrete effectors, and treats the adversary's placement — including placements beneath the
> harness that a protocol-layer model assumes away — as a scored variable rather than a fixed
> assumption. AgentThread's own strongest positive result, that DID-based identity verification
> "provides no mechanism to bound content integrity or delegation scope," is the
> authorization-execution gap observed at the protocol layer and left unnamed.
