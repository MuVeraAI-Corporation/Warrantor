I could not file this programmatically — the Support API requires a paid support plan, and upgrading costs money. The portal path is free on every plan, including Developer. This document is the case, ready to paste.

Why item 3 matters more than it looks

newly foundone numberunlocks the whole catalog

Low-priority GPU is gated by a single aggregate, not per family

What the API actually returns Each VM family appears twice in the Machine Learning quota list, distinguished by the type field rather than by the name. For the A100:
type: .../vmFamily/dedicatedCores/usages     limit: 0
type: .../vmFamily/lowPriorityCores/usages   limit: -1
Reading the −1 −1 is Azure’s convention for “not enforced”. Every GPU family returns −1 on its low-priority row. The binding constraint is the single subscription-level aggregate, TotalLowPriorityCores, which is 0. So one number gates spot across A100, H100, H200, MI300 and everything else — and raising that one number unlocks them all.
Why this is the high-value ask under the no-overage rule. Azure spot typically runs far below pay-as-you-go, so the same $5,000 credit stretches substantially further on low-priority capacity. Research batch jobs are the ideal spot workload — they are interruptible by nature, checkpoint cheaply, and carry no uptime obligation. Nothing in this program needs a persistent endpoint. Verify the current rate in the Azure pricing calculator before planning spend; the discount varies by region and family.
What I have not proven. I read the quota rows; I did not deploy a spot cluster. The “−1 means unenforced” reading is the standard one and is consistent with the aggregate being the only nonzero gate, but it is inference from the API rather than an observed successful deployment. If the aggregate is granted and a spot A100 still refuses to schedule, the per-family row is the next thing to check.

The raw-VM lane is a different ticket, and you do not need it. Microsoft.Compute carries its own separate GPU family quotas, also all at 0. That lane is only for plain IaaS VMs. Azure ML managed compute is the lane these experiments would use, so requesting Compute-VM quota would be the wrong ticket — it would be granted and still not let an AML cluster start.
Azure OpenAI is unrelated. It has its own per-model quota and a separate access approval. Nothing in this program calls it — the work runs open-weight models on our own compute.

It is not a credential — you cannot authenticate with it — but it identifies the tenant, so it does not belong in published text. Read it straight off the portal blade you will already be on, or run az account show --query id -o tsv.
4
Quota type: Machine Learning Service: Virtual Machine Quota
Not Compute-VM (cores-vCPUs). That is the raw-VM path. It would be granted and still leave AML managed compute unable to start — and the failure would look like a capacity problem rather than a wrong-ticket problem.
5
Region: East US. Request all three rows from the table above.

What happened when I tried to automate it

StepResult
Register Microsoft.MachineLearningServices worked quota rows went from 0 to 127
Request A100 via the Quota API failed accepted as InProgress, then “Request failed.” with no reason given
File a ticket via the Support API failed InvalidSupportPlan — writes need a paid plan
The Support API returned HTTP 202 Accepted, and no ticket was ever created. The truth was only in the Azure-AsyncOperation status endpoint. A 202 is a receipt, not a result. This is the same pattern that has cost this program time before — a check that reports on the transport rather than on the outcome it is meant to guarantee — turning up in a new place.

A correction to the earlier record

An earlier note recorded that Azure AI Foundry showed 8× A100-80GB, 8× H100-80GB and 8× MI300-192GB all free in westus3. The API does not agree. With the provider registered, every modern GPU family reads 0 in both eastus and westus3. Only standardNCFamily and standardNVFamily are nonzero, at 6 cores each, and those are legacy K80- and M60-class hardware.

The $5,000 credit cannot buy GPU today. That is now measured rather than assumed — and registering the provider is what made it measurable, so the failed automation attempt still paid for itself.

Perspective on urgency

Nothing is blocked on this. The margin-shrinkage experiment ran on Modal for about $0.70, and every remaining cheap idea is a re-analysis of data already on disk. Azure matters only for the scale-dependent work — the benchmark and the scaling-laws study — which is exactly where the $100 Modal ceiling was the real constraint.

If the request stalls, ask for less. A single A100 — 24 cores — runs everything currently designed. The 48/40 above buys parallelism, not capability, and a smaller request is likelier to clear quickly. If you trim anything, keep item 3: the low-priority aggregate is the one that changes what the credit can afford.
