Executive Summary

The NVIDIA H100 (Hopper)[1] and the forthcoming N1 are the first broadly available GPUs with hardware-enforced confidential computing, enabling inference and training workloads where the model weights, the prompts, and the outputs are cryptographically protected from the host, the hypervisor, and the cloud operator. This is a structural change in the trust model of AI infrastructure — but the operational reality is poorly documented, and most teams that attempt confidential inference stall on attestation-domain setup, multi-tenant composition, or key-release orchestration. This whitepaper is the deployment guide built on the AumOS C1 components (Paper 5, Paper 7), the NVIDIA Attestation SDK, and the Intel+NVIDIA seamless composite-attestation work[2].

§1. The practitioner problem

Confidential computing on a CPU TEE (Intel TDX, AMD SEV-SNP) is a solved operational problem. Confidential computing on an H100 is not, for three reasons: (1) the attestation model is NVIDIA-specific and runs through NVIDIA's root of trust; (2) multi-tenant composition without cross-tenant leakage requires careful attestation-domain design (Paper 7); (3) the performance overhead is real and must be tuned — Chrapek et al.[3] pinpoint PCIe encryption as the dominant bottleneck. Teams need a documented path through all three.

§2. Architecture: the attestation domain

The foundational concept is the attestation domain (Paper 7): a set of GPUs, model keys, and a verification policy over which a consistent trust decision is made. AumOS C1-1 binds to NVIDIA NVTrust; C1-2 retrieves/verifies attestation reports; C1-3 orchestrates the attested pipeline in-TEE; C1-4 terminates TLS in the enclave; C1-5 composes the streams and gates model-key release. The five compose; none is sufficient alone.

§3. The attestation handshake

  • Provisioning. Model owner encrypts weights to a policy only a compliant GPU satisfies.
  • Request. Tenant requests inference; serving node brings up the H100 in CC mode and obtains an attestation report.
  • Verification. C1-2 verifies the report against the policy (firmware floor, CC mode, debug off, measurements).
  • Key release. On success, C1-5 releases the key to the GPU's protected memory; never through host RAM.
  • Inference. C1-4 terminates TLS in the enclave; prompt traverses host only as ciphertext.
  • Teardown. Confidential memory scrubbed; keys never persisted to host disk.

§4. Multi-tenant composition

The naive anti-pattern — one GPU per tenant — is economically fatal. The AumOS pattern is attestation-domain partitioning (Paper 7): tenants sharing a physical GPU are isolated by distinct policies and distinct key-release gates, so a key released for tenant A's model cannot be consumed by tenant B's context, and a context switch requires a fresh attestation. C1-5 enforces this by binding each key release to both the attestation and the tenant's identity (I1).

§5. Deployment sequence

  1. Establish the attestation service. Deploy NVIDIA attestation + C1-1; register the fleet; verify one GPU end-to-end.
  2. Encrypt & register the first model. Encrypt weights to a policy; verify the key-release path.
  3. Deploy the in-enclave serving path. C1-3/C1-4 + TLS-terminating inference server; verify prompt ciphertext-only on host.
  4. Define attestation domains. Partition the fleet by tenant/sensitivity; configure C1-5 per domain.
  5. Tune for throughput. Profile confidential vs. baseline; tune batch size, key-caching, attestation cadence.
  6. Operationalize. Wire attestation failures to alerting; define the runbook for failed-attestation events.

§6. What this delivers, measurably

(a) A verified attestation report for every confidential inference, loggable for audit; (b) zero host-disk plaintext for weights or prompts, verifiable by inspection; (c) a documented and tuned throughput overhead (target ≤10–15% vs. non-confidential baseline[3]); (d) multi-tenant isolation that is policy-enforced, not merely topology-assumed.
