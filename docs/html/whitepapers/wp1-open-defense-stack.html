Executive Summary

The dominant model for securing AI today is point-product accumulation — an LLM firewall here, a prompt-injection detector there, an SBOM generator elsewhere — assembled into a brittle, vendor-locked perimeter that breaks the moment an agent changes framework, runtime, or cloud. This whitepaper presents AumOS as the reference open defense stack for AI: a single, coherent, vendor-neutral architecture that composes 49 components and 12 protocols across four runtimes (Rust, Go, Python, TypeScript) into a deployable platform covering the full agent-security lifecycle — identity, delegation, attestation, action evidence, supply-chain integrity, incident response, and evaluation. We argue that the open-stack pattern (Linux for operating systems, Kubernetes for container orchestration, OpenTelemetry for observability, SPIFFE for workload identity) is the only structurally viable answer to AI security, and that AumOS occupies that position for the agentic layer.

§1. The practitioner problem

Security architects evaluating AI today face four structural failures of the point-product model. (1) Coverage gaps: no single commercial product spans identity, attestation, and supply chain, so the gaps between products become the attack surface. (2) Lock-in: proprietary agent-identity and model-signing schemes mean that a commitment to one vendor forecloses every other. (3) No composability: products do not interoperate, so evidence from one cannot be consumed by another. (4) No reference implementation: there is no neutral baseline against which commercial claims can be benchmarked, so buyers cannot tell marketing from substance. The open defense stack exists to correct all four.

§2. Architecture: seven pillars and the protocol spine

AumOS organizes its 49 components into seven pillars that map one-to-one onto the security lifecycle, connected by a protocol spine of 12 cross-cutting protocols. Each pillar is independently deployable (a team can adopt supply-chain integrity without adopting confidential computing), but the pillars compose through shared protocols so that adopting more yields more than the sum of the parts.

  • Pillar T — Trust & authority core (T1 trust-core, T2 authority-spec): the cryptographic primitives and the AAE canonicalization that every other pillar depends on.
  • Pillar I — Identity (I1 agent-identity, I2 federation): the SPIFFE-derived agent-identity document, trust-domain model, and cross-organization federation (WP3).
  • Pillar C — Confidential computing (C1-1…C1-5): TEE attestation binding to NVIDIA NVTrust, end-to-end attested inference pipelines (Papers 5, 7).
  • Pillar S — Supply chain (S1…S9): signed model provenance, Merkle-lineage ledgers, CycloneDX-ML-BOM, OpenSSF Model Signing interop (Papers 9–12).
  • Pillar R — Response & runtime (R1…R8): the kill switch (R3, Paper 14), canaries, egress control (Paper 15), sandboxing.
  • Pillar A — Auditing & assurance (A1…A8): bias auditing (Paper 19), red-team harnesses, the Open Harness (Paper 17/23).
  • Pillar E/V — Evaluation & vectors (E1, V2, V3): conformance-vector suites proving cross-runtime correctness (Papers 2, 18).

The 12 protocols (P1 delegation, P2 action receipt, P3 attestation handshake, P4 model signing, P5 lineage, P6 kill switch, P7 federation, P8 audit export, P9 harness, P10 BOM, P11 trust manifest, P12 red-team report) are the contract layer: a component in any pillar speaking a protocol can interoperate with any other component speaking it, regardless of runtime.

§3. Methodology: open-core with a conformance gate

The stack is delivered open-core under a permissive license, with a conformance program that is the structural answer to lock-in. Any implementation — AumOS's reference or a commercial fork — may claim conformance to a protocol only after passing the published conformance-vector suite (Paper 18) for that protocol in all four runtimes. The conformance gate is itself open: the vectors, the harness, and the CI pipeline are all in the repository. This means a buyer can verify a vendor's "AumOS-compatible" claim by running the same gate the vendor ran. It is the same structural mechanism that made Kubernetes' CNCF conformance program the credible neutrality guarantee for container orchestration. The NIST AI RMF[1] provides the governance frame the lifecycle maps onto; the OWASP LLM Top 10[2] the threat taxonomy; CoSAI[3] the vendor-neutral venue; Google SAIF the defense-in-depth reference.

§4. Deployment sequence (operator runbook)

  1. Establish the trust root. Deploy T1/T2 and bootstrap the agent-identity CA (I1). Issue the first trust-domain's signing keys inside an HSM or TEE. This is the foundation; nothing else verifies without it.
  2. Stand up the supply-chain gate. Deploy S2/S4 and wire the model registry to require signed provenance + ML-BOM on every artifact (Papers 9, 11). Block unsigned models at admission. Fastest path to measurable risk reduction.
  3. Add attestation for the inference path. Deploy C1-1/C1-3 and the attestation service; require a valid attestation document before model keys are released (C1-5, Paper 5). This is where confidential computing begins to pay back its complexity.
  4. Turn on action evidence. Deploy the flight-recorder (P2) and wire every authorized agent action to emit an AAR (Paper 3). Anchor the receipt chain periodically. This is what makes the system auditable.
  5. Wire the kill switch and canaries. Deploy R3 (Paper 14) and the canary harness; define the escalation policy and exercise it quarterly. This is the containment backstop.
  6. Plug in evaluation. Deploy the Open Harness (X3, Paper 17) and run the red-team corpus in CI. This is what keeps the stack honest as models and agents evolve.

§5. Evidence & validation

What the stack proves, operationally:
  • Cross-runtime byte-identical canonical signing (Paper 2) — the structural fix to the C1 canonicalization defect.
  • Sub-5 ms p99 delegation verification latency across 10,000 synthetic scenarios (Paper 1).
  • End-to-end attested inference with ~11–18% throughput overhead, benchmarked on H100 (Paper 5).
  • Tamper-evident action-receipt chains a regulator can verify without trusting the operator (Paper 3).
  • EU AI Act Article 55 obligation-to-component traceability matrix (WP2).

§6. How this differs from the academic papers

Papers 5 and 7 establish the science of attested pipelines and confidential GPU composition. This whitepaper is the engineering: the operator runbook, the deployment sequence, the conformance program, the support model, and the commercial framing that turns the science into something a platform team can adopt. It is the artifact a CTO hands to a platform-engineering director to justify the build-versus-buy decision.
