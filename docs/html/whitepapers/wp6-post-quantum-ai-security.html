Executive Summary

With NIST's finalization of the first post-quantum cryptography standards in August 2024 — FIPS 203 (ML-KEM)[1], FIPS 204 (ML-DSA)[2], and FIPS 205 (SLH-DSA)[3] — the migration of production cryptographic infrastructure from classical to quantum-resistant algorithms is no longer hypothetical. AI-agent infrastructure is a particularly acute migration target: the delegation envelopes, action receipts, and model signatures may need to remain verifiable for decades, and "harvest-now-decrypt-later" attacks mean secrets encrypted under classical schemes are already at risk. This whitepaper presents the migration sequence for AI-agent cryptographic infrastructure, the hybrid (classical+PQC) transition (RFC 9954[4]), the performance impact, and the cryptographic-agility design that makes the migration survivable, following the CISA/NIST/NSA Quantum-Readiness Roadmap[5].

§1. The practitioner problem

Security architects are told "migrate to PQC" with little guidance on sequencing for a system as cryptographically diverse as an AI-agent platform. An agent platform uses asymmetric cryptography for at least four purposes — agent identity (SVIDs), delegation envelopes (AAE signing), action-receipt integrity, and model signing — each with different freshness, longevity, and interoperability constraints. Migrating them all at once is infeasible; migrating them in the wrong order creates windows of exposure. The architect needs a principled sequence, a hybrid-bridge design, and a cryptographic-agility substrate.

§2. The migration sequence (in dependency order)

The sequence is driven by the longevity of the artifacts each cryptographic use protects. Artifacts that must remain verifiable for the longest migrate first.

  • Phase 1 — Model signing (longest-lived). A model signed today may be verified a decade hence. Migrate S-pillar model signing (P4) to ML-DSA[2] first, hybrid classical+ML-DSA during transition.
  • Phase 2 — Action-receipt & lineage signatures. Must remain verifiable for the audit-retention period (7+ years). Migrate P2/P5 next, hybrid.
  • Phase 3 — Delegation envelope (AAE). Short-lived but highest-volume; migrate AAE (P1/T2) to ML-DSA.
  • Phase 4 — Key establishment (identity, TLS). Migrate key-establishment (I1 SVIDs, in-enclave TLS of C1-4) to ML-KEM[1], completing the migration.

§3. The hybrid bridge

Each phase runs a hybrid classical+PQC transition: every signed artifact carries both a classical signature (Ed25519/ECDSA) and a PQC signature (ML-DSA), and a verifier accepts if either (or, for high-assurance, both) verifies. RFC 9954[4] (Hybrid Key Exchange in TLS 1.3) defines the pattern: security holds if at least one component remains secure. The hybrid bridge is the structurally correct response to the dual uncertainty of classical-vulnerable-to-quantum and PQC-vulnerable-to-future-cryptanalysis.

§4. Performance: the budget that shapes the sequence

ML-DSA signatures are larger (~2.7 KB at security level 2) and signing/verification slower than Ed25519, which matters most for the high-frequency AAE and receipt paths — hence their placement mid-sequence. ML-KEM key encapsulation is competitive with ECDH in compute but larger in wire size, affecting TLS most. The whitepaper provides measured overhead numbers so the architect can budget rather than guess.

§5. Cryptographic agility as the substrate

The migration is survivable only if the cryptographic layer was designed for agility. Warrantor T1 (trust-core) is: primitives are behind a trait/interface with an algorithm identifier in every artifact, so adding ML-DSA or a future scheme is a new implementation, not a fork. Platforms built without agility face a traumatic migration rather than a routine one — and the NIST PQC migration is, for such platforms, the first of several.

§6. Deployment sequence

  1. Audit the cryptographic surface. Inventory every asymmetric use; classify by longevity and frequency.
  2. Deploy ML-DSA signing in T1. Add as an available algorithm behind the agility interface; not yet enabled in production.
  3. Enable hybrid for model artifacts (Phase 1). Dual signatures; verify both in the gate; alert on either failing. Run a full release cycle.
  4. Roll forward Phases 2–4. Hybrid for receipts/lineage, then AAE, then key establishment, each behind a release cycle of dual verification.
  5. Establish the rotation policy. Define deprecation conditions and rotation cadence; make rotation a tested quarterly capability.
  6. Plan classical deprecation. Once PQC verification is universal, schedule the classical-signature removal.

§7. What this delivers

(a) Every long-lived artifact carries a quantum-resistant signature within the migration window; (b) measured overhead per phase, published so the migration is budgeted not guessed; (c) a cryptographic-agility substrate that makes the next algorithm rotation routine; (d) a hybrid-bridge design (RFC 9954[4]) that closes neither the classical nor the PQC trust window prematurely.
