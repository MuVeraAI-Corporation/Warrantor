Executive Summary

Workload identity solved the service-to-service authentication problem; agent identity is the same problem one layer up, materially harder, and currently unsolved by any standardized mechanism. This whitepaper, for platform engineers already operating SPIFFE/SPIRE[1], traces the precise evolution from workload identity to autonomous-agent identity: what carries over unchanged, what must be generalized, and how AumOS I1 reuses SPIRE's trust-domain and SVID concepts while extending them to bind a delegation, a host attestation, and a capability scope into a single verifiable agent identity. We present the federation model for cross-organization agent identity and an operational deployment guide for the agent-identity control plane, grounded in NIST SP 800-207 Zero Trust Architecture[2].

§1. The practitioner problem

A platform team that has standardized on SPIRE issues X.509-SVIDs to every workload and has clean, mTLS-everywhere, zero-trust service mesh. Then an LLM agent arrives. The agent is not a workload in the SPIRE sense — it has no fixed pod, it acts on behalf of a human principal, its permissions vary per delegation, and it calls APIs in other trust domains. Issuing it a workload SVID conflates the agent's identity with the principal's authority and breaks the zero-trust model the team spent years building. The team needs an identity primitive that is to agents what SVIDs are to workloads: standardized, federation-ready, and bound to the authority it acts under.

§2. What carries over from SPIFFE

The SPIFFE specification (SPIFFE IDs, trust domains, SVIDs, the workload API, federation) is the right foundation, and AumOS I1 inherits it deliberately. The trust domain remains the unit of administrative authority; the SVID remains the carrier of identity; the workload API pattern remains the secret-distribution mechanism. A team that understands SPIRE understands 80% of AumOS I1. The remaining 20% is the generalization.

§3. What must be generalized

Three properties distinguish an agent identity from a workload identity, and each requires an extension. (1) Delegation binding: an agent's authority is dynamic (delegated per-task by a human principal), so the SVID must carry the AAE (Paper 1) that authorized it. (2) Host-attestation binding: the SVID must bind an attestation document (C1) so a relying party can require a confidential host. (3) Capability scope: a first-class field of the identity document, verified by the intersection contract (Paper 4).

§4. Federation across organizations

Workload federation (SPIFFE Federation) lets trust domain A verify workloads from B by trusting B's bundle. Agent federation adds the wrinkle: A must verify not only the agent's identity but the principal who delegated, and that the delegation is still valid. AumOS P7 extends SPIFFE federation with a delegation-bundle and revocation-distribution mechanism, so a relying party in A verifies the full chain — agent identity, principal identity, delegation validity, host attestation — without out-of-band coordination.

§5. Deployment sequence

  1. Extend the trust domain. Register AumOS I1's agent-identity CA as an issuer within the existing trust domain, or stand up a dedicated agent trust domain federated with the workload domain. Reuse existing SPIRE bundle distribution.
  2. Deploy the agent workload API. The agent-runtime retrieves its SVID+AAE via the same workload-API pattern SPIRE uses; the secret never touches disk in plaintext.
  3. Wire the delegation issuer. The principal's IdP issues AAEs that the agent-identity CA binds into the SVID — the human-in-the-loop step that authorizes the agent.
  4. Configure relying-party verification. API gateways and mesh sidecars verify the SVID (existing SPIRE logic) and the AAE extension (new logic) before honoring an agent request.
  5. Stand up revocation distribution. Deploy the revocation-bundle distribution so a revoked delegation propagates within the freshness window (target: seconds).
  6. Federate with partners. Exchange trust bundles per P7; agents acting cross-organization now verify end-to-end.

§6. The migration proof

An existing SPIRE deployment can adopt AumOS I1 without forklifting the workload-identity layer. The agent SVID is a SPIFFE SVID with a well-defined extension; SPIRE-verified workloads continue to verify; only the agents and their relying parties adopt the new logic. This is the same incremental-adoption property that made SPIRE itself deployable.
