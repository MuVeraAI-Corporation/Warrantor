Introduction

This is the canonical reference for the AumOS component catalog. Every component has shipped real v1.0 code in this repository; every API surface, type signature, and usage snippet below is extracted directly from the source — rust/<crate>/src/lib.rs, python/<pkg>/src/<pkg>/__init__.py, go/<module>/<file>.go, and typescript/<pkg>/src/index.ts. Nothing here is invented.

The catalog reconciles four source portfolios (DefStack 36-component plan, AumSecure V2/V3 portfolios, PROJECT SENTINEL's 10 frameworks) into 49 implementable components distributed across four languages following the polyglot stack pressure test: Rust owns every security invariant (sign / verify / enforce), Python owns agents, evals, and research outside the trust boundary, TypeScript owns developer surfaces (console, MCP gateway, arena), and Go is phase-gated for Kubernetes control plane (identity, inference fleet ops, sovereign bundles).

How to read each component

Every component has both a card (in its group's grid) and a detail section. Cards are the 30-second summary; detail sections are the maximum-depth reference: overview, real public APIs, usage examples, the problem/attack/compliance obligation it satisfies, dependencies, what is mock vs real, and cross-references to the protocols and other components it touches.

Overview

aumos-trust-core is the single authoritative implementation of every security invariant in AumOS. Per the polyglot stack pressure-test kill criterion, no security invariant may have two authoritative implementations. The crate is compiled with #![forbid(unsafe_code)] and #![deny(missing_docs)] — there is no unsafe anywhere in the trusted core, and every public item is documented. It owns four primitives: canonical CBOR encoding (deterministic, RFC 8949 §4.2.2), SHA-256 binary Merkle trees (RFC 6962 ordering), Ed25519 signing (with key zeroization on drop), and Ed25519 verification (constant-time in the secret material, fails closed on any error).

Key APIs

pub mod canonical;       // canonical_cbor::<T: Serialize>(&T) -> Result<Vec<u8>>
pub mod merkle;          // leaf_hash, node_hash, merkle_root(leaves: &[&[u8]]) -> [u8;32]
pub mod signing;         // SigningKeyWrapper (Zeroize on Drop), sign(payload)
pub mod verification;    // verify::<T: Serialize>(payload, sig, vk) -> Result<()>
pub const VERSION: &str;
pub fn version() -> &'static str;

Usage

use aumos_trust_core::{signing::SigningKeyWrapper, verification};

let signer = SigningKeyWrapper::generate();
let payload = ("agent_action", "issue_credential");
let signature = signer.sign(&payload).expect("canonical+sign");
verification::verify(&payload, &signature, &signer.verifying_key())
    .expect("verifies cross-language via canonical CBOR");

Benefits

The kill criterion that motivated this crate: "More than one language contains authoritative allow/deny logic → stop and consolidate." By centralizing every cryptographic operation in one Rust crate consumed (via PyO3 / napi-rs / FFI) by Python, TypeScript, and Go, AumOS guarantees that a receipt signed in Rust verifies identically when re-canonicalized in any other language. The golden vectors in testvectors/T1/ lock this cross-language contract; CI fails if any language's re-canonicalization diverges. The crate underpins invariants I-06 (artifact identity is exact), I-07 (evidence precedes commitment), and I-10 (replay is detectable).

Dependencies

Depends on: ed25519-dalek, serde_cbor, sha2, thiserror, zeroize, and the generated aumos-api crate. Depended on by: T2, R2, R3, R4, E1, S1, S2, and (via bindings) every Python and TypeScript component that signs or verifies.

Limitations / Deferred work

KMS/HSM backing for the signing key is task 03 (AWS KMS) and task 04 (GCP, Azure, YubiKey, PKCS#11). Wave-1 generates keys in-process via OsRng. Full RFC 8949 §4.2.2 determinism compliance (length-first then bytewise key sorting) is task 02-mvp-sign-verify.

Cross-references

RFC T-CORE-1; consumed by every crate that needs canonical bytes or a signature; see Category 2 (KMS/HSM) for the production key-backing roadmap.

Overview

aumos-authority-spec is the normative reference validator for the Agent Authority Envelope (AAE, protocol P1) — the signed task-specific delegation that authorizes an agent to act. The schema lives in specs/protocols/P1-aae.{cddl,schema.json}; the wire type is aumos_api::identity::v1::AgentAuthorityEnvelope. The validator performs five fail-closed checks: (1) the Ed25519 signature over the canonical-CBOR encoding verifies against the expected issuer key, (2) the envelope has not expired, (3) the side-effect class is in the caller's allowed set, (4) consequential classes (financial, destructive, physical) carry at least one approval (invariant I-08), and (5) the delegation depth does not exceed the caller's maximum. It deliberately does not check policy (that's R5/R6) or revocation freshness (that's I1's job against the live revocation stream).

Key APIs

pub enum SideEffectClass { Read, Write, Financial, Destructive, Physical }
impl SideEffectClass {
    pub const fn is_consequential(self) -> bool;   // Financial|Destructive|Physical
    pub fn parse(s: &str) -> Result<Self, AaeError>;
    pub const fn as_str(self) -> &'static str;
}

pub struct ValidateOptions<'a> {
    pub issuer_verifying_key: &'a VerifyingKey,
    pub now: Option<u64>,
    pub allowed_side_effect_classes: &'a [SideEffectClass],
    pub max_delegation_depth: u32,
}
impl ValidateOptions<'_> {
    pub fn coding_agent(vk: &VerifyingKey) -> Self;  // Read+Write only, depth 2
}

pub fn validate(
    envelope: &AgentAuthorityEnvelope,
    unsigned_canonical_cbor: &[u8],
    options: &ValidateOptions<'_>,
) -> Result<(), AaeError>;

Usage

use aumos_authority_spec::{validate, ValidateOptions, SideEffectClass};

let opts = ValidateOptions::coding_agent(&issuer_vk);
validate(&envelope, &canonical_cbor, &opts)
    .expect("fail-closed: tampered/expired/unauthorized all reject");

Benefits

This crate is the confused-deputy defense: the AAE must be signed by the issuer the caller trusts, not just any issuer. It enforces invariant I-08 (consequential actions require non-delegable human authority) at the structural layer — a financial AAE without an approval entry fails validation regardless of what policy later decides. The delegation-depth cap prevents runaway delegation chains. Together with I1's revocation stream, this crate closes the spoofing and elevation-of-privilege STRIDE categories.

Dependencies

Depends on: ed25519-dalek, thiserror, serde, aumos-api (the proto wire type). Depended on by: every component that consumes an AAE — I1, R3, R4, X8 mcp-gateway, and all trusted-core consumers.

Limitations / Deferred work

Wave-2 v1.0 uses serde_cbor for the canonical encoding in tests; real callers receive the canonical bytes from T1 trust-core. Revocation freshness is deferred to I1 (the live revocation stream). The CDDL schema itself is authored in specs/protocols/ and is the normative source.

Cross-references

Protocol P1 (AAE); consumed by I1, R3, R4, X8; see protocols.html for the AAE schema.

Overview

agent-identity is the identity and authority layer — the keystone that 12 other components depend on. The Go implementation activates the Go activation gate (trigger #3: SPIRE registration lifecycle). The service issues SPIFFE-style SVIDs (JWT-formatted, 15-minute default TTL) bound to agent attributes (publisher, model, version, rules of engagement, parent SVID), issues short-lived (60s default) capability tokens scoped per AAE, maintains a delegation graph with intersection semantics (invariant I-02: the child's authority is the intersection of every link in the chain, never the union), and revokes identities with a 5-second propagation budget (invariant I-05). The implementation is self-contained in Wave-2 v1.0 — SVIDs and capability tokens are signed with an in-process Ed25519 key; real SPIRE integration is task 03.

svc, _ := identity.NewService("muveraai.com")
svid, _ := svc.Issue("spiffe://muveraai.com/agent/coding-1",
    identity.AgentAttributes{Publisher: "muveraai.com/coding-agent", Model: "claude-opus-4.5"},

Benefits

I1 is the implementation of invariants I-01 (no active identity, no action), I-02 (no authority expansion — the intersect helper rejects any child claim not present in the parent), I-05 (bounded revocation latency — Revoke measures elapsed and returns an error if it exceeds RevocationBudget), and I-10 (replay detection via JTI + timestamps). Every other component that checks an AAE first asks I1 whether the SVID is still valid. The intersection semantics block the canonical confused-deputy escalation where a delegated sub-agent quietly widens its parent's authority.

Dependencies

Depends on: Go stdlib crypto/ed25519, encoding/hex, encoding/json. Depended on by: 12 components — R3 kill-switch, R4 credential-vault, X8 mcp-gateway, N4 tenant-guard, C1-5 confidential-fabric, F1 fed-core, and every component that presents an SVID. SPIRE integration (task 03) will add github.com/spiffe/spire-api-sdk.

Limitations / Deferred work

Wave-2 signs with an in-process Ed25519 key (real SPIRE is task 03). The capability-token issuance path is stubbed (the capJTI is generated but the second JWT signing is deferred). Revocation propagation is single-process; the multi-replica fan-out via CloudEvents is task 04.

Overview

aumos-eval-guard is the cryptographic sandbox boundary attestation. Before an agent starts, R2 runs four pre-flight checks — NetworkIsolation (canary IPs: huggingface.co, pypi.org, 1.1.1.1), FilesystemBoundary, ProcessIsolation, and EgressAttestation (eBPF iptables rules, deny-all default). The crate requires Linux 5.13+ for eBPF; CI runs the non-eBPF checks and gates the eBPF tests.

aumos-flight-recorder is the verifiable agent flight recorder. It emits signed Agent Action Receipts (AAR, protocol P2) for every material agent action. The recorder exports to OCSF (class 6003, API Activity) and OpenTelemetry semantic-attribute JSON.

Overview

fed-core is the attested federated training orchestrator — the most complex component in AumOS. Three roles collaborate: the Aggregator (the coordinator, runs in a TEE) collects model updates from trainers, averages them with FedAvg (weighted by num_examples), runs the verifier over the aggregated delta, then publishes the new global model — it refuses to admit a trainer that does not present a valid TEE attestation bound to the round nonce; the Trainer (one per participant) runs local training (PyTorch, NeMo, JAX — abstracted by the TrainingEngine protocol), then emits a signed update plus its measurement; the Verifier (a small, stateless checker) rejects updates with NaN/Inf, with too-large norms (poisoning / free-rider defence), or whose measurement diverges from the trusted client image. Overview

dp-crate is the production-grade differential privacy toolkit. Three building blocks, all framework-agnostic (operate on flat list[float] gradients so they work equally well with PyTorch, JAX, TensorFlow, or NeMo): the DPSGDOptimizer clips per-example gradients to a fixed L2 bound and adds calibrated Gaussian noise (the two mechanical steps of DPSGD, Abadi et al. 2016); the PrivacyAccountant tracks the privacy budget via Rényi Differential Privacy (Mironov 2017) — the RDP→(ε,δ) conversion uses the standard Balle et al. 2020 bound, and composition is additive in RDP space (the whole point of the moments accountant); and the DPDashboard is a serializable snapshot of the current budget for ops dashboards. Overview

@warrantor/mcp-gateway is the authority-aware Model Context Protocol (MCP) middleware. The gateway sits between an MCP client (an agent) and one or more MCP tool servers. It intercepts every tool call, checks the caller's AAE (P1 Agent Authority Envelope) for the tool's required scope, and either forwards the call to the real tool server or denies it. Three defenses are implemented per RFC X8 / specs/protocols/P1-aae.md: the confused-deputy defense (the AAE's tools list must explicitly contain the requested tool's SPIFFE ID — the gateway can never be tricked into calling a tool the principal did not authorize, even if the agent hands it a crafted tool name); the audience check (the AAE must be issued for this gateway — its resources list must contain the gateway's SPIFFE ID; an AAE minted for a different gateway is rejected); and side-effect-class enforcement (each tool declares the side-effect class it performs — read / write / financial / destructive / physical; the AAE's side_effect_class must cover the tool's declared class; consequential classes additionally require an explicit approval entry per invariant I-08). v1.0 ships the authorization logic + tool registry; forward() is a stub that would in production proxy the call over MCP JSON-RPC.

Overview

sovereign-stack is the air-gapped sovereign deployment bundle manager. AumOS can be deployed fully air-gapped (no cloud dependencies) for sovereignty-sensitive environments. This package produces and validates a SovereignBundle: a self-contained manifest that names every component required for a given deployment mode, plus a checksum over the component set so the bundle's integrity can be verified at import time without any external trust root.
