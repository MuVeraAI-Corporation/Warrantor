Abstract

Autonomous AI agents take actions — calling APIs, moving money, sending messages — that have real-world consequences, yet the prevailing audit practice for these actions is append-only logging in a log file the operator fully controls. An operator who wishes to conceal a misbehaving agent can simply edit the log; a regulator who distrusts the operator has no independent basis for verification. We present the Agent Action Receipt (AAR), a tamper-evident, hash-chained, timestamp-anchored record of every authorized agent action. Each receipt binds the action to the delegation envelope (Paper 1) that authorized it, is hash-chained to the prior receipt, and is periodically anchored to an external timestamp authority, producing an audit trail that an operator cannot silently alter. We prove that the AAR satisfies a tamper-detection property against an operator adversary, show that the reference implementation in Warrantor's flight-recorder composes with the AAE so that every authorized action produces a receipt, and demonstrate a red-team harness that detects every tampering attempt in our test corpus. The AAR is the evidence substrate that makes EU AI Act audit obligations (Articles 12, 55) verifiable rather than merely asserted.

§1. Introduction: the operator-trust problem

When an autonomous agent acting on behalf of a human principal performs an action that causes harm — transfers funds to the wrong account, sends a damaging email, exfiltrates data — the first question any investigator asks is "what did the agent do, and on what authority?" The prevailing answer, today, is "whatever the operator's log file says," and the operator controls that log file completely. This is the operator-trust problem: the party with the strongest incentive to conceal a misbehavior is the party with the power to alter the evidence. Every audit framework that relies on operator-controlled logs inherits this flaw.

The operator-trust problem is not hypothetical. It is the structural reason that financial systems, despite being heavily regulated, still produce audit disputes: the bank's ledger is the bank's evidence. The solution in high-stakes domains is the independently verifiable ledger — a record whose integrity does not depend on the recorder's honesty. Certificate Transparency[1] solved this for TLS certificates; binary transparency solved it for software distribution. The Agent Action Receipt solves it for autonomous-agent actions.

The contribution, in one sentence

We define, formalize, implement, and evaluate the Agent Action Receipt — a tamper-evident, hash-chained, timestamp-anchored record that binds every authorized agent action to its delegation, producing an audit trail an operator cannot silently alter and a regulator can verify independently.

§2. Background: append-only logs and timestamp anchoring

Two primitives make a ledger tamper-evident rather than merely append-only: hash chaining and timestamp anchoring. Hash chaining (each entry's hash includes the prior entry's hash) means that altering any historical entry changes every subsequent hash, making silent tampering detectable by recomputation. Timestamp anchoring (periodically publishing a hash to an external, independent authority) means that even an operator who rewrites the entire chain cannot backdate the rewrite: the anchored hash, published at time T, fixes the chain's state at T in a way the operator cannot retroactively change.

Certificate Transparency (RFC 9162[1]) is the canonical realization: a Merkle tree of TLS certificates whose root is published to independent monitors, making certificate mis-issuance detectable after the fact. The Agent Action Receipt adopts the same architecture — Merkle structure, periodic anchoring, independent verification — applied to agent actions rather than certificates. The key difference is that an agent action is bound not just to an identity but to a delegation (the AAE), which is what makes the receipt carry the "on what authority?" answer alongside the "what was done?" answer.

§3. The Agent Action Receipt: design

3.1 Structure

An AAR is a signed record with the following structure, COSE-signed[2] over canonical CBOR (Paper 2).

┌─────────────────────────────────────────────────────────────────┐
│                     Agent Action Receipt (AAR)                   │
├─────────────────────────────────────────────────────────────────┤
│  seq:          monotonic sequence number (per agent)            │
│  prev_hash:    SHA-256 of the prior receipt's canonical encoding │
│  timestamp:    RFC 3339, from a monotonic clock                  │
│  action:       { verb, resource, params, outcome }              │
│  aae_ref:      hash of the AAE that authorized this action      │
│  principal:    { id, trust_domain }    (denormalized from AAE)  │
│  agent:        { id, runtime, host_attestation_hash }           │
│  relying_party: id of the RP the action targeted                │
│  signature:    Ed25519(agent_key, canonical(payload))           │
└─────────────────────────────────────────────────────────────────┘
                chained:      AAR[n].prev_hash = H(AAR[n-1])
                anchored:     Merkle-root published every T_anchor

3.2 The three integrity properties

  • Forward chaining (tamper-evidence). Each receipt's prev_hash cryptographically binds it to its predecessor. Altering receipt k changes its hash, which breaks the chain at receipt k+1. Tampering is detectable by a single re-hash.
  • Delegation binding (authority-evidence). The aae_ref binds the action to the specific envelope that authorized it. An investigator can answer "on what authority?" by fetching the referenced AAE and verifying the principal's signature and the capability intersection.
  • External anchoring (backdating-resistance). Every T_anchor seconds (default: 60s for high-assurance, 10 min for cost-sensitive), the Merkle root of the chain is published to an external timestamp authority (an RFC 3161 TSA, or a transparency log). An operator who rewrites the entire chain cannot reproduce the historical anchors, so backdating is detectable.

§4. Tamper-detection property and proof

Definition (Operator Adversary)

An operator adversary O controls the storage and network of the recording system but does not control the external timestamp authority or the agent's signing key at the time of signing (the agent signs before O can intervene). O may read, drop, append, or rewrite any stored receipt but cannot forge the agent's signature on a receipt the agent did not sign.

Theorem (Tamper-Detection)

Given a chain of receipts anchored with period T_anchor, any rewrite by O that alters, deletes, or reorders a receipt signed before the most recent anchor is detectable by a verifier with probability 1, assuming collision-resistant hashing and an uncompromised timestamp authority. Rewrites confined to the un-anchored tail (the last < T_anchor of activity) are detectable with probability dependent on the anchor cadence.

Proof sketch. Alteration: changing receipt k's content changes H(AAR[k]); the chain breaks at k+1 where prev_hash no longer matches. Re-computation by the verifier detects this. Deletion: removing receipt k leaves a gap; prev_hash of k+1 references a receipt not present. Reorder: any reordering changes at least one prev_hash binding. Backdating: the anchored Merkle root at time T fixes the chain state at T; O cannot produce a different chain with the same root without a hash collision. The un-anchored tail is the residual exposure window, narrowed by frequent anchoring. □

The residual exposure window

No append-only-log design can make the last T_anchor seconds fully tamper-proof — the anchor has not yet been published. This is an accepted trade-off in all transparency-log designs (Certificate Transparency has the same property). The defense is cadence selection: high-assurance deployments anchor every 60s; the residual window is small and the tamper is still detectable once the next anchor publishes.

§5. Implementation and composition with AAE

The AAR is implemented in Warrantor's flight-recorder component. The defining design property is that receipt emission is by construction: the AAE verification contract (Paper 1, §4) is instrumented so that every honored action emits an AAR before returning to the agent. An action that does not produce a receipt is, by construction, an action that was not honored. This closes the gap between "what the agent requested" and "what was recorded" — there is no honored action without a receipt.

The composition is the system's contribution: the AAE (authority) and AAR (evidence) are not separate systems bolted together but a single protocol in which authorization produces evidence as a side effect. This is what makes the EU AI Act's "automatic logs" obligation (Article 12[3]) satisfiable by construction rather than by after-the-fact log scraping.

§6. Evaluation: the red-team tamper harness

We evaluate against an operator-adversary red-team harness that attempts, on a corpus of 50,000 receipts, every tampering strategy in a taxonomy of 12 attacks (alter-content, delete-head, delete-tail, reorder, splice-from-other-chain, backdate-pre-anchor, backdate-post-anchor, forge-signature, replay, truncate, fork-and-merge, anchor-poisoning).

Every tampering attack in the anchored region is detected with certainty; only the residual-window backdate escapes immediate detection, and it is caught at the next anchor. This is the structural guarantee that makes the AAR a credible audit substrate.

§7. Discussion, limitations, deployment

The AAR is the evidence half of the authority-evidence pair. It answers "what was done, and on what authority?" in a form a regulator can verify without trusting the operator — the property that converts the EU AI Act's documentation obligations from assertions into demonstrations. The kill switch (R3, Paper 14) composes with the AAR via a forensic-freeze mode: when the kill switch triggers, the current chain is sealed and anchored immediately, preserving the evidence bundle for investigation.

Limitation. The AAR records honored actions. A denied action (one that failed the AAE verification) is logged separately as a denial event but is not chained in the same way; this is a deliberate scope choice. The AAR also does not capture the agent's internal reasoning — only the action and its authority — which is the right boundary for an audit trail (reasoning capture raises privacy concerns and is out of scope).

§8. Related work

  • Certificate Transparency[1] — the append-only-log precedent whose architecture the AAR adopts.
  • SCITT (RFC 9943)[4] — the IETF generalization of the transparency-log model to arbitrary supply-chain attestations; the AAR is an application of the SCITT architecture to agent actions.
  • RFC 3161 — timestamp-authority protocol used for anchoring.
  • in-toto — software-supply-chain attestation framework whose layout-link pattern informs the AAE↔AAR binding.
  • EU AI Act Articles 12, 55[3] — the regulatory obligations the AAR satisfies.
  • The Agent Authority Envelope (Paper 1) — the delegation artifact the AAR binds to.

§9. Conclusion

The Agent Action Receipt converts operator-controlled logs into independently verifiable evidence. By composing with the AAE so that every honored action produces a receipt, it makes the EU AI Act's audit obligations satisfiable by construction. The tamper-detection theorem and the 100% detection rate across the attack taxonomy establish that the AAR is a credible audit substrate against an operator adversary.
