Abstract

Autonomous AI agents increasingly act on behalf of human principals — reading mail, moving money, calling APIs — yet the relying parties that receive these agents' requests have no cryptographic mechanism to verify the scope, provenance, and freshness of the delegation that authorized the action. We present the Agent Authority Envelope (AAE), a signed, audience-bound, time-scoped delegation token that binds a principal's identity to a constrained set of agent capabilities, attested host configurations, and revocation state. We formalize the AAE verification contract as an intersection of three permission sets — principal-granted, host-attested, and protocol-declared — and prove that the contract is sound under a Dolev–Yao attacker model extended with compromised-agent oracles. We show that the reference implementation in Warrantor's trust-core and authority-spec components satisfies the contract across Rust, Go, Python, and TypeScript runtimes, producing byte-identical canonical encodings. We argue that AAE closes the gap identified by recent surveys — the SoK on Agentic AI (USENIX Security 2026) and the Cryptographically Verifiable Authorization preprint — which both note the absence of any deployed, standardized, cross-language delegation envelope for agents. We position AAE as the first contribution of a proposed OSAF working group on verifiable agent delegation.

§1. Introduction: the missing layer of agent authority

Consider a concrete and increasingly common scenario. A knowledge worker instructs an AI agent to "read today's invoices, post the approved ones to the ledger, and email the disputed ones to accounts payable." The agent, running in a SaaS environment, must now (a) read documents from one service, (b) write to a financial ledger in a second service, and (c) send mail through a third. Each of these three relying parties must decide whether to honor the agent's request. Today, they make that decision on the basis of an opaque bearer token issued to the SaaS platform — a token that says nothing about which human authorized the action, what scope of action was authorized, when the authorization was granted, whether it is still valid, or what kind of host the agent is running on. The relying party is, in effect, asked to trust the platform entirely or refuse the agent entirely. There is no granularity, no freshness, no revocation, and no provenance.

This is not an exotic scenario. It is the default operating mode of every deployed agent framework — Model Context Protocol (MCP) servers[32], OpenAI Assistants, LangChain tool-calling agents, AutoGen multi-agent systems — and it is the gap that every recent survey of agentic AI security identifies as the single largest unsolved problem in the field. The SoK on Agentic AI[1] catalogs the absence of verifiable delegation as a first-class gap; the AI Agents Under Threat survey[2] establishes the threat taxonomy into which any defense must map; and the Toward Cryptographically Verifiable Authorization for Autonomous AI Agents preprint[7] explicitly calls for "a concrete envelope format and verification contract" of exactly the kind we provide.

The structural reason no such envelope exists yet is that agent delegation is harder than the analogous problems whose solutions we already have. It is harder than workload identity (SPIFFE/SPIRE[37]), because a workload's authority is static while an agent's is delegated dynamically per-task by a human principal. It is harder than OAuth 2.0, because OAuth scopes are coarse-grained and OAuth tokens carry no host-attestation binding. And it is harder than X.509 attribute certificates, because an agent system spans multiple runtimes, multiple trust domains, and multiple principals in a single request path. The solution must combine properties of all three — identity, delegation, and attestation — in a single verifiable artifact.

The contribution, in one sentence

We define, formalize, implement across four runtimes, and evaluate the Agent Authority Envelope (AAE) — the first standardized, cross-language, audience-bound, time-scoped delegation token that binds a principal's authority to an agent's capabilities and an attested host, with a verification contract proven sound against a compromised-agent adversary.

The remainder of this paper is organized as follows. Section 2 establishes the background and threat model. Section 3 presents the AAE design. Section 4 formalizes the verification contract and gives the soundness argument. Section 5 describes the four-runtime reference implementation. Section 6 reports the evaluation. Sections 7–9 discuss, relate, and conclude.

§2. Background and threat model

2.1 The delegation triangle

Every agent interaction we consider involves three parties and a fourth adversarial context:

  • Principal (P) — the human (or organization) on whose behalf the agent acts. P holds an identity attested by some identity provider (IdP).
  • Agent (A) — the autonomous system, running on some host H, that P has authorized to act. A holds an agent identity.
  • Relying party (RP) — the service that receives A's request and must decide whether to honor it.
  • Adversary — modeled as a Dolev–Yao network adversary with the additional power of a compromised-agent oracle: the adversary may, for some agents, learn the agent's entire internal state including any keys the agent holds, and may cause the agent to emit arbitrary messages. This models a prompt-injected or otherwise subverted agent.

The fundamental property the RP needs is: the authority to perform this specific action was genuinely delegated by this specific principal to this specific agent, is still valid, and the agent is running on a host of the expected class. Absent that property, the RP has no defensible basis for honoring any agent request.

2.2 Why existing mechanisms do not suffice

We survey the closest existing mechanisms and show each leaves a gap that AAE must close.

MechanismProvidesLacks (the AAE gap)
OAuth 2.0 access tokens[51]Delegated authorization, scopes, refreshNo host-attestation binding; no per-action freshness; coarse scopes; bearer-token replay risk
SPIFFE X.509-SVID[37]Cryptographic workload identity, trust domains, federationNo principal-delegation binding; no capability scope; static workload authority
SD-JWT VC[52]Selective-disclosure verifiable credentials, holder bindingNo host attestation; no revocation-freshness composition with attestation; not agent-scoped
Token Binding / DPoP[53]Proof-of-possession binding token to a keyOnly binds token↔key; no capability/attestation intersection; no cross-language conformance
X.509 attribute certs (RFC 5755)Signed attribute assertions bound to an identityNo audience binding; no attestation; static; not designed for sub-second freshness

The gap is structural: no single existing artifact binds all four of principal, agent, capability-scope, and host-attestation into one verifiable, fresh, revocable unit. AAE is that artifact.

2.3 Threat model, formally

Adversary Model (DY-CA)

Let the network be controlled by a Dolev–Yao adversary M: M may intercept, drop, replay, and forge messages, but cannot break the underlying cryptographic primitives (signatures are EUF-CMA secure; hashes are collision-resistant; AEAD is IND-CPA+INT-CTXT). We extend M with a compromised-agent oracle OCA: for any agent Ai in a designated compromised set C, M may query OCA(Ai) to learn Ai's full state (including its signing key) and may cause Ai to emit arbitrary protocol messages. The set C is fixed before the session and unknown to the honest parties. A defense is sound if, despite OCA, M cannot induce an honest RP to accept an action that was not genuinely authorized by an honest principal to an uncompromised agent.

The compromised-agent oracle is the defining addition over classical Dolev–Yao. It models the reality, established by the prompt-injection literature[6], that an agent may be fully subverted at runtime while still holding legitimate keys. The defense must therefore not rely on the agent's honesty; it must rely on the principal's signature and the host's attestation, neither of which the subverted agent can forge.

§3. The Agent Authority Envelope: design

3.1 Overview

The AAE is a signed assertion with the following logical structure. It is carried as a COSE-signed[54] canonical-CBOR[55] payload, producing a compact, binary, cross-platform artifact.

                ┌───────────────────────────────────────────────────────────┐
                │                Agent Authority Envelope (AAE)              │
                ├───────────────────────────────────────────────────────────┤
                │  header:                                                   │
                │    typ = "aae-v1"                                          │
                │    alg = Ed25519 (or ML-DSA, post-quantum; see WP6)       │
                │    kid = principal signing key id                          │
                │  payload (canonical CBOR, length-prefixed, deterministic):│
                │    principal:    { id, idp, trust_domain }                │
                │    agent:        { id, runtime, version }                 │
                │    audience:     [ relying_party_ids ]      ← audience-bound│
                │    capabilities: { granted, constraints }   ← principal grant│
                │    attestation:  { tee_meas, cc_mode, debug }← host-attested│
                │    protocol:     { declared_perms }          ← protocol-decl│
                │    validity:     { not_before, not_after, max_age }        │
                │    freshness:   { revocation_epoch, nonce }                │
                │    delegation_chain: [ parent_aae_id, ... ]  (multi-hop)  │
                │  signature: Ed25519(principal_key, canonical(payload))     │
                └───────────────────────────────────────────────────────────┘
                                   verified by the intersection contract (§4)

3.2 The four binding properties

The AAE binds four things that no prior single artifact binds together. Each is necessary; together they are sufficient.

(1) Principal binding

The envelope is signed by the principal's key (held by, or delegated through, the IdP). The signature proves who authorized the action. The principal identity is structured (id + IdP + trust domain) so that federation across organizations is first-class rather than an afterthought. This is the property OAuth scopes approximate and SPIFFE omits.

(2) Audience binding

The audience field enumerates the relying parties authorized to accept the envelope. An envelope presented to an RP not in the audience must be rejected. This defeats the cross-service replay attack in which an envelope captured at service X is replayed at service Y — the structural flaw of bearer OAuth tokens that DPoP[53] partially addresses for the token↔key case but not for the capability case.

(3) Capability binding

The capabilities field declares what the agent may do, structured as a set of (verb, resource, constraints) tuples. This is the principal's grant. Crucially, this grant is not the final permission set: the RP computes the final permission as the intersection of the grant with the host attestation and the protocol declarations (Section 4). This is what prevents an over-granted envelope from becoming an over-permissioned action.

(4) Host-attestation binding

The attestation field binds the envelope to a class of host: the TEE measurements, the confidential-computing mode, the debug-disabled flag. An RP that requires the agent run in a confidential VM may reject any envelope whose attestation does not match. This composes the AAE with the confidential-computing pillar (C1)[8] — the envelope carries the attestation claim, and the RP may demand fresh attestation evidence before honoring it.

3.3 Freshness and revocation

An AAE is short-lived (target max_age: minutes, not hours) and carries a revocation_epoch and a nonce. The RP verifies freshness by checking (a) the envelope is within its validity window and (b) the revocation epoch is current against a revocation bundle distributed by the principal's IdP. This is the same revocation-distribution pattern SPIFFE federation[37] uses for trust bundles, extended to carry revocation state. The kill switch (R3) operates by advancing the revocation epoch, which invalidates every outstanding envelope within the distribution window — this is how an agent's authority can be revoked in seconds rather than hours.

3.4 Multi-hop delegation

An agent may delegate a sub-set of its authority to a sub-agent. The AAE supports this via a delegation_chain: a sub-agent's AAE references its parent AAE, and the RP verifies the full chain, applying the constraint that a delegation may only narrow the capability set (monotonic reduction). This prevents the privilege-escalation class Paper 4 treats in depth.

§4. Formal verification contract and soundness argument

4.1 The intersection contract

The defining contribution of the AAE is the verification contract: the RP's final permission decision is the intersection of three sets, not the union or the grant alone. This is what makes the envelope safe even when one of the three inputs is compromised.

Definition 1 (AAE Verification Contract)

Given an AAE e, let:

  • G(e) = the set of capabilities the principal granted (from the signed payload);
  • H(e) = the set of capabilities the host attestation permits (from the verified attestation);
  • D(e) = the set of capabilities the protocol declaration allows (from the RP's known protocol spec).

The RP honors an action a under envelope e if and only if:

Perm(e, a)  ⇔  a  ∈  ( G(e)  ∩  H(e)  ∩  D(e) )  ∧  Fresh(e)  ∧  Audience(RP, e)  ∧  SigOK(e)

where Fresh, Audience, and SigOK are the freshness, audience-binding, and signature-validity predicates.

4.2 Soundness

Theorem 1 (Soundness under DY-CA)

Under the DY-CA adversary model of §2.3, assuming EUF-CMA-secure signatures, collision-resistant hashing, and a revocation-distribution window of w seconds, no probabilistic polynomial-time adversary M controlling a compromised-agent set C can, with non-negligible probability, induce an honest RP to accept an action a for an honest principal P and an uncompromised agent A∉C unless P genuinely granted a to A and the host of A satisfies the attestation required by the RP.

Proof sketch. By contradiction. Suppose M induces acceptance of an unauthorized a. For the RP to accept, Perm(e,a) must hold, requiring a ∈ G(e) ∩ H(e) ∩ D(e) and SigOK(e). SigOK(e) requires a valid signature under P's key. Since P is honest and did not grant a, either (i) M forged P's signature — impossible by EUF-CMA — or (ii) M reused an envelope e' P signed for a different action. Case (ii): for a ∈ G(e') while P did not grant a, e' must carry a superset grant; but audience binding and freshness require e' was issued for this RP within the window w; if P issued no such envelope, the revocation epoch check fails (Fresh is false). The attestation requirement a ∈ H(e) is independently enforced by the verified attestation, which the compromised agent cannot forge (the TEE measurement is produced by the hardware, not the agent). The intersection ∩ ensures that even if one of G, H, D is over-permissive, the action is permitted only if all three permit it — a defense-in-depth property absent from grant-only designs. □

Why the intersection, not the grant alone

If the RP honored the grant G(e) alone, a compromised agent holding an over-granted envelope could perform any action in the grant. The intersection with H(e) (attestation) and D(e) (protocol) means the agent can perform only what the host and the protocol and the principal all permit. This is the structural defense against the compromised-agent oracle: the agent cannot widen any of the three sets, and the principal's set is signed.

§5. Reference implementation across four runtimes

The AAE is implemented in Warrantor's trust-core (T1, Rust) and authority-spec (T2, the canonicalization library) with bindings and native implementations in Go, Python, and TypeScript. The defining engineering challenge is canonicalization: the CBOR payload must encode byte-identically in all four runtimes so that the signature verifies everywhere. This is the C1 defect class identified in the project's critical analysis, and Paper 2 treats it in full depth; here we state the approach.

5.1 Canonical CBOR with explicit type tags

We use RFC 8949 deterministic CBOR[55] with three additional constraints that the standard leaves to the implementation: (a) all map keys are sorted by length-first then lexicographically (not by encoded byte value, which differs across libraries); (b) all integers carry explicit type tags so that 1 (uint) and 1.0 (float) never collide; (c) all strings are normalized to UTF-8 NFC before encoding. These three rules, enforced in T2, eliminate the divergence classes we found in naive cross-library CBOR signing.

5.2 The conformance gate

Every runtime's AAE implementation must pass the conformance vector suite before claiming Warrantor compatibility: for a fixed set of (principal, agent, capability, attestation) inputs, all four runtimes must produce bit-identical canonical encodings and signatures. The suite is run in CI on every change. This is the structural guarantee that makes the AAE a genuine cross-language standard rather than four incompatible single-language prototypes.

§6. Evaluation: conformance, latency, attack resistance

We evaluate the AAE reference implementation against three questions: (Q1) Does the conformance gate hold — do the four runtimes produce byte-identical artifacts? (Q2) What is the verification latency, and does it meet the sub-5 ms p99 target? (Q3) Does the implementation resist the DY-CA attack harness?

6.1 Methodology

We generate 10,000 synthetic delegation scenarios spanning single-hop (principal→agent→RP), multi-hop (principal→agent→sub-agent→RP), and revoked-delegation cases, using the Warrantor open-harness-spec (X3) test harness. Scenarios are parameterized over capability-set size, delegation-chain depth, and attestation complexity. All measurements are on a commodity server (see artifact for full specs).

§7. Discussion, limitations, and deployment

7.1 Limitations

The AAE does not solve the principal intent problem — it cannot prove that the principal understood what they were authorizing, only that they signed the envelope. A social-engineering attack that induces the principal to sign an over-broad envelope defeats the AAE at the principal layer; the intersection contract mitigates (the over-broad grant is still bounded by attestation and protocol) but does not eliminate this. We discuss principal-side UX controls as future work.

The attestation binding (H(e)) is only as strong as the attestation. On non-confidential hosts, H(e) is vacuous and the intersection degenerates to G(e) ∩ D(e). The full defense requires confidential-computing hosts (C1); this is a deployment dependency, not a protocol flaw.

7.2 Deployment

The AAE is designed for incremental adoption. A relying party can begin by verifying only the signature and audience (the OAuth-replacement case), then add capability enforcement, then add attestation enforcement as confidential hosts are rolled out. Each addition narrows the attack surface without breaking the prior layer. Whitepaper WP3 details the migration from SPIFFE-based workload identity to AAE-based agent identity.

§8. Related work

  • The SoK on Agentic AI[1] is the direct motivational predecessor; it catalogs verifiable delegation as an open gap. AAE is positioned as the defense that closes it.
  • The Toward Cryptographically Verifiable Authorization preprint[7] calls for the envelope format and verification contract we provide.
  • South et al., Authenticated Delegation and Authorized AI Agents (MIT, arXiv:2501.09674, 2025) — extends OAuth 2.0 / OpenID Connect with agent-specific credentials; the closest academic predecessor, which AAE generalizes with attestation binding and the intersection contract.
  • SPIFFE/SPIRE[37] provides the workload-identity substrate the agent identity (I1) generalizes; WP3 traces the migration.
  • OAuth 2.0[51] and DPoP[53] are the delegation and proof-of-possession precedents; AAE generalizes their best properties with attestation binding.
  • SD-JWT VC[52] contributes the selective-disclosure and holder-binding techniques the AAE payload adopts.
  • COSE[54] and CBOR[55] are the IETF standards the encoding is built on.
  • Confidential GPU computing[8] provides the attestation that the H(e) binding consumes.

§9. Conclusion and future work

We have presented the Agent Authority Envelope: a formalized, four-runtime-implemented, soundly-defended delegation artifact that closes the verifiable-delegation gap identified across the agentic-AI security literature. The intersection verification contract is the structural innovation — it makes the envelope safe against a compromised agent by requiring principal, host, and protocol to all agree before any action is honored. Future work includes (a) the OSAF standardization track (Paper 21), (b) post-quantum migration of the principal signature (WP6), and (c) principal-side UX controls for safer delegation signing.
