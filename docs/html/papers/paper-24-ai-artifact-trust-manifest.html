Specification Abstract

A deployed AI system is not just a model: it is a model, a dataset (or dataset manifest), a codebase (inference server, agent runtime, tool definitions), and a configuration. Existing BOM formats — CycloneDX ML-BOM[1], SPDX 3.0[2], the in-toto Attestation Framework[3] — describe each artifact class separately but do not bind them into a single, signed, verifiable trust manifest that a relying party can check before invoking the system. We propose the AI Artifact Trust Manifest (AATM), extending CycloneDX ML-BOM, as an OASIS-track specification that binds model, data, code, and configuration into one signed manifest with a single verification entry point. The AATM composes with the OpenSSF Model Signing lineage (Paper 9) and the in-toto Statement format[3], and is implemented in AumOS model-sbom (S4).

§1. Introduction: the four-artifact problem

To trust a deployed AI system, a relying party must know four things, bound together: which model (weights + architecture), which data it was trained/evaluated on, which code (runtime, tools) executes it, and which configuration governs it. Today each lives in a separate document — an ML-BOM for the model/data, an SBOM for the code, a config file — and nothing binds them. A relying party who verifies the model signature still does not know whether the code invoking it is the audited code; a party who checks the code does not know the configuration. The four-artifact binding is the gap the AATM closes.

§2. Why separate BOMs are insufficient

CycloneDX ML-BOM[1] represents models, datasets, and dependencies well; SPDX 3.0[2] adds the AI profile; the in-toto Attestation Framework[3] provides the Statement+predicate format SLSA provenance builds on. Each is excellent for its artifact class. None binds all four into a single verifiable unit. The consequence: the relying party must manually cross-reference separate documents of separate integrity, a process so error-prone that in practice it is skipped — and the system is trusted on faith.

§3. The AATM structure

┌───────────────────────────────────────────────────────────┐
│              AI Artifact Trust Manifest (AATM)             │
├───────────────────────────────────────────────────────────┤
│  version, system_id                                        │
│  model:    { artifact_hash, arch, license, provenance_ref }│  ← Safetensors++ block (Paper 9)
│  data:     { manifest_hash, license_set, provenance_refs } │
│  code:     { inference_server_hash, agent_runtime_hash,    │
│              tool_hashes, sbom_ref }                       │
│  config:   { config_hash, policy_ref, capability_decl }    │
│  bindings: cross-artifact signed bindings (model↔data↔code↔config)│
│  signature: COSE-Sig(manonical(manifest))                  │
└───────────────────────────────────────────────────────────┘
   single verification entry point: verify signature ⟹ all four bound

§4. Normative: the binding

The bindings are normative and cryptographic: each artifact's hash is signed as part of the manifest, and the manifest signature covers the binding. Substituting any artifact (a different model, a different code commit, a different config) breaks the signature. The binding is the property that makes the four artifacts a system rather than four separate files.

§5. Normative: single-entry-point verification

A conformant relying party verifies the AATM at one entry point: check the manifest signature, then check that each artifact's runtime hash matches the manifest's bound hash. If all match, the system is the audited system; if any differs, the system is not what the manifest claims, and invocation is refused. This single-entry-point design is what makes verification tractable — one check, not four cross-references.

§6. Interop with CycloneDX, SPDX, in-toto

The AATM is designed as a CycloneDX ML-BOM extension (the model/data/code fields reuse CycloneDX types) carrying an in-toto Statement (so it composes with SLSA/OpenSSF signing). SPDX 3.0 interop is provided via a translator, since SPDX 3.0's extensible model can represent the same bindings. The AATM does not compete with these standards; it binds them.

§7. Path to standardization

CycloneDX working-group extension Q1 2027, with a parallel OASIS standard track; committee-spec Q4 2027, referencing the AumOS S4 implementation and the OpenSSF Model Signing interop (Paper 9). The G7 SBOM-for-AI minimum elements (Paper 11) are the floor the AATM exceeds.
