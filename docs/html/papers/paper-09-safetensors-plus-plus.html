Abstract

The open model ecosystem — Safetensors, GGUF, ONNX — has standardized how model weights are serialized, but it has not standardized how their provenance is asserted. A model file downloaded from a hub today carries, at best, a repository commit hash; it carries no cryptographically-signed assertion of who trained it, on what data, under what license, with which dependencies, or whether it has been tampered with since release. OpenSSF Model Signing v1.0[1],[2] addresses the signing layer; we present Safetensors++, a backward-compatible extension to the open model formats that carries signed provenance metadata inside the artifact itself, composes with OpenSSF Model Signing bundles and the in-toto attestation framework[3], and is verifiable by any relying party without a hub round-trip. We position the extension as the format-layer complement to the OpenSSF signing layer and the SLSA[4] provenance model, closing the gap between "is this file signed?" and "do I know what I'm running?"

§1. Introduction: signed but not known

OpenSSF Model Signing v1.0[1] solved an important problem: a relying party can now verify that a model artifact is signed by a trusted identity and has not been altered. But "signed" is not the same as "known." A signed model still does not tell the relying party what dataset it was trained on, what license applies, what base model it was derived from, or what training pipeline produced it — the provenance assertions that determine whether a model is appropriate to deploy, not merely intact. The signing layer answers "is this authentic?"; the missing format layer must answer "what is this?"

§2. Background: model formats and the signing layer

Safetensors (Hugging Face) is the dominant open format for model weights — a simple, memory-mapped tensor serialization. GGUF serves the quantized-inference community; ONNX the interoperable-graph community. None carries structured provenance beyond an optional comment field. OpenSSF Model Signing v1.0[1] and its specification[2] add a signature bundle alongside the model (sigstore-backed, in-toto predicates), which is verifiable but lives outside the artifact — meaning a model divorced from its bundle (copied, mirrored, re-shared) loses its signature. The in-toto attestation framework[3] and SLSA v1.0[4] define the provenance predicate model but are software-oriented; their ML application is emerging.

§3. The metadata gap

The gap is three-fold. (1) Co-location: provenance metadata should travel with the artifact, not in a sidecar that is easily separated on re-sharing. (2) Structure: the metadata should be a signed, schema-validated structure (not free text) so relying parties can make automated deployment decisions. (3) Interop: the structure should compose with OpenSSF signing bundles, in-toto attestations, and the emerging CycloneDX ML-BOM (Paper 11), rather than invent a parallel format.

§4. Safetensors++ design

Safetensors++ extends the Safetensors header (the JSON metadata prefix) with an optional provenance block, signed as a COSE-Sign structure over canonical CBOR (Paper 2). The block is backward-compatible: parsers that do not understand it ignore it (the format's existing extensibility), while conformant parsers verify the signature and surface the provenance.

Safetensors file:
┌──────────────────────────────────────────────────────┐
│ header (JSON, length-prefixed)                       │
│   { tensor_defs...,                                   │
│     "provenance++": {                                 │
│       " signer": { id, key_id, alg },                 │
│       " training": { dataset_manifest_hash, base_model_hash, │
│                      pipeline_hash, framework, started, finished },│
│       " license": { spdx_id, restrictions },          │
│       " evaluation": { benchmark_hashes, scores },    │
│       " lineage_parent": parent_artifact_hash,        │
│       " signature": COSE-Sig(canonical(payload))      │
│     }                                                 │
│   }                                                   │
│ tensor data (memory-mapped, unchanged)                │
└──────────────────────────────────────────────────────┘

The dataset_manifest_hash and base_model_hash bind the model to its inputs without embedding the inputs themselves (preserving confidentiality and size). The signature covers the entire provenance block, so any alteration is detectable. The lineage_parent enables the Merkle lineage ledger of Paper 10.

§5. Interop with OpenSSF, in-toto, SLSA

The provenance block is designed as a carrier for an in-toto Statement (the framework's standard assertion format), so the same attestation that OpenSSF Model Signing writes as a sidecar is embedded in the artifact. This means Safetensors++ does not compete with the OpenSSF signing layer — it co-locates it. A relying party can verify either the embedded copy (no hub round-trip) or fetch the canonical bundle from the OpenSSF transparency log; the two are byte-identical attestations.

§7. Related work

  • OpenSSF Model Signing v1.0[1],[2] — the signing layer Safetensors++ co-locates.
  • in-toto[3] (USENIX Security 2019) — the attestation framework whose Statement the block carries.
  • SLSA v1.0[4] — the provenance model the block instantiates for ML.
  • Sigstore — the keyless-signing infrastructure the interop uses.

§8. Conclusion

Safetensors++ closes the gap between "is this model signed?" and "do I know what I'm running?" by embedding signed, structured, in-toto-compatible provenance in the artifact itself — backward-compatible, co-located with the weights, and byte-identical to the OpenSSF sidecar. It is the format-layer complement to the signing layer.
