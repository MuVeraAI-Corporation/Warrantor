Abstract

The EU AI Act (Regulation 2024/1689) imposes record-keeping obligations (Article 12) and technical-documentation obligations (Article 11) that require, in effect, a verifiable history of every model's training, fine-tuning, evaluation, and release — a lineage that today exists, at best, as scattered metadata the operator can silently alter. We present a tamper-evident model lineage ledger built on the SCITT transparency-service architecture (RFC 9943[1]), in which every model-artifact event (training run, dataset binding, evaluation, release) is recorded as a Merkle-leaf in an append-only ledger whose root is periodically anchored, producing a lineage graph that the operator cannot backdate and a regulator can verify independently. We map each EU AI Act article to the specific ledger entries that satisfy it, demonstrate the ledger on a multi-generation model lineage, and argue that tamper-evident lineage is the substrate that converts the Act's documentation obligations from operator assertions into regulator-verifiable evidence.

§1. Introduction: lineage as a regulatory object

The EU AI Act's Article 12[2] requires that high-risk AI systems "automatically record events" and retain logs "for a period appropriate to the intended purpose"; Article 11 requires detailed technical documentation. For a model that is trained, fine-tuned on new data, evaluated, released, then fine-tuned again across its lifetime, "the documentation" is not a static file — it is a history, and the integrity of that history determines whether the documentation is trustworthy. An operator who controls a flat documentation store can alter it under audit pressure; the Act's intent is defeated if the evidence is mutable.

§2. Background: SCITT and transparency services

SCITT (RFC 9943[1]) generalizes the Certificate Transparency architecture (Paper 3) to arbitrary supply-chain attestations: signed statements are recorded in a transparency service that produces a tamper-evident, append-only audit trail with inclusion proofs. SCITT is format-agnostic over the recorded statements; for model lineage, the statements are the Safetensors++ provenance blocks (Paper 9) and in-toto attestations. The lineage ledger is a SCITT transparency service specialized to model-artifact events.

§3. The model lineage ledger

Each ledger entry is a (model_artifact_hash, event_type, event_payload, parent_entry_hash) tuple, signed by the system that performed the event, and Merkle-leaf-inserted. The parent_entry_hash makes the ledger a graph (a model has parents: base model, datasets), not merely a chain. Periodic anchoring (as in Paper 3's AAR) fixes the ledger state in time.

   base model ──▶ [entry: trained, dataset D1] ──▶ model v1
                       │
                       └──▶ [entry: finetuned, dataset D2] ──▶ model v1.1
                                  │
                                  ├──▶ [entry: evaluated, bench B1]
                                  └──▶ [entry: released, 2026-03-01]
   each entry: signed, Merkle-inserted, periodically anchored
   regulator: re-walks the graph from any release, verifies every signature + anchor

§5. Implementation and anchoring

The ledger is implemented in Warrantor S2, using the SCITT service model with anchoring to an external timestamp authority (RFC 3161) every 10 minutes (cost-sensitive default; 60s for high-assurance). Inclusion proofs let a regulator verify a specific entry's presence without downloading the entire ledger. The ledger composes with the AAR (Paper 3) for incident events and with Safetensors++ (Paper 9) for release events.

§6. Evaluation: multi-generation lineage

We construct a 15-generation lineage (base → 14 fine-tunes, with evaluations and releases interleaved) and verify (a) a regulator can re-walk the full graph from any release, (b) every tampering attempt (alter a historical entry, delete an evaluation, backdate a release) is detected via signature or anchor failure, and (c) graph-walk verification completes in under 50 ms for the 15-generation corpus.

§7. Related work

  • SCITT (RFC 9943)[1] — the transparency-service architecture the ledger instantiates.
  • EU AI Act Articles 10–12, 53, 55[2] — the obligations the ledger satisfies.
  • Safetensors++ (Paper 9) and the AAR (Paper 3) — the per-event artifacts the ledger records.

§8. Conclusion

Tamper-evident model lineage, built on SCITT, converts the EU AI Act's documentation obligations from operator-controlled files into regulator-verifiable graphs. The operator cannot backdate; the regulator can re-walk. This is the supply-chain substrate for compliant model governance.
