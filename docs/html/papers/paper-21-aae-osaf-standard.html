Specification Abstract

This document specifies the Agent Authority Envelope (AAE) as a proposed OSAF standard for verifiable agent delegation, generalizing the research artifact of Paper 1 into an interoperable, multi-vendor specification. The AAE is a signed, audience-bound, time-scoped delegation token that binds a principal's authority to an agent's capabilities and an attested host, with a verification contract (the intersection of Paper 4). The specification is built on established IETF standards — COSE (RFC 9052[1]) over deterministic CBOR (RFC 8949), with selective-disclosure options modeled on SD-JWT (RFC 9901[2]) and SD-JWT VC[3] — and aligns with the W3C VC-JOSE-COSE securing model[4]. The normative sections define the envelope structure, the verification contract, the conformance requirements (Paper 2's CSF-v1), and the registry/interop story. The reference implementation is Warrantor T1/T2; the conformance vectors are V2/V3.

§1. Introduction and status

This document specifies the Agent Authority Envelope (AAE) for submission to the Open Secure AI Foundation (OSAF) and parallel consideration in the IETF. It generalizes the research contribution of Paper 1 (Verifiable Agent Authority) and the safety contract of Paper 4 (Delegation Intersection Semantics) into a normative, multi-vendor specification. The status is a first draft for working-group chartering; the reference implementation and conformance vectors exist today in Warrantor, providing the basis for the standard's testability.

§2. Foundational standards

The AAE is deliberately built on established IETF/W3C standards rather than inventing new infrastructure. COSE (RFC 9052)[1] provides the signing structure; deterministic CBOR (RFC 8949) provides the canonical encoding; SD-JWT (RFC 9901)[2] inspires the selective-disclosure option (an agent may reveal only the capabilities a relying party needs to see); SD-JWT VC[3] and the W3C VC-JOSE-COSE securing model[4] provide the verifiable-credential framing. AUCorrect: RFC 9901 is SD-JWT (selective disclosure), not RFC 9068 (which is the JWT Profile for OAuth 2.0 Access Tokens) — the specification uses the correct RFCs.

§3. Normative: envelope structure

The normative envelope structure is that of Paper 1, §3.1, with the following mandatory fields (typ, alg, kid, principal, agent, audience, capabilities, attestation, validity, freshness, signature) and optional fields (protocol, delegation_chain for multi-hop). Field semantics, type tags, and the canonical-encoding rules (Paper 2's CSF-v1) are normative. The COSE-Sign1 structure is the wire format.

§4. Normative: the verification contract

The intersection verification contract of Paper 4 (§3) is normative: a conformant relying party MUST honor an action only if it is in the intersection G(e) ∩ H(e) ∩ D(e) and the freshness, audience, and signature predicates hold. A relying party that honors the grant G(e) alone is non-conformant. This is the security-critical normative requirement.

§5. Normative: conformance

An implementation claims AAE conformance only after passing the V2/V3 conformance vector suite (Paper 18's service) in all declared runtimes, producing byte-identical canonical encodings and signatures. Conformance is the structural guarantee that makes "AAE-compatible" verifiable.

§6. Interop and the registry story

The specification defines a registry for algorithm identifiers, attestation formats identifiers, and capability vocabularies, so the standard can evolve without re-chartering. The registry is operated by OSAF (or a delegated standards body) under a documented policy. Interop with SPIFFE federation (WP3) and OAuth ecosystems is addressed in appendices.

§7. Security considerations

The security considerations section restates the DY-CA soundness result (Paper 1, §4.2), the canonicalization-defect threat (Paper 2), and the multi-hop safety property (Paper 4). It documents the residual exposures (the un-anchored freshness window; the principal-intent problem; the non-confidential-host attestation degeneration) and the mitigations.

§8. Path to standardization

Proposed path: OSAF working-group charter Q4 2026; draft specification with reference implementation and conformance vectors Q2 2027; v1.0 specification Q4 2027, with parallel IETF BoF exploration for the COSE/SD-JWT composition. The standard ships with the conformance program (Paper 18) from day one — the structural property that distinguishes it from single-vendor delegation schemes.
