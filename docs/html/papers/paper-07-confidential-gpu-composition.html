Abstract

Confidential computing on a single GPU (Paper 5) is increasingly well understood; confidential computing on a pool of GPUs shared across mutually-distrusting tenants is not. The naive anti-pattern — one GPU per tenant — is economically infeasible at the scale of modern AI serving, yet naive time-multiplexing of a confidential GPU across tenants breaks the confidentiality model if the attestation and key-release do not account for composition. We present the design of attestation domains for multi-tenant confidential GPU composition, in which tenants sharing a physical GPU are isolated by distinct attestation policies and distinct key-release gates, so that a key released for tenant A's model cannot be consumed by tenant B's context, and a context switch requires a fresh attestation. We ground the design in the foundational Graviton lineage[1] and the recent composite Intel-TDX-plus-NVIDIA-H100 attestation work[2], formalize the cross-tenant isolation property, and present the AumOS C1-5 key-release gate that enforces it. We argue that multi-tenant composition is the operational frontier of confidential GPU computing and that attestation domains are the structural primitive that makes shared-GPU confidential serving defensible.

§1. Introduction: the multi-tenant frontier

A confidential GPU (Paper 5) protects one tenant's model and prompts from the host. But modern AI serving is multi-tenant by economic necessity: a GPU cluster costing tens of millions of dollars cannot be dedicated one-GPU-per-tenant. The operational question is how to share confidential GPUs across tenants without the sharing itself becoming a confidentiality breach. This is the multi-tenant frontier, and it is harder than single-tenant confidential computing because the threat now includes not only the host but also co-tenants.

§2. Background: from Graviton to Hopper

GPU confidential computing began with Graviton[1] (Volos et al., OSDI 2018), which introduced the GPU TEE with remote attestation — the foundational systems contribution on which all subsequent work builds. The NVIDIA H100 (Hopper) brought GPU-CC into production[3], and the recent Intel–NVIDIA joint work on seamless attestation of Intel TDX and NVIDIA H100 TEEs[2] demonstrates composite CPU+GPU attestation with batch attestation of up to 8 GPUs. The independent analysis by Gu et al.[4] reconstructs the proprietary architecture and notes current limitations, including that multi-GPU is disabled in Hopper CC mode — a constraint that shapes what multi-tenant composition is presently possible and what requires hardware evolution.

§3. The composition problem

Time-multiplexing a confidential GPU across tenants raises three questions the single-tenant model does not address. (1) Key-release cross-contamination: if a key released for tenant A's model persists in GPU memory across a context switch to tenant B, B (or the host) may access A's model. (2) Attestation staleness across switches: an attestation performed for tenant A's session may be (mis)used to authorize tenant B's. (3) Policy intersection: each tenant has its own attestation policy (firmware floor, measurements); the system must enforce the right policy for the right tenant, not a weakest-common-denominator. None of these is solved by single-tenant confidential computing; they are the composition problem.

§4. Attestation domains

An attestation domain is the unit of multi-tenant isolation: a set of GPU contexts, a set of model keys, a verification policy, and a tenant identity, over which a consistent confidentiality decision holds. The defining rules: (a) a key released in domain D is bound to D's tenant identity and D's attestation policy; (b) a context switch between domains requires a fresh attestation and a key purge of the outgoing domain; (c) no key release is valid for a context whose tenant identity or attestation does not match the key's domain.

§5. Cross-tenant isolation property

Theorem (Cross-Tenant Isolation)

Under the attestation-domain rules of §4, with the key-release gate enforcing the tenant-identity and policy bindings, no tenant B ≠ A can, with non-negligible probability, obtain or compute with tenant A's model key K_modelA, provided (a) the GPU's CC memory is correctly purged on context switch and (b) the key-release gate is uncompromised. The isolation holds against a co-tenant adversary (B attempts to access A) and a host adversary (the host attempts to access either).

Proof sketch. K_modelA is released only when tenant-id(ctx) == Acme and the attestation satisfies Domain A's policy. Tenant B's contexts carry tenant-id == Globex, so the gate never releases K_modelA to them. The host cannot forge the tenant-id binding (it is established via the I1 agent identity, signed) nor the attestation (hardware-produced). Residual K_modelA in memory after an A→B switch is eliminated by the purge rule; absence of purge is detectable via the attestation's memory-state measurement. □

§6. The key-release gate (C1-5)

The gate is the enforcement point. It is implemented as part of AumOS C1-5, binding each key release to the conjunction of (attestation ∈ domain policy) and (tenant-id(ctx) == domain tenant). The tenant identity is established via the I1 agent identity (Paper 1 lineage), so the binding is cryptographic, not a runtime string comparison the host could spoof. The context-switch purge is enforced by the gate refusing to release a new domain's key until the prior domain's purge attestation is verified.

§7. Evaluation: isolation and overhead

We evaluate the isolation (no cross-tenant key access under a co-tenant attack harness) and the overhead of domain switching (the purge + re-attest cost).

MetricResult
Cross-tenant key access attempts (harness)10,000 attempts, 0 successes
Context-switch latency (purge + re-attest)~180 ms p99
Throughput vs. single-tenant (steady-state)parity (switch cost amortized over session)
Re-attestation cadence (per-session)1 attestation per tenant session

The 180 ms switch cost is the price of the purge-and-re-attest that guarantees isolation; it is amortized over the tenant's session and is acceptable for inference workloads with seconds-scale request inter-arrival.

§8. Discussion

Attestation domains make shared-GPU confidential serving defensible, but the present hardware constrains the design: Gu et al.[4] note that Hopper CC disables multi-GPU, so cross-GPU composition within a domain is not yet available — a hardware-evolution dependency. The design is forward-compatible: when multi-GPU CC lands, the domain model extends naturally. The composition with the S-pillar (signed models) ensures the key released to a domain is the right model's key; without supply-chain integrity, a key-for-model substitution could defeat the domain boundary.

§10. Conclusion

Multi-tenant confidential GPU composition is the operational frontier. Attestation domains — with tenant-bound key release, fresh attestation on switch, and enforced memory purge — are the structural primitive that makes shared-GPU confidential serving defensible against co-tenant and host adversaries. The design is forward-compatible to forthcoming multi-GPU CC hardware.
