Abstract

Serving a large language model is, today, an act of wholesale trust: the model owner hands weights to the serving operator, the user hands prompts to the same operator, and both must trust that the operator will not exfiltrate, leak, or repurpose either. Confidential computing on the NVIDIA H100 (Hopper) GPU — with its hardware-enforced confidential-computing mode and remote attestation — offers the structural alternative: serve inference inside a TEE whose confidentiality is guaranteed by the hardware, not the operator. We present the design and reference implementation of an end-to-end attested inference pipeline built on AumOS's C1 components, in which model weights are encrypted to a policy only an attested GPU can satisfy, prompts traverse the host only as ciphertext, and the attestation handshake gates model-key release. We measure the overhead of the full confidential path versus a non-confidential baseline on the H100, characterize where the overhead arises (PCIe encryption dominates, per prior work[4]), and document the operational properties that distinguish a defensible confidential-serving deployment from a superficial one. We position the pipeline as the reference implementation that makes "confidential AI" a verifiable property rather than a marketing claim.

§1. Introduction: the trust problem in model serving

Modern LLM serving concentrates three sensitive assets in the hands of one party — the serving operator. The model weights are the model owner's crown-jewel intellectual property, often the product of months of training at seven-figure cost. The prompts are the user's private data, frequently containing personal, medical, or proprietary information. The outputs may themselves be sensitive. Today, all three traverse the operator's infrastructure in plaintext: the operator can read the weights, log the prompts, and inspect the outputs at will. The legal mitigations (DPAs, terms of service) are promises; the technical mitigation — confidential computing — exists but is poorly operationalized.

The NVIDIA H100 GPU, released in 2022 and broadly deployed by 2024, introduced hardware-enforced confidential computing (Hopper CC[1]): a mode in which the GPU's memory is cryptographically protected from the host, and the GPU produces a signed attestation report a remote verifier can check before trusting it. This is the hardware primitive that makes end-to-end confidential LLM serving possible in principle. Making it possible in practice — turning the primitive into a deployable, defensible pipeline — is the contribution of this paper.

§2. Background: GPU confidential computing

The H100's confidential-computing mode (HCC) establishes a hardware root of trust: the GPU boots into a measured state, asserts a confidential-computing mode that protects its memory from the host CPU and hypervisor, and produces an attestation report whose verification confirms the firmware version, the CC-mode assertion, the debug-disabled flag, and the measurement values[1]. The recent independent analysis by Gu et al. ("Blueprint, Bootstrap, and Bridge"[2]) reverse-engineers and reconstructs the proprietary NVIDIA GPU-CC architecture, documenting the bootstrap process and the data-transfer protections (the "bridge"), and responsibly disclosing security findings to NVIDIA PSIRT. This is the most rigorous public account of how GPU-CC actually works, and our pipeline builds on its threat-model clarifications.

The foundational lineage is Graviton[3] (OSDI 2018), which introduced GPU TEEs with remote attestation; Hopper CC is the production descendant. The performance characterization of Chrapek et al.[4] establishes that the dominant overhead in confidential LLM inference on H100 is the CPU–GPU encrypted transfer (PCIe encryption), not GPU compute — a finding our measurements reproduce and that shapes our tuning recommendations.

The five components and their trust-boundary roles: C1-1 binds to NVIDIA NVTrust and establishes the attestation domain; C1-2 is the high-level Python attestation client that retrieves and verifies the report; C1-3 orchestrates the inference server inside the TEE; C1-4 terminates TLS inside the enclave so prompts are never plaintext on the host; C1-5 gates model-key release, handing the key to the GPU only after attestation verifies. None is sufficient alone; the composition is the contribution.

§4. The attestation handshake and key release

The defining security property is that the model key never exists on any host that has not been attested. The handshake (protocol P3) achieves this: the model owner encrypts weights to a policy (a predicate over firmware version, CC mode, debug state, and measurements); the serving node brings up the H100 in CC mode and obtains an attestation report; C1-2 verifies the report against the policy; only on success does C1-5 release the key — and the release channel routes the key directly into the GPU's protected memory, never through host RAM. A host that fails attestation never receives the key; the encrypted weights are useless to it.

The freshness requirement

An attestation report proves the GPU's state at the moment of reporting. A serving node could, in principle, be reconfigured after attestation. The defense is to re-attest on a cadence (per-session for high-assurance; per-window for throughput-sensitive) and to bind each key release to a fresh report. The cadence is the trade-off between assurance and overhead; we report both regimes in §6.

§5. Reference implementation on H100

We implement the pipeline on an NVIDIA H100 cluster using the NVIDIA Attestation SDK (NRAS / LocalVerify) for report retrieval and verification, the Gramine LibOS to run an unmodified inference server inside a TEE without application changes (per the Chrapek et al. finding[4] that LibOS approaches avoid the application modifications FHE requires), and the AumOS C1 components as the orchestration and key-release layer. The implementation is the artifact a platform team deploys to make confidential inference operational.

§6. Evaluation: overhead and the confidentiality boundary

We measure throughput and latency of the full confidential path versus a non-confidential baseline on a representative LLM inference workload, and we verify the confidentiality boundary by inspection (no plaintext weights or prompts on host disk; no plaintext on the PCIe bus outside the encrypted channel).

ConfigurationThroughputp99 latencyPlaintext on host
Baseline (non-confidential)1.00×1.00×weights + prompts
Confidential, per-window attestation0.89×1.08×none
Confidential, per-session attestation0.82×1.14×none

The 11–18% throughput overhead is consistent with the Chrapek et al. finding that PCIe encryption dominates, and is recoverable in part through batch-size tuning and key-caching. The confidentiality boundary — no plaintext weights or prompts on the host — is the structural deliverable: it is what converts "confidential AI" from a claim to an inspectable property.

§7. Discussion

The pipeline's security rests on the H100's hardware root of trust and the NVIDIA attestation service's integrity. The threat it defeats is the honest-but-curious operator and the compromised host; it does not defeat an adversary who controls the GPU firmware at fabrication (a supply-chain threat addressed by the S-pillar, Paper 9). The composition with the S-pillar — signed model provenance feeding the encrypted-weights registry — is the full defense. Whitepaper WP5 translates this paper into a deployment guide for infrastructure teams.

§9. Conclusion

End-to-end attested inference is the structural answer to the trust concentration of model serving. The pipeline composes five components into a path where model weights and prompts are never plaintext on the host, gated by an attestation handshake. The 11–18% overhead is the cost of the property, and it is recoverable through tuning. The contribution is the deployable, defensible pipeline — the reference that makes confidential AI verifiable.
