Specification Abstract

This document specifies the Agent Action Receipt (AAR) as an OSAF standard for tamper-evident, hash-chained, timestamp-anchored logging of autonomous-agent actions, generalizing the research artifact of Paper 3 into an interoperable specification. The AAR is designed for cross-organizational verification — a regulator can verify an operator's receipts without trusting the operator — composes with the AAE (Paper 21) as the evidence artifact for each authorized action, and maps directly to EU AI Act audit obligations (Articles 12, 55). The architecture reuses the transparency-log model of Certificate Transparency (RFC 9162[1], RFC 6962[2]) and its generalization SCITT (RFC 9943), with an AI-audit specialization. The reference implementation is AumOS flight-recorder; the tamper-detection property is proven in Paper 3.

§1. Introduction and status

This OSAF specification generalizes the Agent Action Receipt of Paper 3 into a vendor-neutral, cross-organizationally-verifiable standard. It is a companion to the AAE specification (Paper 21), sharing the working-group charter. The defining property — tamper-evidence against an operator adversary (Paper 3, §4) — is the security objective the normative requirements enforce.

§2. Foundational transparency-log standards

The AAR architecture is a specialization of the transparency-log model: Certificate Transparency v2 (RFC 9162)[1] and its predecessor RFC 6962[2] define the append-only Merkle-tree log with inclusion proofs verifiable by independent monitors; SCITT (RFC 9943) generalizes this to arbitrary supply-chain attestations. The AAR applies the SCITT transparency-service architecture to agent actions, with an AI-audit-specific statement format (the receipt payload of Paper 3, §3.1).

§3. Normative: receipt structure

The normative receipt fields (Paper 3, §3.1): seq, prev_hash, timestamp, action, aae_ref, principal, agent, relying_party, signature. All fields are mandatory; the encoding is COSE-Sign over CSF-v1 canonical CBOR. The aae_ref binds the receipt to the AAE (Paper 21) that authorized the action, making "on what authority?" answerable from the receipt alone.

§4. Normative: chaining and anchoring

Normative requirements: (a) prev_hash MUST be the SHA-256 of the prior receipt's canonical encoding; (b) the chain MUST be periodically anchored (default 60s high-assurance, 600s cost-sensitive) to an external timestamp authority (RFC 3161) or transparency log, producing an inclusion proof; (c) anchors MUST be independently verifiable. These enforce the tamper-detection property of Paper 3, Theorem (Tamper-Detection).

§5. Normative: the verification procedure

A conformant verifier MUST: re-hash each receipt and check the prev_hash chain; verify each signature; check the inclusion proofs against the anchored roots; and report any break as a tamper event. The procedure is what makes the AAR verifiable by a regulator without trusting the operator.

§6. Composition with AAE and the kill switch

The AAR composes with the AAE (every honored action produces a receipt, by construction — Paper 3, §5) and with the kill switch (R3 triggers forensic-freeze, sealing and anchoring the chain — Paper 14). This composition is what makes the AAR the evidence substrate for incident response as well as audit.

§7. Path to standardization

OSAF charter Q4 2026 (shared with AAE); v1.0 specification Q4 2027, coordinated with the IETF SCITT working group for the transparency-service interop. The standard ships with the tamper-detection test harness (Paper 3, §6) as the conformance gate.
