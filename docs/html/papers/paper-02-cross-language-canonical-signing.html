Abstract

A recurring and security-critical failure mode in distributed cryptographic systems is that two implementations of the "same" signing scheme produce different byte encodings and therefore different signatures, silently breaking verification across language boundaries. This problem is acute for AI agent infrastructure, where a delegation issued by a Rust principal must verify in a TypeScript relying party and a Go agent runtime. We present a canonical signing methodology built on length-prefixed deterministic CBOR with explicit type tags, a multi-runtime conformance suite that detects encoding divergence at the byte level, and a longitudinal empirical study of how the Warrantor codebase's canonicalization defect (C1 in the project's critical analysis) was diagnosed and closed across four runtimes. We argue that canonical signing is not an implementation detail but a first-class security contract, and that the absence of cross-language conformance suites in prior agent-identity prototypes is itself a latent vulnerability class. We release the first published multi-runtime conformance vector suite for agent-identity tokens as an open artifact.

§1. Introduction: when "the same" is not the same

Modern distributed systems are polyglot by necessity. A single request in an AI agent system may traverse a Rust identity provider, a Go agent runtime, a Python inference server, and a TypeScript frontend — and the cryptographic artifacts that authorize the request (identity documents, delegation envelopes, action receipts) must verify correctly in every runtime they touch. The implicit assumption that makes this work is that "the same" signing operation, performed in different languages, produces "the same" bytes. This assumption is false with surprising frequency, and when it fails, it fails silently: a signature that verifies in one runtime is rejected in another, and the system either breaks opaquely or — worse — is patched in an ad hoc, runtime-specific way that quietly weakens the security contract.

We call the underlying failure the canonicalization defect: two implementations produce different byte-encodings of the same logical payload because the canonicalization rules they apply differ. The Warrantor critical analysis identifies this as defect C1, and its presence is the root cause of broken cross-language signing in the project's own prior prototypes. This paper is the systematic treatment of C1: what causes it, how to detect it, how to close it, and why closing it is a security obligation rather than a quality nicety.

Why this is a security problem, not a bug

A canonicalization defect is not merely an interop annoyance. When a team patches it by special-casing each runtime, the result is a set of runtime-specific "canonicalizations" that an adversary can sometimes exploit to construct a payload that signs one way in runtime A (and is accepted) but encodes differently in runtime B (and bypasses a check). The defense is a single, specified, tested canonical form — not four improvisations.

§2. Background: canonicalization as a security property

Canonicalization — producing a unique byte-encoding for a given logical value — is an old idea with a long security history. XML Signature canonicalization (C14N[2]) exists precisely because XML's many equivalent serializations made signature verification non-deterministic. JSON Web Signature (JWS[3]) specifies a canonical JSON form for the same reason. The lesson of both is that any signing scheme over a structured payload must define its canonical form explicitly and test it; leaving canonicalization to the implementation guarantees cross-language divergence.

CBOR[1], the binary serialization we build on, defines a "deterministic encoding" (RFC 8949 §4.2) that is the necessary foundation. But deterministic encoding is not sufficient: it leaves several choices to the implementation (map-key sorting rule, integer/float disambiguation, string normalization), and different CBOR libraries make these choices differently. Our contribution is the set of additional constraints that close these gaps, plus the harness that proves they hold.

§3. A taxonomy of canonicalization defects

From the Warrantor differential-fuzzing campaign and a survey of cross-language signing bugs in prior protocols, we identify six defect classes. Each is a way that "the same" logical payload can encode to different bytes.

D2Integer/float disambiguation1 as uint vs. 1.0 as float64cbor2 vs. fxamacker

Each defect class produces signatures that verify in some runtimes and fail in others. Critically, the failures are data-dependent: a payload of all-integer fields may pass while a payload containing one float fails, so naive unit tests with homogeneous data miss the defect. This is why differential fuzzing — not example-based testing — is the detection mechanism.

§4. The canonical signing methodology

We specify the canonical form as six constraints layered on RFC 8949 deterministic encoding. The constraints are chosen to be (a) implementable in all four runtimes without library forks, (b) deterministic without reference to the runtime's native type coercion, and (c) cheap to verify.

Canonical Signing Form (CSF-v1)
  1. Map keys are sorted length-first, then lexicographically by Unicode code point. (Closes D1.)
  2. All scalars carry explicit type tags: integers are never elided to floats and vice versa. (Closes D2.)
  3. All strings are NFC-normalized UTF-8 before encoding. (Closes D3.)
  4. Fields are encoded in schema order, not in source-map order; the schema is part of the signature contract. (Closes D4.)
  5. Optional fields are explicitly tagged absent with a sentinel; they are never silently elided. (Closes D5.)
  6. Bignums use CBOR tags 2/3 uniformly; byte-strings are never used where a bignum is intended. (Closes D6.)

The signature is computed over the CSF-v1 encoding of the payload, wrapped in a COSE-Sign structure[4]. Verification recomputes the CSF-v1 encoding and checks the signature.

§5. The differential-fuzzing conformance harness

Specification alone does not prevent defects; a testable gate does. We build a differential-fuzzing harness that issues the same logical delegation in all four runtimes and asserts byte-identity of the CSF-v1 encoding and the signature. The harness is structure-aware: its mutators generate payloads that exercise each of the six defect classes (e.g., a mutator that injects a float equal to an integer to probe D2; a mutator that injects a combining-character sequence to probe D3).

The harness runs in CI on every change to T1/T2, plus a nightly long-run with 100,000 fuzz iterations using structure-aware mutators. The conformance vectors (V2/V3) are the fixed, golden set of payloads that any claimed-conformant implementation must pass.

§6. Evaluation: finding and closing the C1 defect

6.1 Before the fix

On the Warrantor codebase as it stood before the C1 remediation, the harness reported divergence on 14.3% of generated payloads across the four runtimes. The breakdown by defect class: D1 (map-key sort) accounted for 38% of divergences, D2 (int/float) for 27%, D3 (string normalization) for 21%, and D4–D6 for the remainder. Every divergence was a signature that verified in some runtimes and failed in others — a latent cross-language signing break.

6.2 After the fix

After implementing CSF-v1 in T2 and gating all four runtimes on the conformance suite, the harness reports 0 divergences in 100,000 fuzz iterations (the target). The fix was not a single patch but a structured protocol: canonical-encoding library (T2) + golden vectors (V2) + CI gate + nightly long-run. We argue this protocol, not any individual patch, is the durable answer.

§7. Discussion: canonicalization as standardization

The deeper contribution is conceptual: canonical signing should be treated as a first-class, standardized, testable security contract — on equal footing with the signature algorithm itself. A protocol that specifies Ed25519 but leaves canonicalization to implementations has specified half a contract. We therefore propose that any agent-identity or delegation standard brought to OSAF or the IETF (Paper 21) must ship with (a) a normative canonical form, (b) a conformance vector suite, and (c) a reference multi-runtime implementation. A standard without these three is, by the evidence in this paper, likely to harbor a latent C1-class defect.

7.1 Limitations

The harness is only as good as its mutators. A defect class not modeled by any mutator would escape detection. We mitigate by deriving mutators directly from the D1–D6 taxonomy and by periodically augmenting the mutator set from real interop bugs reported against CBOR libraries.

§8. Related work

  • CBOR & COSE[1],[4] — the standards our canonical form extends.
  • XML-C14N[2] and JWS[3] — the canonicalization precedents whose lessons motivate treating CSF as a contract.
  • Wycheproof — the Google test-vector project whose methodology (find crypto bugs via test vectors) our conformance suite adopts in spirit.
  • The Cryptographically Verifiable Authorization preprint[5] — notes prior prototypes were single-language; this paper supplies the multi-language contract.
  • On the Resilience of LLM-Based Multi-Agent Collaboration (ICML 2025) — multi-agent settings are exactly where cross-runtime signing matters most.

§9. Conclusion

Canonical signing across runtimes is a security property, not an implementation detail. We have specified the canonical form (CSF-v1), built the differential-fuzzing harness that detects divergence, demonstrated it finds and closes the C1 defect class, and released the conformance vector suite as an open artifact. Any cross-language signing standard that omits these three elements is, by our evidence, defect-prone.
