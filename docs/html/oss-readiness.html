1.Executive Summary

AumOS reconciles four source portfolios (DefStack 36-component, AumSecure 20+ protocols, AumSecure-V3 6-repo, PROJECT SENTINEL 10-framework) into one unified catalog of 49 implementable components across four languages and 12 spec-only protocols. The strategic question is no longer whether to open-source it — the OSAF (Open Secure AI Alliance) mandate requires verifiable, multi-vendor agent authority and evidence — but how and when.

Why now. The agent-security space is a land grab. EU AI Act Article 55 obligations land on GPAI providers in 2026-2027; vendors are racing to ship proprietary attestation layers; and the window to set the open standard for agent authority (the AAE), agent evidence (the AAR), and capability attestation (the CAP) is open for roughly 12-18 months before a closed incumbent locks it down. AumOS already has the most complete reference implementation. Open-sourcing it converts that lead into a defensible standard.

The Strategy in One Sentence

Publish AumOS as a hybrid GitHub organization under a single pure Apache 2.0 license, governed BDFL → Steering Committee → Foundation, with the 12 protocols submitted to OSAF as the standard-bearing wedge and the cryptographic spine fixed before a single repo goes public.

The strategy has three pillars:

  • Hybrid repo model. One core monorepo (the contract plane + Rust trusted core + cross-cutting docs), one repo per independently-adoptable service/package, one repo per OSAF protocol. Maximizes both coherence (the contract plane is enforced centrally) and adoption (a Go shop can go get one service without cloning 49 components).
  • Pure Apache 2.0. No BSL, no "source-available" tiers, no 4-year change-date gymnastics. Apache 2.0 is the license OSAF member orgs can adopt without a legal review. The commercial moat is the managed cloud (X11 defstack-cloud) and enterprise support, not license lock-in.
  • OSAF protocol submission. The 12 protocols (AAE, AAR, CPE, AMIL, SSP, AATM, ABS, VEB, AIX, MADE, PRB, CAP) are submitted to OSAF working groups as candidate standards. Each ships with normative CDDL + JSON-Schema, a conformance test suite, and 2+ reference implementations. Winning the standard is worth more than winning the implementation.
Prerequisite — No Public Repo Until C1-C7 Are Fixed

The critical analysis found 7 critical findings (C1-C7) in the cryptographic spine: non-deterministic canonical CBOR, signature-collision canonicalization in flight-recorder/provena-chain, eval-guard attestation not binding results, GPU attestation nonce replay, agent-identity audience no-op, AAE validator trusting caller-supplied bytes, and the kill-switch government API faking confirmed: true. Shipping these publicly under the AumOS banner would destroy credibility on day one. Fixing C1-C7 is a hard gate on launch.

2.GitHub Organization Structure

The organization lives at github.com/MuVeraAI. It uses a hybrid model: one core monorepo that enforces cross-language coherence, a fan-out of independently versionable service repos, and a parallel set of protocol repos that are the OSAF-standard wedge. This is the same shape as the OpenTelemetry project (a core repo + per-language SDKs + a specification repo) — proven to scale to hundreds of contributors.

3.Licensing — Pure Apache 2.0

Every repo in the MuVeraAI org is Apache License 2.0. No exceptions, no BSL, no "change date" tiers. This is a deliberate departure from the earlier governance draft (which proposed BSL 1.1 for enterprise features). The rationale:

Option consideredVerdictWhy
Apache 2.0 (chosen)AdoptedMaximum adoption. OSAF member orgs (and their legal teams) accept Apache 2.0 without review. Permits the patent grant that security infrastructure needs. Compatible with the Rust/Go/Python/npm ecosystems. This is what a standard is licensed under.
BSL 1.1 for enterpriseRejectedThe HashiCorp/MongoDB playbook protects early commercial value but creates permanent friction for every adopter. For a standard, adoption is the asset. Cloud competition is defended by the managed cloud and trademark, not the license.
GPL / AGPLRejectedCopyleft would block adoption by the closed-source incumbents whose compliance we want to enable. Wrong tool for infrastructure that must be embedded.
MPL 2.0 (file-level copyleft)RejectedA reasonable middle ground, but adds just enough friction that Apache 2.0 is strictly better for a standard.

SPDX & file headers

  • Every repo root carries LICENSE (Apache-2.0 full text) and LICENSE-APACHE.
  • SPDX identifier SPDX-License-Identifier: Apache-2.0 appears at the top of every source file (Rust //!, Go //, Python module docstring, TS header comment).
  • Cargo.toml / pyproject.toml / package.json / go.mod all declare license = "Apache-2.0".
  • Protocol specs (CDDL/JSON-Schema) and documentation are dual-licensed Apache-2.0 (for code) and CC-BY-4.0 (for the prose spec), so OSAF can adopt them as standards with no encumbrance.

DCO, not CLA — for individuals

Individual contributors sign the Developer Certificate of Origin only. Every commit carries Signed-off-by: Jane Doe <jane@example.com> via git commit -s. A CI bot (probot/dco) rejects unsigned commits. The DCO asserts the contributor has the right to contribute the code — it is not a copyright assignment. Contributors keep their copyright.

CLA bot — for corporate contributors

Corporate contributors (employees contributing on behalf of an employer) complete a lightweight Corporate CLA via the cla-assistant GitHub App. The CCLA is a one-time org-level grant, not per-employee. This protects the foundation's ability to relicense (e.g., on donation to Linux Foundation) without chasing down every contributor.

Trademark

"AumOS", "DefStack", and the OSAF protocol names (AAE, AAR, CAP, etc.) are trademarks of the founding company, licensed freely to OSS projects that comply with the usage guidelines. Commercial products and derivative forks must use a distinct name (e.g., "Acme AumOS Fork"). Trademark policy lives at github.com/MuVeraAI/.github.

4.Governance

Governance is phased, matching the project's maturity. Each phase lasts roughly a horizon.

Phase 1 (M0-M12)BDFL — CEO/CTO decides, with maintainer input. Rationale: speed during the OSS land grab. The BDFL is the final reviewer on every protocol RFC.
Phase 2 (M12-M24)Steering Committee — 5-7 members: founding team + key external contributors + 1 OSAF representative. Consensus where possible, 2/3 majority vote otherwise. Incorporates community input as adoption grows.
Phase 3 (M24+)Foundation Donation — Option A: Linux Foundation; Option B: a dedicated AumOS Foundation under OSAF; Option C: PyTorch-style governance. Maximizes neutrality for long-term adoption.

RFC Process

  1. Idea → open a GitHub Discussion in github.com/MuVeraAI/aumos.
  2. Draft RFC → PR against docs/rfcs/ using the 10-section template. Two-week comment window minimum.
  3. Accepted / Rejected / Deferred → Steering Committee decision (Phase 1: BDFL). Accepted RFCs get a tracking issue and a component/protocol repo if applicable.
  4. Implementation → the RFC's tasks/01-setup.md ... 08-release.md drive the work. A typical component takes one coding-agent session (~8 focused hours).

Conflict Resolution

  • Technical disputes → RFC discussion → Reviewer consensus → Steering Committee vote (2/3 majority).
  • Behavioral disputes → Code of Conduct enforcement by the CoC team (3 volunteers, rotating annually).
  • License/IP disputes → Legal counsel + Steering Committee; the offending contribution is reverted pending resolution.

Code of Conduct

AumOS adopts the Contributor Covenant 2.1, enforced by a rotating 3-person CoC team. Reports go to conduct@MuVeraAI.org (confidential, reviewed within 72 hours). The full text lives at github.com/MuVeraAI/.github/CODE_OF_CONDUCT.md and is mirrored into every repo.

5.Contribution Workflow

The contribution workflow is identical across every repo in the org — defined once in the cross-cutting developer-experience standard and enforced by per-repo templates.

The loop

1. Fork the repo (github.com/MuVeraAI/<repo>) or branch if internal
2. git checkout -b feat/<canonical-id>-<short-description>
3. Make changes; commit with `git commit -s`   (DCO sign-off — REQUIRED)
4. make lint test conformance                    (all must pass locally)
5. Open PR; fill the template (which RFC, which task ticket, coverage delta)
6. Two reviewer approvals required:
     - 1 from the component owner (codeowner per OWNERS)
     - 1 from any other maintainer
7. CI runs: lint + test + conformance + SBOM (CycloneDX) + SLSA L3 provenance
8. Squash-merge to main; maintainer cuts a signed release tag

Commit message format: feat(<scope>): <subject> / fix / docs / refactor / test / chore / ci / build. Scope = canonical ID (e.g. feat(T1): switch to ciborium canonical CBOR).

The 5-Minute Quickstart

A new contributor's first task must be runnable in 5 minutes on a fresh machine. If it takes longer, that is a bug against the developer-experience standard.

git clone https://github.com/MuVeraAI/aumos.git

make test       # tests every present language; skips missing ones

How to add a new component

  1. Write an RFC in docs/rfcs/<id>-<name>.md (10-section template). Get it to "Accepted".
  2. Scaffold the RFC's companion files: CLAUDE.md (build instructions), AGENTS.md (agent anti-patterns), PROMPT.md (master agent prompt), tasks/01-setup.md ... 08-release.md.
  3. Decide the language via the polyglot stack-test doctrine (default Rust; Go only if it clears the Go activation gate — 3 of 7 conditions).
  4. If it's a standalone service/package, create its repo under github.com/MuVeraAI/<name> from the repo-template; otherwise add it to the monorepo.
  5. Register it in docs/00-reconciliation-matrix.md and the conformance suite.

6.CI Strategy

CI runs at two levels: per-repo CI (every repo is independently buildable and testable) and cross-repo conformance (the core monorepo runs the conformance suite against every implementation).

Per-repo CI (GitHub Actions)

Every repo has the same workflow shape, templated from github.com/MuVeraAI/.github/workflow-templates:

JobWhat it enforces
lintclippy::pedantic (Rust), golangci-lint (Go), ruff + mypy (Python), eslint + prettier (TS)
testFull unit + integration test suite. Matrix over supported OS / language-version.
conformanceRun the shared testvectors/ against this implementation. Fails on any vector mismatch.
coveragecargo-tarpaulin / go test -cover / coverage.py / c8. PRs that drop coverage below threshold are blocked.
SBOMGenerate CycloneDX SBOM on every build; attach to release.
SLSA L3Provenance attestations via slsa-github-generator. Every release artifact is verifiable back to source.
DCOprobot/dco rejects unsigned commits.
secret-scangitleaks on every push.

Cross-repo conformance (the contract plane)

The core monorepo's tools/conformance/run.sh is the heartbeat of the whole org. On every change to proto/, specs/, or testvectors/, it checks out every implementation (the Rust crates in-tree, plus the latest tag of each service repo) and runs the conformance suite against all of them. A drift in one language fails the build for everyone — exactly the property the contract plane is supposed to provide.

Critical-analysis finding H3 — conformance is one vector today

Currently the "cross-language conformance lane" is a single Ed25519 signature over the bytes "hello aumos conformance" — verified raw, not over canonical-CBOR. The testvectors/README.md promises vectors for C1-1/C1-2/R2/R3/R4/I1/P1/P2 — none exist. Expanding this to canonical-CBOR vectors, protocol vectors, and adversarial vectors (H3 fix) is itself a launch task, because without it the conformance gate is theatrical.

Release process

  1. Maintainer opens a release PR with an updated CHANGELOG.md (Keep a Changelog format).
  2. CI runs the full test suite + security scans.
  3. Reviewer approves.
  4. Maintainer cuts a signed tag (git tag -s, GPG / Sigstore).
  5. CI publishes to the package registry (crates.io / PyPI / npm / pkg.go.dev).
  6. A GitHub Release is created with release notes + SBOM attached.
  7. Announcement: Discord, the blog, the @MuVeraAI account.

Releases are signed and reproducible. Every release artifact carries an SLSA L3 provenance attestation that can be verified with cosign verify-attestation.

7.Security

For a project whose entire value proposition is "verifiable agent authority and evidence," the security posture is the product. The disclosure policy is modeled on Google Project Zero and is documented in full in the cross-cutting security-disclosure standard.

SECURITY.md — private disclosure

  • Do NOT open a public GitHub issue for security vulnerabilities.
  • Email security@MuVeraAI.org (PGP key published at MuVeraAI.org/security/pgp-key.asc), or use the GitHub "Security" tab → "Report a vulnerability" (creates a private advisory).
  • Reports should include: component name and version, description, reproduction steps, impact assessment, suggested fix (optional), and credit handle (optional).
  • We promise: acknowledge every report within the SLA, credit reporters, take no legal action against good-faith reporters, work with reporters on coordinated disclosure, and be transparent about timelines.

90-day coordinated disclosure

We follow the Google Project Zero standard: reporter reports → we acknowledge within SLA → we develop the fix → fix released → public disclosure after the fix is widely deployed, or 90 days, whichever is sooner. Extensions are granted for good cause (e.g., a complex fix requiring a major version bump).

CVE Numbering Authority & bug bounty

  • CNA candidate. AumOS applies to become a CVE Numbering Authority by M9. Until then, CVEs are requested through MITRE (cveform.mitre.org); critical issues get expedited assignment.
  • Bug bounty (Q2 2027). A HackerOne program launches post-Series A. Until then, reporters are credited in release notes and receive AumOS swag.
  • Backporting. Current major (v1.x): all fixes. Previous major (v0.x): Critical/High only. Older: end of life, upgrade required.
