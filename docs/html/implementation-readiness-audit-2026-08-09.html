01 · Executive verdict

Broad implementation. Narrow proof.

“Implemented” in this report means source exists and behaves under at least some tests. It never means the component is integrated, hardened, operated, or production-proven unless separate evidence says so.

Warrantor is best understood as a monorepo of security-oriented reference libraries, schemas, CLIs, and demonstrations—not yet as one installable authority plane. The design is unusually comprehensive; the runtime story is fragmented. That distinction explains why the repository can contain substantial code and hundreds of tests while the production verdict remains no-go.

Architecture verdict

Substantive and differentiated

The trust-core, authority envelopes, signed evidence, policy/evaluation, containment, provenance, confidential-compute, federated-learning, incident, and observability concepts form a coherent north star. Source is not merely empty scaffolding: all four languages contain meaningful behavior and tests.

Operations verdict

Not enterprise ready

Core workflows frequently stop at in-memory, mock, synthetic, or health-only boundaries. The primary MCP bridge can convert downstream failures into successful mock results. CI and conformance contain skip/suppress paths. Helm appears structurally invalid before cluster testing.

Completion boundary

This audit establishes repository state on one Windows/WSL/Docker development host. It is not evidence of GPU/TEE attestation, SPIRE federation, Kubernetes enforcement, cloud KMS/HSM operation, Rekor transparency, multi-region durability, published packages, signed images, or adversarial resilience. Those require dedicated environments and retained evidence.

02 · Scope and method

Claims were graded by evidence tier.

The audit deliberately separates documentation coverage, source presence, local execution, integration proof, and production evidence. Passing a lower tier cannot satisfy a higher one.

Tier 1 · Declared

Roadmaps, reconciliation tables, RFCs, README statements, task markers, manifests, and release claims. Useful for intent; insufficient for behavior.

Tier 2 · Implemented

Source-level paths, validation, cryptography, error handling, tests, service wiring, and defaults. Demonstrates code; not a deployed system.

Tier 3 · Executed

Commands run from the repository on the evidence date, including Rust, Python, Go, TypeScript, Buf, Docker Compose, conformance, and documentation gates.

Tier 4 · Integrated

Multiple real components exchange authenticated data, exercise failure semantics, persist state, and enforce policy in a representative environment.

Tier 5 · Operated

Load, upgrade, rollback, backup/restore, HA, observability, SLO, incident, tenancy, and disaster-recovery evidence from a durable deployment.

Tier 6 · Assured

Threat-led adversarial testing, independent cryptographic and isolation review, reproducible signed releases, and control-to-evidence traceability.

Scope covered

  • Repository catalogue, reconciliation arithmetic, source layout, build metadata, test declarations, task/deferred markers, Dockerfiles, Compose, Helm, workflows, Make targets, specifications, schemas, vectors, SDKs, CLIs, and UI workspaces.
  • All 49 entries claimed as shipped, the five other implementable canonical IDs, and P1–P12.
  • Developer onboarding, packaging, API consistency, language parity, local workflow, error semantics, framework integration, and test ergonomics.
  • Enterprise identity, tenancy, least privilege, cryptographic key custody, policy enforcement, audit durability, observability, availability, compliance, supply chain, deployment safety, and operations.
  • Current official signals for MCP, A2A, OWASP agentic security, NIST AI RMF, EU AI Act, OpenTelemetry, SLSA, Sigstore, SPIFFE/SPIRE, C2PA, and CycloneDX.

Limitations

No external registry, remote Git host, cloud account, production cluster, confidential GPU, TEE hardware, HSM/KMS, enterprise identity provider, SIEM, or Rekor deployment was supplied. Helm was statically inspected because the Helm CLI was not installed. Network-facing penetration testing, performance benchmarking, formal verification, dependency-CVE scanning, and legal certification were outside this evidence run.

04 · System model

A persuasive control-plane decomposition.

The conceptual layering is one of the repository’s strongest assets. The weakness is not the taxonomy; it is the lack of a single enforced runtime path through it.

Agent interface

MCP server, MCP gateway, console, arena, SDKs, agent wrapper, CLI.

Problem: outdated MCP lifecycle and synthetic fallbacks.

Authority & policy

Trust core, authority spec, identity, policy compiler, eval guard, kill switch, vault, egress.

Problem: enforcement and key custody stop at adapters.

Evidence & assurance

Flight recorder, provenance, SBOM, tamper scan, training guard, safe eval, adversarial and compliance suites.

Problem: durable append-before-execute path is not integrated.

Execution & confidentiality

Open serve, runtime bridge, proxy, tenant guard, GPU/TEE attestation, confidential fabric.

Problem: production backends and attesters are mostly pending.

Operations & federation

Federated learning, DP, edge/fleet controls, metrics, incidents, sovereign stack, cloud plane.

Problem: health containers do not form an operated platform.

The required native-agent request path

  1. Authenticate the caller and workload with an enterprise identity mapped to a SPIFFE workload identity and tenant.
  2. Resolve delegated authority from a signed, audience-bound, time-bound grant with revocation and replay protection.
  3. Validate the tool/agent contract using versioned schemas and negotiated capabilities.
  4. Evaluate policy and budgets against the requested tool, data classification, egress destination, cost, and risk.
  5. Precommit durable evidence before side effects, then execute through a real enforcement point.
  6. Attest the execution environment where required and bind evidence to workload, model, code, and artifact identities.
  7. Observe, revoke, and recover with traces, signed incident events, kill propagation, idempotency, and rollback.

Warrantor has components corresponding to nearly every box. It does not yet demonstrate this chain as one fail-closed transaction. Today a developer can call libraries independently, while the MCP façade may return plausible success when the underlying control is unreachable.

Cross-cutting observation

The repository’s breadth is real: approximately 25,744 implementation lines were found across 20 Go, 42 Python, 30 Rust, and 4 TypeScript source files after excluding tests, targets, and generated dependency trees. The central risk is not “there is no code”; it is inconsistent depth, weak integration, and claims that collapse library readiness into platform readiness.

Protocol engineering gaps common to P1–P12

Normative wire behavior

Version negotiation, canonical encoding, cryptographic algorithm identifiers, extension rules, unknown-field behavior, maximum sizes, error codes, time/replay semantics, and downgrade resistance.

Executable conformance

Positive, negative, adversarial, boundary, canonicalization, compatibility, and multi-language vectors; validators that fail when a required implementation is unavailable.

Lifecycle governance

Schema registry, semantic versioning, compatibility policy, change-control body, security disclosure, deprecation window, IANA-style registries, reference implementations, and independent TCK results.

Broken documentation link

The protocol README points to proto/aumos/protocols/v1/aae.proto; that file does not exist. The protobuf README also describes evidence/protocol layouts that are absent, while buf.gen.yaml generates Rust only despite cross-language claims.

Native agent environment fit

MCP

Immediate modernization required

The server advertises 2024-11-05 and implements initialize/session state. The official MCP 2026-07-28 revision moved to a stateless core, header-based routing, server/discover, MRTR resilience, and extension-based Tasks/authorization. Migration must also remove every “successful mock on downstream failure” path.

A2A

Specification is not implementation

P10 does not implement the current A2A v1.0 semantic model, Agent Cards, tasks, messages/artifacts, multiple bindings, or version negotiation. Warrantor should complement MCP tool access with a real A2A client/server and map authority/evidence into A2A extensions.

Agent SDKs

No native adapters found

No first-class adapter was found for OpenAI Agents SDK, Google ADK, Microsoft Agent Framework, LangGraph/LangChain, or similar orchestrators. Generic HTTP/MCP access is valuable, but enterprises need maintained middleware for identity, policy, traces, approvals, and evidence.

Provider switching

Abstractions exist; parity does not

open-serve-kit and bridge-rt model provider/runtime switching, but the integrated environment defaults to mock. Streaming, tool calls, multimodal content, structured output, usage accounting, cancellation, and error parity need a provider conformance suite.

Deployment plane findings

Docker Compose

Seventeen services parse. Defaults include mock inference and standalone/mock MCP behavior. Multiple Dockerfiles compile a library then create a tiny inline health server; a healthy container can therefore say nothing about the advertised component function.

Helm

The shared templates treat an alternating Helm list as a map, likely failing render. Empty registry values can produce leading-slash image names. Probe ports do not reliably match generated health servers. There are no NetworkPolicy, RBAC/service-account, Secret, PVC, Ingress, StatefulSet, or usable PDB templates.

Configuration safety

mTLS and persistence default off, open-serve-kit defaults to mock, and some infrastructure uses mutable latest tags. A production profile must be explicit and reject these states before startup.

10 · Prioritized findings

What blocks a truthful production claim.

Severity reflects the combination of exploit/assurance impact, likelihood, and how directly the condition invalidates platform claims. IDs are local to this audit.

Critical
AUD-001

MCP returns success-shaped mocks when controls fail

Connected-mode handlers catch downstream errors and return plausible data for identity, flight recorder, attestation, evaluation, credential, SBOM, and related tools. The kill-switch fallback can report triggered: true. A network outage or broken control service can therefore look like a successful security decision.

Evidence: typescript/aumos-mcp-server/src/index.ts, fallback blocks around identity, evidence, attestation, eval, kill, vault, installation, SBOM, and evaluation handlers.

Fix: Separate explicit demo adapters from production adapters at construction time; production must fail closed with typed JSON-RPC errors, no fabricated IDs/evidence, and an audit event for control unavailability. Add fault-injection tests asserting zero success responses.

Critical
AUD-002

Green gates can mean “nothing meaningful ran”

The conformance runner succeeds when no verifiers are available. Make targets suppress failing Rust, Go, npm, docs, and conformance commands. CI’s protobuf-breaking check is warning-only. The main workflow omits Go and TypeScript and tests only one Python project.

Evidence: tools/conformance/run.sh, root Makefile, .github/workflows/ci.yml.

Fix: Define required lane/tool matrices, fail on missing executors or zero discovered tests/vectors, remove || echo from required gates, and publish signed machine-readable results.

Critical
AUD-003

Deployment health is decoupled from functional behavior

Several Docker images are library builds with an inline health-only server. Compose can become green without authority, evidence, tenant, sovereign, or cloud functionality being callable. This creates a false readiness signal at the exact boundary operators rely on.

Evidence: 16 Dockerfiles and 17-service docker-compose.yml; generated health-server patterns in multiple Rust/Go images.

Fix: Build real service binaries with authenticated readiness probes that validate required dependencies. Add an E2E transaction that traverses identity → authority → policy → evidence → execution → revocation.

High
AUD-004

The current correctness baseline is red

Two Rust tests fail, strict Clippy fails, one Python project suite fails, the root Python command cannot collect, and TypeScript lint cannot launch. Security-sensitive failures cannot be normalized as documentation drift.

Evidence: live ledger in §03.

Fix: Repair semantics, not just assertions; lock the expected Merkle construction against vectors, define exfil-finding aggregation, make harness commands platform-neutral, install/configure ESLint, and enforce one hermetic root test command.

High
AUD-005

MCP and A2A interoperability are behind the current ecosystem

MCP is fixed to the 2024 lifecycle; the gateway forwarding path is explicitly synthetic. P10 is a local CDDL record, not an A2A v1.0 implementation. Current agent runtimes cannot rely on discovery, negotiated capabilities, tasks, streaming, auth, or standard state behavior.

Evidence: MCP_PROTOCOL_VERSION = '2024-11-05'; mcp-gateway sets stubbed: true; P10 assets.

Fix: Implement current official SDKs/protocols, preserve Warrantor authority/evidence via extensions, and test against independent clients/servers and official compatibility suites.

High
AUD-006

Protocol documentation exceeds wire-level reality

Twelve protocols have CDDL, but CDDL is not validated; most lack bindings and all lack dedicated conformance vectors. Several schemas omit versioning, signer identity, audience/freshness, canonical signing rules, lifecycle, and error behavior.

Evidence: specs/protocols, proto, testvectors, buf.gen.yaml.

Fix: Establish a protocol working group, freeze shared envelope primitives, generate four-language bindings, add adversarial vectors for every protocol, and require two independent implementations before stable status.

High
AUD-007

Control components do not yet enforce the physical side effect

Kill, egress, tenant isolation, fleet enforcement, attestation, vault custody, and policy distribution stop before real infrastructure. Recording intent is valuable, but cannot contain a rogue or compromised agent.

Evidence: R3/R7/N4/F3/F4/C1/R4 task markers and mock adapters.

Fix: Prioritize one reference enforcement stack—Kubernetes + SPIRE + service mesh/CNI + cloud KMS—then measure fail-closed behavior and kill propagation under partition and compromise.

High
AUD-008

Helm is not a credible production installer

The templates likely cannot render correctly due to list/range construction, and the chart lacks fundamental security/state/availability resources. Helm lint itself could not be run in this environment.

Evidence: deploy/helm/aumos/templates/{deployments,services,hpa}.yaml and values.yaml.

Fix: Replace the component list with a values map or named templates; add schema validation, chart tests, kind-based E2E, RBAC, NetworkPolicy, secrets, security contexts, storage, PDB, upgrade and rollback tests.

High
AUD-009

Supply-chain claims lack published, verifiable outputs

Workflows describe SBOM, provenance, and release behavior, but the checkout has no remotes/tags and no retained signature, in-toto, or SBOM artifacts. Actions are tag-pinned rather than commit-SHA pinned; several workflow steps ignore failure.

Evidence: .github/workflows, Git metadata, absent release artifacts.

Fix: Pin actions by digest/SHA, lock all ecosystems, generate CycloneDX 1.7 ML-BOMs and SLSA v1.2 provenance, sign with Sigstore, verify before deploy, and retain a public verification bundle.

High
AUD-010

No durable, available evidence and control-plane data layer

Core assurance depends on keys, policies, revocations, budgets, audit records, provenance, incidents, and tenancy state. The repository does not define an operational data architecture with consistency, backup/restore, retention, migration, HA, and disaster recovery.

Evidence: in-memory/library implementations, persistence disabled by default, no PVC/StatefulSet/database migrations in the deploy plane.

Fix: Publish data contracts and consistency requirements per service; implement encrypted stores, transactional outbox/idempotency, migrations, backup/restore drills, tenant deletion/export, and recovery objectives.

Medium
AUD-011

Model SBOM output trails the current format

S4 and MCP mocks emit CycloneDX 1.5. CycloneDX 1.7 and its ML-BOM capability are current, and Warrantor’s custom AI properties are not shown to validate or interoperate.

Evidence: python/model_sbom and typescript/aumos-mcp-server.

Fix: Upgrade to validated 1.7, map model/dataset/prompt dependencies to the ML-BOM model, attach hashes/licenses/provenance, sign the BOM, and add external-tool round trips.

Medium
AUD-012

Status documents are not generated from evidence

Phase, catalogue totals, test counts, release status, and “no stubs” claims conflict. Stale critical-analysis findings also predate later source fixes.

Evidence: README, reconciliation matrix, final verification report, changelog, current source/tests.

Fix: Create a machine-readable component registry and evidence manifest. Generate status pages from it; attach command, commit, toolchain, timestamp, environment, result, and artifact digest to every readiness claim.

Historical critical findings: source-level closure, not production proof

The 6 August critical analysis predates the later C1–C7 repair commit. Current source reflects repairs for deterministic/canonical signing, length-delimited hashing, evaluation-result binding, nonce validation, audience enforcement, signed-envelope validation, and conservative government acknowledgement. These should be retained as regression tests and independently reviewed; they should not remain listed as open current defects, nor be upgraded to production assurance without integration evidence.

12 · Remediation roadmap

Concentrate breadth into one trusted path.

The fastest route to credibility is not implementing more catalogue entries in isolation. It is making one vertical slice real, fail-closed, observable, and reproducible—then expanding.

P0 · 0–14 days

Restore truth and deterministic gates

Fix Rust, Python, and TypeScript quality failures. Make root test orchestration hermetic. Delete failure suppression from required gates. Require non-zero verifier/language/vector counts. Correct the catalogue to 54 + 12 and generate status from an evidence manifest.

Exit: clean checkout; one command produces zero failures; machine-readable evidence lists exact tests/tools/commit; documentation claims match it.

P0 · 0–21 days

Remove false-success security behavior

Split demo and production dependency graphs. Production MCP/gateway paths return typed failures when identity, policy, evidence, attestation, kill, vault, or evaluation controls are unavailable. Remove synthetic forwarding. Add outage, timeout, partial-write, and replay tests.

Exit: fault injection proves no fabricated success, ID, audit receipt, attestation, credential, or kill acknowledgement.

P1 · 2–6 weeks

Build one functional control-plane slice

Choose Kubernetes + SPIRE + a durable SQL/event store + cloud KMS as the reference. Implement I2, R1, R8, real E1 precommit, real R3/R7/N4 enforcement, and one non-mock inference backend. Ship real services, not health wrappers.

Exit: an authenticated agent tool call is delegated, policy/budget approved, durably precommitted, executed, traced, and revocable under network faults.

P1 · 3–8 weeks

Modernize agent interoperability

Implement MCP 2026-07-28 and A2A v1.0 using official SDKs. Define Warrantor extensions for authority, evidence, budget, and attestation. Publish OpenAI Agents SDK and at least one other ecosystem adapter.

Exit: independent current clients pass discovery/auth/task/streaming/resume/error tests; A2A interop works across two independent implementations.

P1 · 4–10 weeks

Turn protocols into products

Repair P1–P12 semantics, shared envelope, registries, errors, and versioning. Validate CDDL in CI. Generate Rust/Python/Go/TypeScript bindings. Add positive/negative/adversarial vectors and two-implementation compatibility gates.

Exit: every protocol has normative schemas, vectors, generated bindings, reference implementation, compatibility policy, and a non-vacuous TCK.

P2 · 6–12 weeks

Make deployment an enforceable product boundary

Repair/refactor Helm, add Kubernetes security/state/availability resources, pin images, require mTLS and persistence, build readiness against real dependencies, and add kind-based install/upgrade/rollback/backup tests.

Exit: clean-cluster install and upgrade survive pod/node/database faults; tenant isolation and kill/egress enforcement are measured.

P2 · 8–16 weeks

Produce verifiable releases

Lock dependencies, pin CI actions, build reproducibly, generate CycloneDX 1.7 ML-BOMs, SLSA v1.2 provenance, signatures and transparency proofs. Add artifact admission and revocation.

Exit: a third party can verify source → builder → package/image → deployment with offline instructions and negative tamper tests.

P3 · 12–24 weeks

Prove enterprise operation

Load/soak/chaos, multi-region/sovereign modes, SLOs, capacity/cost model, DR, incident drills, independent security/crypto/isolation audits, EU/NIST evidence packs, and customer reference deployments.

Exit: retained operational evidence supports bounded production claims for named configurations—not a blanket “feature complete” label.
