1Executive Summary ¶

This is the operational deployment plan for the AumOS platform (github.com/MuVeraAI) — the reference implementation of the open authority and evidence layer for autonomous systems. It is the most operationally detailed document in the portal: every dollar of cloud credit is allocated to a phase and a component, every component gets a deploy command, and every phase ends with a concrete verification step an engineer can run. The goal is to turn the existing v1.0.0 codebase (49 components, 12 protocols, 691 tests) into a fully running cloud demonstration in 90 days.

Deployment philosophy — cloud-native, multi-cloud, credit-optimized

Three principles drive every allocation decision in this document:

  • Cloud-native. Every component runs as a managed service, container, or serverless function — no pet VMs, no manual configuration drift. AKS and EKS host the long-running services; Modal hosts the bursty workloads; confidential VMs host the trust boundary.
  • Multi-cloud. No single cloud satisfies AumOS's confidentiality, GPU, and serverless requirements simultaneously. Azure is the only cloud with GPU-accelerated confidential VMs (NCCads H100 v5); AWS Nitro Enclaves are CPU-only (no GPU pass-through); Modal is the only per-second-billed serverless GPU. The deployment deliberately spans all three so each component runs where its constraint is best met.
  • Credit-optimized. Every dollar is assigned before it is spent. Spot/reserved pricing is used wherever the workload tolerates interruption; serverless is used wherever the workload is bursty; the cheapest confidential VM that satisfies the security boundary is chosen for each role.

Why Azure is primary — the GPU-in-TEE constraint

The single architectural fact that drives the entire allocation is this: only Azure offers a GPU inside a hardware confidential VM (NCCads H100 v5, AMD SEV-SNP based). AWS Nitro Enclaves explicitly do not support GPU pass-through (see the Nitro Enclave docs). Because AumOS's headline invariant is "attested inference on a real GPU," the H100 confidential VM must live on Azure. Everything else is placed to minimize cost around that fixed point.

Why Modal for evaluation — the per-second advantage

Evaluation and adversarial-attack workloads are inherently bursty: HELM runs a benchmark suite in tens of minutes, then sits idle for hours; a red-team attack batch spikes then stops. On a reserved VM you pay for the idle. Modal's per-second billing means a 14-minute HELM run costs ~$0.26 on A10G, not the $26.40 a 24-hour reserved GPU would cost. Over 90 days this is the difference between evaluation fitting in $270 and evaluation blowing the entire budget.

Cross-cloud trust & networking

  • Identity. A single SPIFFE trust domain (spiffe://aumos.prod) spans all three clouds. trust-core (T1) on the Azure DC-series VM is the SPIRE trust bundle anchor. Every workload on AKS, EKS, and Modal holds an X.509 SVID minted from that bundle; mTLS is mandatory between every pair of services.
  • Networking. Azure ↔ AWS is peered (VNet peering + Transit Gateway) for the operator-plane callbacks. Modal egresses over the public internet but every request is mTLS-authenticated; no Modal function is reachable without a valid SVID.
  • Keys. Production signing lives in Azure Key Vault (Managed HSM). AWS KMS holds a backup key for disaster recovery. No private key material ever leaves an HSM.
  • Evidence. All signed artifacts (model signatures, attestation envelopes, eval results, incident records) land in Azure Cosmos DB through trust-core, which countersigns each entry.

4Phase-by-Phase Deployment Plan (90 days) ¶

The four phases are strictly sequential — each phase's verification gate is a precondition for the next. Costs are ceilings, not estimates; the plan spends up to the ceiling and no more.

Phase 1 — Foundation

Days 1–14 ~$200 Azure + ~$50 AWS

Theme: stand up the trusted core on a CPU-only confidential VM, wire real KMS signing, and prove the evidence pipeline end-to-end with a single signed compliance-report. No GPU yet — this phase is cheap and de-risks everything downstream.

Tasks

  1. Provision Azure DC-series confidential VM (Intel TDX), Ubuntu 24.04, with the github.com/MuVeraAI component binaries deployed via defstack.
  2. Deploy trust-core (T1) on that VM as a systemd unit, plain HTTP behind an Azure internal load balancer (mTLS terminates at the mesh, not the LB).
  3. Deploy agent-identity (I1) alongside trust-core (Go binary, same VM). It issues the first SPIFFE SVIDs for itself and trust-core.
  4. Provision Azure Key Vault with Managed HSM; create the production Ed25519 key aumos-prod-ed25519-v1.
  5. Provision AWS KMS; create the backup Ed25519 key aumos-backup-ed25519-v1.
  6. Deploy flight-recorder (E1) alongside trust-core; point its sink at Azure Blob Storage.
  7. Wire defstack-cli (X1) to install and verify all Phase-1 components; point it at the real Key Vault backend.
  8. Deploy credential-vault (R4) with the Azure Key Vault backend (primary) and AWS Secrets Manager backend (fallback).

Key commands

# Provision the foundation (terraform — see §7)
cd deploy/terraform/azure && terraform init && terraform apply \
  -var="phase=foundation" -var="vm_sku=Standard_DC2s_v3"

# Install Phase-1 components on the confidential VM
defstack install trust-core agent-identity flight-recorder credential-vault \
  --backend keyvault://aumos-prod-ed25519-v1

# Register the AWS backup signer
defstack signer add --id aws-backup --backend kms://aumos-backup-ed25519-v1
Verification gate

defstack compliance-report --format json > report.json produces a real, Key-Vault-signed JSON document whose signature verifies against the Azure Key Vault public key, with trust-core, agent-identity, flight-recorder, and credential-vault all listed as verified against real backends. If the signature does not verify, Phase 2 does not start.

Phase 2 — Confidential Inference

Days 15–30 ~$2,500 Azure (H100 hours)

Theme: boot the GPU confidential VM, install the GPU stack inside the TEE, load a real model, and produce a real chat completion wrapped in a real attestation envelope. This is the single most expensive phase and the entire reason Azure is the primary cloud.

Tasks

  1. Provision the NCCads H100 v5 confidential GPU VM (AMD SEV-SNP). Single GPU is sufficient for Llama-3-8B.
  2. Inside the confidential VM: install NVIDIA drivers, CUDA 12.x, and NVTrust (the confidential-computing attestation agent).
  3. Deploy open-serve-kit (N1, Go) as the inference proxy — the OpenAI-compatible front door.
  4. Deploy bridge-rt (N2, Python) as the backend abstraction layer; configure it for vLLM on the H100 (Ollama as fallback).
  5. Deploy tee-serve (C1-4, Go) as the TEE sidecar that measures the running process and exposes the attestation endpoint.
  6. Deploy attesta-flow (C1-2) orchestrator inside the confidential VM; reuse the existing attesta-flow/terraform/main.tf module (see §7).
  7. Deploy cuda-gram (C1-3, Python) in real-attestation mode (not mock): it queries the H100 attestation through NVTrust.
  8. Deploy eval-guard (R5, Rust) to attest the sandbox boundary before any inference is allowed.
  9. Deploy inference-proxy (N3, Rust) in front of open-serve-kit; it validates the attestation envelope on every request.
  10. Pull Llama-3-8B from HuggingFace into the VM; load it into vLLM.

Key commands

# Boot the confidential GPU VM
cd deploy/terraform/azure && terraform apply \
  -var="phase=inference" -var="vm_sku=Standard_NCCads_H100_v5_1_2_1024"

# Inside the VM: install the GPU stack inside the TEE
defstack install gpu-stack --driver 550 --cuda 12.5 --nvtrust latest

# Deploy the inference plane
defstack install open-serve-kit bridge-rt tee-serve attesta-flow \
                cuda-gram eval-guard inference-proxy \
  --backend vllm --model meta-llama/Meta-Llama-3-8B \
  --attestation real

# Pull + load the model
huggingface-cli download meta-llama/Meta-Llama-3-8B --local-dir /models/llama3-8b
defstack model load /models/llama3-8b
Verification gate

Send a real chat completion request to inference-proxy:

curl -s https://inference.aumos.prod/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"llama3-8b","messages":[{"role":"user","content":"Say hello"}]}' \
  | defstack verify-attestation --stdin

The response must contain (a) a real Llama-3 completion, and (b) an attestation envelope whose GPU attestation report verifies against the H100's measurement register (not a mock). cuda-gram must report attestation: verified, source: h100-cc.

Phase 3 — Supply Chain + Evaluation

Days 31–60 ~$1,500 Azure + ~$500 AWS + ~$200 Modal

Theme: build the provenance chain for the deployed model, run real evaluation and adversarial attacks, and gate releases on compliance. This is the phase where the EU AI Act Article 55 obligations become demonstrable.

Tasks

  1. Deploy safe-tensors-pp (S1): download Llama-3-8B from HF Hub, sign it with the Azure Key Vault key, store the signed artifact in Blob.
  2. Deploy provena-chain (S2): record the model lineage edge HF Hub → sign → deploy.
  3. Deploy model-sbom (S4): generate a CycloneDX SBOM with the AI extensions for Llama-3-8B (weights hash, license, dataset refs).
  4. Deploy data-provenance-kit (S5): record a sample dataset's lineage.
  5. Deploy tamper-scan (S8): scan the signed weights for anomalies (entropy outliers, known-bad hash prefixes).
  6. Deploy safe-eval (A1) on Modal: run HELM and LM-Eval benchmarks against the served model (A10G burst).
  7. Deploy adversaria (A2) on Modal: run prompt-injection and jailbreak attack suites.
  8. Deploy agentsec-lab (A5) on Modal: run the agentsec prompt-injection scenario pack.
  9. Deploy bias-sentinel (A3): run bias and copyright checks.
  10. Deploy comply-gate (A4): install the CI/CD compliance gates (every PR must pass).
  11. Deploy kill-switch (R3): wire it to eval-guard + sentinel-trace + credential-vault so a failed gate can revoke a model.

Key commands

# Supply chain
defstack install safe-tensors-pp provena-chain model-sbom data-provenance-kit tamper-scan
safe-tensors-pp sign --model meta-llama/Meta-Llama-3-8B --key aumos-prod-ed25519-v1

# Evaluation + attacks (Modal burst)
modal deploy deploy/modal/safe_eval.py        # HELM + LM-Eval
modal deploy deploy/modal/adversaria.py       # prompt-injection + jailbreak
modal deploy deploy/modal/agentsec_lab.py     # agentsec scenarios
modal deploy deploy/modal/bias_sentinel.py    # bias + copyright

# Compliance gate + kill-switch
defstack install comply-gate kill-switch
defstack compliance-report --format json > report-phase3.json
Verification gate

defstack compliance-report produces a full report containing: (1) real model lineage (HF → sign → deploy, signed), (2) a real HELM evaluation result from Modal, (3) a real CycloneDX SBOM, (4) real adversaria attack results. Every artifact must be signed by the Key Vault key and verifiable. The report must map to all 8 EU AI Act Article 55 obligations (see portal § EU AI Act coverage).

Phase 4 — Multi-Tenancy + Edge + Federated

Days 61–90 ~$800 Azure + ~$450 AWS + ~$70 Modal

Theme: complete the architecture with the operator plane (AWS EKS), federated learning, edge simulation, the web console, and the MCP gateway — then run the headline end-to-end incident-response demonstration.

Tasks

  1. Deploy tenant-guard (N4) as a Kubernetes operator on AWS EKS; configure GPU-slice allocation for simulated tenants.
  2. Deploy fleet-marshal (F4) for OTA model updates; perform a canary rollout of a second model variant.
  3. Deploy fed-core (F1) + dp-crate (F2); run a 3-node demonstration federated training round with differential privacy.
  4. Deploy edge-sentinel (F3) as a simulated edge agent on the AWS G5.xlarge.
  5. Deploy the console (X7) as a web UI served from AKS, browser-accessible.
  6. Deploy the MCP gateway (X8) with a sample MCP server exposing AumOS evidence as MCP resources.
  7. Wire incident-exchange (X9), retro-spec-kit (X5), and metr-bridge (X6).
  8. Run the full incident simulation (see verification).

Verification gate — the headline demo

Inject a simulated prompt-injection attack through adversaria → kill-switch (R3) triggers and revokes the model slice → the event is recorded by flight-recorder (E1) into Cosmos DB → incident-exchange (X9) emits the incident record → retro-spec-kit (X5) analyzes root cause → metr-bridge (X6) exports a METR-format report. The entire chain must complete in under 60 seconds and every step must be signed. This is the demo shown in §10.
