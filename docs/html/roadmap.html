1Introduction & How to Read This Roadmap ¶

This document is the per-component roadmap for the Warrantor project (github.com/MuVeraAI). It covers all 49 implementable components across the seven domain groups and the 12 open protocols (P1–P12). It is the successor artifact to the stress-test audit: where that document diagnosed what is broken, this one schedules the fix, the hardening, and the long-arc feature work.

Read this first — the honest starting point

The repo advertises itself as "feature-complete at v1.0.0" with "691 tests passing." The stress test proved that framing is false: 7 Critical, 11 High, and 10 Medium findings sit on the cryptographic spine that is supposed to make the security invariants trustworthy. Every component below is therefore listed as v1.0 shipped but with critical fixes pending. Treat v1.0 as "reference-shape implementation with known breaks," not "deployable."

How to read each component entry

Every component gets a roadmap card with five time-boxed milestones:

  • Q3 2026 (now) — what actually exists in the tree today, including the specific finding IDs from the stress test that block it.
  • Q4 2026 — v1.1 (critical fixes + mock→real) — the cryptographic repair work and the swap of every mock backend for a real one. This is the gate that makes the security claims honest.
  • Q1 2027 — production hardening — observability (OpenTelemetry, /metrics), persistence (durable ledgers, HA), and the operational surfaces a v1.1 service needs.
  • Q2 2027 — ecosystem integration — OSAF working-group participation and the first wave of co-development partners building against each component.
  • Q3–Q4 2027 — v2.0 features — the items each component's RFC lists under "Non-Goals" that become goals once the v1.x spine is trustworthy.

Timeline philosophy — quarterly milestones, not dates

Warrantor plans in quarters, not calendar dates. Software-security work has irreducible uncertainty (a cryptographic repair can unlock three dependents or expose two more breaks), so we commit to milestone order and milestone scope, not to specific days. The rule is strict sequencing: v1.1 before v2.0, fixes before features, the cryptographic spine before everything that depends on it. A component may not start v2.0 feature work until its v1.1 critical fixes land and pass the expanded conformance suite. The Gantt in §2 makes the dependency order explicit.

Versioning contract

v1.0 = today's reference shape (shipped, with known breaks). v1.1 = critical fixes + real backends + expanded conformance; this is the first version whose security claims are auditable. v1.2–1.x = rolling production-hardening and ecosystem work. v2.0 = the RFC "Non-Goals" become goals. No component ships a 2.0 until its 1.1 critical fixes are merged.

Why every v1.1 lands in the same quarter (Q4 2026)

The critical fixes are not independent. C1 (canonical CBOR) is a prerequisite for every other cryptographic fix because every signature is computed over canonical bytes. Fixing T1 first and then waiting a quarter to fix T2 would ship a halfway state. So the v1.1 wave is one coordinated release: every spine component fixes its break in the same window, against the same repaired T1, and ships together through the expanded conformance gate.

The 49 components are grouped by the same seven domains used in the component reference. Within each domain, the most-depended-on component comes first, because its v1.1 unblocks the rest.

§3.1Trust Core / Identity / Authority

T1 rust trusted core
trust-core
rust/trust-core/
v1.0 shippedcritical fixes pending (C1, M6, M10)

The single authoritative implementation of every security invariant in Warrantor. Owns canonical CBOR, SHA-256 binary Merkle trees, Ed25519 signing/verification, and the cross-language golden vectors. Every other language consumes it via PyO3, napi-rs, and FFI. It is the keystone of the keystone — 14 dependents wait on its correctness.

Q3 2026
Shipped at v1.0 with 14 tests. Critical break C1: canonical.rs uses serde_cbor with no deterministic feature, so map keys are not sorted — two signatures can be produced for one payload. M6: signing key not zeroized on drop (missing zeroize feature). M10: Merkle orphan promotion is not second-preimage resistant (RFC 6962 requires re-hashing the lone node).
Q4 2026
v1.1. Migrate from deprecated serde_cbor to ciborium with explicit RFC 8949 §4.2.2 canonicalization (length-first then bytewise). Add a golden vector built from an unordered IndexMap so the determinism cannot regress. Enable ed25519-dalek/zeroize and a real Zeroize impl in SigningKeyWrapper::Drop. Re-hash the lone node in orphan promotion. This is the highest-priority fix in the entire project — it unblocks C2, C3, C6 and every downstream verifier.
Q1 2027
v1.2 harden. Land KMS/HSM backing (AWS KMS, GCP KMS, Azure Key Vault, YubiKey/PKCS#11) behind a KeyBacking trait so production keys never live in-process. Add clippy::pedantic + publish = false to the workspace. Add a /metrics surface and OTel span export for every sign/verify call. Add Sigstore Rekor transparency-log entry emission on every signature.
Q2 2027
Ecosystem. OSAF working-group submission of the canonical-CBOR + Ed25519 profile as the reference signing profile. First co-development partner: a cloud provider that adopts T1 as the signing root for its internal agent platform. Publish the golden-vector harness as a standalone repo so any language can self-certify.
Q3–Q4 2027
v2.0. Post-quantum signature hybrid (Dilithium3 + Ed25519, double-sign). BLS aggregate signatures for multi-approver AAEs (I-08). Verifiable random function for nonce-derivation in AAE/ABS. Threshold-signing mode for the credential-vault revoke path. These were RFC Non-Goals and become goals once the v1.1 spine is auditable.
T2 rust protocol P1
authority-spec
rust/authority-spec/
v1.0 shippedcritical fix pending (C6)

The normative reference validator for the Agent Authority Envelope (P1). Validates signature, expiry, side-effect class, consequential-action approval (I-08), and delegation depth. The structural checks are correct today; the signature-binding check is broken.

Q3 2026
Shipped at v1.0 with 9 tests. Critical break C6: validate(envelope, unsigned_canonical_cbor, options) verifies the signature over a byte buffer the caller supplies separately from the envelope. The validator never recomputes canonical bytes from the envelope's own fields, so the signature does not bind to the envelope contents. An attacker can pair any envelope with bytes that match a known signature.
Q4 2026
v1.1. Remove the unsigned_canonical_cbor parameter entirely. The validator reconstructs canonical bytes from the envelope itself (via the repaired T1 canonical_cbor) before verifying. Add a property test that signs an envelope, mutates one field, and asserts the mutated envelope fails validation. Depends on T1 v1.1 landing first.
Q1 2027
v1.2 harden. Add revocation-status checking (query the aumos.<domain>.revoked.v1 topic) as a first-class validation step. Add a policy hook so deployments can layer custom structural rules. OTel span per validation decision; metrics on accept/reject/expired/revoked.
Q2 2027
Ecosystem. Submit the P1 CDDL + JSON-Schema (completed in the protocol track) plus the repaired validator as the OSAF reference AAE validator. Co-development: a policy engine vendor embeds T2 as its AAE admission gate.
Q3–Q4 2027
v2.0. Delegated-attestation chains with proof-carrying delegation (>2 hops). Conditional-approval workflows (approve-then-act receipts). On-chain/ledger anchoring of the AAE root for regulated deployments. Selective-disclosure AAEs (zero-knowledge proofs over resources).

4Protocol Roadmap (P1–P12) ¶

The 12 open protocols are spec-only canonicals. They have no single language implementation; every relevant component consumes them. Their roadmap is a standards track, not a shipping track: spec → machine-checkable schema → conformance suite → OSAF working group → OSAF ratification → IETF RFC (for the three most load-bearing). Today only P1 has a CDDL + JSON-Schema; the rest are markdown sketches.

High-severity finding H4 governs this whole section

The stress test's H4: "No CDDL/JSON-Schema for 11 of the 12 protocols." Each P2–P12 spec file claims "normative schema lives at ... CDDL" but only P1 (specs/protocols/P1-aae.cddl and P1-aae.schema.json) actually exists. The Q4 2026 milestone for every protocol is therefore the same: produce the missing machine-checkable schema.

5Dependency Critical Path ¶

The order in which components must ship is not arbitrary. The cryptographic spine must be fixed first because every downstream verifier transitively inherits its breaks. The diagram below shows the four tiers: anything in a lower tier cannot be trusted until everything above it is at v1.1.

TIER 0 — THE CRYPTOGRAPHIC SPINE (must ship first; everything inherits these fixes) T1 trust-core ── C1 canonical CBOR fix ──▶ unblocks every signer/verifier T2 authority-spec ── C6 envelope-binding fix ──▶ unblocks every AAE consumer E1 flight-recorder ── C2 length-prefix fix ──▶ unblocks every AAR consumer S2 provena-chain ── C2 + M10 + H10 ──▶ unblocks every provenance consumer TIER 1 — THE IDENTITY & RUNTIME KEYSTONE (depends on Tier 0) I1 agent-identity ── C5 audience fix ──▶ unblocks R3, R4, N3, X7, X8, X10 (12 dependents) C1-1 nvtrust-bridge── C4 nonce fix ──▶ unblocks C1-2, C1-3, C1-5, F1, F3 A6 conformance ── H3 vector expansion ──▶ unblocks the v1.1 release gate itself TIER 2 — THE ENFORCEMENT & EVIDENCE LAYER (depends on Tier 1) R2 eval-guard ── C3 attestation binding ──▶ unblocks R1/R8 sandbox, P12 CAP R3 kill-switch ── C7 gov-API + H8 deadline ──▶ unblocks X9 incident, P9 AIX R4 credential-vault── H11 real revoke ──▶ unblocks N3, X8 N3 inference-proxy ── H7 mutex + M8 fail-closed ──▶ unblocks N1 serving TIER 3 — THE DOMAIN LAYER (depends on Tier 2; can develop in parallel) S1 S4 S5 S7 S8 S9 · A1 A2 A3 A4 A5 A7 A8 · N1 N2 N4 · F1 F2 F3 F4 X1 X2 X3 X4 X5 X6 X7 X8 X9 X10 X11 BLOCKED UNTIL TIER 0 LANDS: any v2.0 feature work, any OSAF submission, any "feature-complete" claim, any production deploy.
Why the spine comes first — a concrete example

If R4 credential-vault shipped its real-revoke fix (H11) before T1 fixed canonical CBOR (C1), then every credential it issued would still be signed over a non-deterministic encoding — the revocation would work, but the credential's signature would still be forgeable. The fix would be real; the security it provides would not be. This is why the tiers are strict.

7Summary ¶

This roadmap turns the stress test's 28 findings into a sequenced, six-quarter plan. The shape is simple: Q4 2026 fixes the cryptographic spine and swaps every mock for a real backend (v1.1); Q1 2027 hardens the result for production; Q2 2027 integrates it into the OSAF ecosystem; Q3–Q4 2027 builds the v2.0 features that were RFC Non-Goals. The 12 protocols move on a parallel standards track, with the three load-bearing ones (P1 AAE, P2 AAR, P6 AATM) targeting IETF RFC submission by the end of 2027.

Nothing in this document is conditional on optimism. The v1.1 fixes are scoped, the dependencies are explicit, and the critical path is one linear chain: fix T1, then everything that signs; fix T1's consumers, then everything that verifies; expand conformance, then declare v1.1. Only after that does the feature work begin. That discipline is the difference between a roadmap that ships and one that slides.

The one-sentence version

Warrantor today is 49 reference-shape components at v1.0 with a broken cryptographic spine; by Q4 2027 it is a hardened, standardized, ecosystem-integrated platform whose three core protocols are on the IETF track — provided the v1.1 critical-fix wave lands first, in order, with no exceptions.
