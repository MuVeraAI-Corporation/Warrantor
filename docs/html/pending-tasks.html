Executive Summary

AumOS ships 49 components at v1.0.0 with 691 passing tests across 4 languages. Every component implements real logic against well-defined interfaces — but many integrate with mock or stub backends for external systems that require infrastructure, credentials, or NDA-gated access. This document enumerates every pending integration, what exactly is needed, and how to verify each one is complete.

The "Task 03" Pattern

Each component's RFC defines an 8-task sprint. Tasks 01–02 (setup, MVP) and 07–08 (docs, release) are done. Tasks 03–06 (external integration, bindings, fuzz, release hardening) are the pending work. This document is the master index for all task-03 work across all 49 components.

Category 1 — NVIDIA GPU & Confidential Compute

What's needed

Item Specification Why
NVIDIA H100 or H200 GPU PCIe or SXM; 80GB HBM3; CC mode capable NVTrust attestation requires a real GPU. The MockBackend in C1-1 always returns "aumos-mock-attestation"; real GPU returns an attestation report signed by the GPU's hardware root of trust.
NVTrust SDK Accessed via NVIDIA Developer Program; C-callable library C1-1's Real backend (behind a feature flag) makes FFI calls into NVTrust. The SDK is NDA-gated and CANNOT be downloaded in CI.
CUDA 12.x toolkit v12.4+ Required by NVTrust; C1-2 cuda-gram links against CUDA libraries for GPU memory access during attestation.
Triton Inference Server v24.x (NGC container) N1 open-serve-kit routes to Triton as one of its backends. C1-4 tee-serve is a sidecar to Triton that terminates TLS in the TEE.
TensorRT-LLM v0.16+ (the breaking-change version N2 bridge-rt adapts for) N2 bridge-rt auto-detects the version and injects sampler_type=trtllm for v0.16+. Real verification requires running TRT-LLM with a real model.
vLLM v0.6+ N1 open-serve-kit's HTTPBackend can route to vLLM's OpenAI-compatible endpoint. N2 bridge-rt probes vllm --version.
Azure DC-series Confidential VM Standard_DC48ads_v5 (Intel TDX) or Standard_ND_H100_v5 (GPU + CC) C1-3 attesta-flow's Terraform provisions a confidential VM; the orchestrator runs inside the TEE. Real attestation requires Azure's Confidential VM attestation service.
AWS Nitro Enclaves Nitro Enclave on an EC2 instance with GPU attachment C1-3 attesta-flow's Terraform has an equivalent AWS module. Requires AWS Enclave CLI.
NVIDIA Jetson (for edge) Jetson Orin AGX or Jetson AGX Xavier F3 edge-sentinel runs on Jetson/EGX as a systemd service. The <5MB binary must be cross-compiled for aarch64.

Per-component integration checklist

C1-1 nvtrust-bridge

Current stateMockBackend returns deterministic mock attestation; Real backend stubbed behind a feature flag that is never enabled.
Integration step1. Obtain NVTrust SDK access. 2. Implement the FFI calls in src/lib.rs behind #[cfg(feature = "real-nvtrust")]. 3. Add nvtrust-sys crate as a build dependency (sys crate wrapping the C headers). 4. Wire the Real backend to call nvtrust_attest().
VerificationRun nvtrust-verify issue-mock → must return a real attestation report from the GPU (not "aumos-mock-attestation"). The verify subcommand must call NVTrust's nvtrust_verify() and confirm the report is signed by the GPU's hardware key.
Blocked onNVIDIA Developer Program access for NVTrust SDK

C1-2 cuda-gram

Current statePure-Python MockBackend mirrors C1-1's mock shape; the real path calls C1-1's Rust core via PyO3 (not ctypes).
Integration step1. Build the PyO3 binding from C1-1's Rust crate (maturin develop). 2. Replace MockBackend with NvTrustPyBackend that calls into the Rust core via PyO3. 3. Wire AttestationVerifier to use the real GPU attestation.
Verificationestablish_session(NvTrustPyBackend()) on a real H100 must return a CCSession with verified=True and gpu_model="H100".
Blocked onC1-1 real NVTrust + PyO3 cross-compilation (non-trivial on Windows; needs Linux)

C1-3 attesta-flow

Current statePipeline runs 5 stages with a MockHardwareAttestor; Terraform module is written but not apply'd.
Integration step1. terraform init && terraform apply on Azure with the DC-series confidential VM. 2. Install AumOS + NVTrust inside the VM. 3. Replace MockHardwareAttestor with RealHardwareAttestor that calls C1-2. 4. Wire infer_fn to call N1 open-serve-kit via HTTP.
Verificationrun_batch() must produce a PipelineAttestation with gpu_model="H100" and a real attestation hex (not "aumos-mock-attestation").
Blocked onAzure subscription + DC-series VM availability + C1-1/C1-2 real NVTrust

C1-4 tee-serve

Current stateTeeProxy forwards HTTP to an upstream via Unix Domain Socket; MockAttestationProvider returns synthetic attestation; TeeAttestationProvider stubbed.
Integration step1. Deploy inside a confidential container (CoCo or Trustee). 2. Wire TeeAttestationProvider to read the CoCo attestation document. 3. Set the upstream to Triton's Unix socket. 4. Sign attestation envelopes with T1 trust-core's key.
VerificationCurl through tee-serve → response must carry an AttestationEnvelope with a valid signature that verifies via T1 trust-core. Overhead must be <2ms per request (benchmark).
Blocked onConfidential Containers infrastructure (CoCo/Trustee) + Triton deployment

N1 open-serve-kit

Current stateMockBackend echoes the prompt; HTTPBackend is fully implemented but untested against a real backend.
Integration step1. Deploy vLLM or Triton on a GPU. 2. Start open-serve-kit with --backend vllm --backend-url http://localhost:8000. 3. Send a real chat completion request through the proxy.
Verificationcurl -X POST http://localhost:8443/v1/chat/completions -d '{"model":"llama-3-8b","messages":[{"role":"user","content":"hello"}]}' must return a real completion from the model.
Blocked onGPU + model weights deployment

N2 bridge-rt

Current stateBackend selection logic + TRT-LLM v0.16 sampler_type adaptation fully implemented and tested against mock backends.
Integration step1. Install TRT-LLM, vLLM, and Ollama. 2. bridge-rt probe --json should report all three as available. 3. bridge-rt generate --model llama-3-8b --prompt "hi" should return a real completion from TRT-LLM (the highest-preference backend).
VerificationThe sampler_type_adapted field in the response must be true when TRT-LLM >= 0.16 is detected.
Blocked onGPU + TRT-LLM/vLLM/Ollama installation

Dependency Order for Integration

The optimal order to integrate external infrastructure, respecting component dependencies:

  1. AWS KMS (item 2) → unblocks T1 trust-core KMS → unblocks S1, S2, E1 signing
  2. SPIRE (item 3) → unblocks I1 real → unblocks R2, R3, R4 wire-off-mock
  3. GPU + NVTrust (item 1) → unblocks C1-1, C1-2 → unblocks C1-3, C1-4, C1-5
  4. Rekor (item 5) → unblocks T1 notarize, S2 checkpoint anchoring
  5. OTel + Kafka + SIEM (item 6) → unblocks E1 real OTLP, I1 revocation fan-out
  6. vLLM/Triton/TRT-LLM (item 9) → unblocks N1, N2 → unblocks A1, A2 (they need a target model)
  7. HELM/garak/PyRIT (item 8) → unblocks A1, A2 real evaluation
  8. K8s + GPU operator (item 7) → unblocks N4, F4 controller deployment
  9. Vault (item 4) → unblocks R4 real credential brokering
  10. Linux eBPF + Falco/Tetragon (items 10-11) → unblocks R2, R7, S6 kernel enforcement
