1.Introduction — the research opportunity

AumOS is a unified, reproducible platform for AI security research. Its 49 components and 12 protocols span the full surface area of secure autonomous-agent computing: cryptographic authority and delegation, confidential computing and GPU attestation, differentially-private federated training, signed model provenance and software bills of materials, sandbox containment and kill switches, egress filtering and exfiltration prevention, retrospective incident analysis, and conformance-driven protocol testing. Few research artifacts in this domain combine a working multi-runtime implementation (Rust, Go, Python, TypeScript) with a normative specification plane and a reproducible evaluation harness in a single body of work.

This roadmap identifies 24 peer-reviewed research papers and 6 industry whitepapers that AumOS's implementation directly enables. Each paper is mapped to (a) the specific AumOS components and protocols it builds on, (b) the real, citable prior work it extends, (c) a concrete experimental setup using AumOS as the reference platform, and (d) a target top-tier venue with a realistic submission timeline.

The strategic value of this roadmap is that AumOS converts a research community problem — the absence of a shared, open, reproducible experimental platform for secure AI agents — into a research community asset. Each paper can cite real related work, use AumOS as the experimental platform, ship reproducible artifacts (Docker images, conformance vectors, benchmark scripts), and produce results that other groups can extend. This is the substrate that makes a coherent publication program possible rather than a series of one-off workshop papers.

Research Thrust 1

Cryptographic Authority for Autonomous Agents

Builds on: T1 trust-core · T2 authority-spec · I1 agent-identity · P1 AAE (Agent Authority Envelope) · P2 AAR (Agent Action Receipt)

This thrust addresses the central unsolved problem of agentic AI security: how does a relying party verify that an action was performed by an agent acting within a cryptographically-scoped delegation from a principal? The existing literature frames this as an open problem — the Cryptographically Verifiable Authorization for Autonomous AI Agents preprint (arXiv:2607.21325, 2026) explicitly calls for envelope formats and intersection semantics that AumOS's T1/T2/I1 components and P1/P2 protocols already specify and reference-implement. The four papers below convert that specification into peer-reviewed contributions.

Paper 1

Verifiable Agent Authority: A Cryptographic Framework for Delegated AI Agent Permissions

Abstract sketch

Autonomous AI agents increasingly act on behalf of human principals — reading mail, moving money, calling APIs — yet the relying parties that receive these agents' requests have no cryptographic mechanism to verify the scope, provenance, and freshness of the delegation that authorized the action. We present the Agent Authority Envelope (AAE), a signed, audience-bound, time-scoped delegation token that binds a principal's identity to a constrained set of agent capabilities, attested host configurations, and revocation state. We formalize the AAE verification contract as an intersection of principal-granted, host-attested, and protocol-declared permission sets, prove that the contract is sound under a Dolev-Yao attacker model with compromised-agent oracles, and show that the reference implementation in AumOS's trust-core and authority-spec components satisfies the contract across Rust, Go, Python, and TypeScript runtimes. We further demonstrate that AAE closes the gap identified by recent surveys — the SoK on Agentic AI (USENIX Security 2026) and the Cryptographically Verifiable Authorization preprint — which both note the absence of any deployed, standardized, cross-language delegation envelope for agents.

Novel contribution

(1) A formal intersection semantics for delegated agent authority that unifies capability-based, attestation-based, and policy-based permission models into a single verification contract. (2) A canonical, cross-language encoding of the AAE that produces byte-identical signed artifacts in four runtimes — addressing the canonicalization gap that the AumOS critical analysis (finding C1) shows is the root cause of broken cross-language signing in prior prototypes. (3) The first open, reproducible reference platform against which the broader community can evaluate proposed agent-delegation schemes.

Paper 2

Cross-Language Canonical Signing for Multi-Runtime Agent Systems

Abstract sketch

A recurring failure mode in distributed cryptographic systems is that two implementations of the "same" signing scheme produce different byte encodings and therefore different signatures, silently breaking verification across language boundaries. This problem is acute for AI agent infrastructure, where a delegation issued by a Rust principal must verify in a TypeScript relying party and a Go agent runtime. We present a canonical signing methodology built on length-prefixed canonical CBOR with explicit type tags, a multi-runtime conformance suite that detects encoding divergence at the byte level, and a longitudinal study of how the AumOS codebase's canonicalization defect (C1 in the project's own critical analysis) was diagnosed and closed across four runtimes. We argue that canonical signing is not an implementation detail but a first-class security contract, and that the absence of cross-language conformance suites in prior agent-identity prototypes is itself a latent vulnerability class.

Novel contribution

(1) A formal definition of canonical-signing conformance suitable for standardization. (2) The first published multi-runtime conformance vector suite for agent-identity tokens, released as an open artifact. (3) Empirical evidence, drawn from the AumOS codebase, that canonicalization defects are common, subtle, and security-critical — and that a structured fix protocol (canonical-encoding library + golden vectors + CI gate) eliminates the entire class.

Related work (with citations)

  • On the Resilience of LLM-Based Multi-Agent Collaboration — ICML 2025. Multi-agent settings are exactly where cross-runtime signing matters most.
  • Security Challenges in AI Agent Deployment — NeurIPS 2025. Identifies deployment heterogeneity as an attack surface that canonical signing mitigates.
  • CBOR (RFC 8949) and COSE (RFC 9052) — the IETF standards the canonical encoding is built on.

Paper 3

The Agent Action Receipt: Tamper-Evident Audit Trails for Autonomous Systems

Abstract sketch

Regulatory frameworks — the EU AI Act, the U.S. AI Kill Switch Act, sectoral regimes — increasingly demand that autonomous AI actions be reconstructable after the fact for audit, liability attribution, and incident investigation. Existing logging practice (append-only files, opaque cloud audit logs) is neither tamper-evident at the cryptographic level nor structured for cross-organizational verification. We present the Agent Action Receipt (AAR), a hash-chained, counter-signed, timestamp-anchored receipt format that proves an agent performed a specific action with a specific authority at a specific time, verifiable by any third party without trusting the agent's operator. We integrate AAR with the AumOS flight-recorder component and demonstrate end-to-end audit reconstruction across a 100,000-action workload, showing that the receipt graph supports both real-time tamper detection and post-hoc forensic reconstruction. We position AAR as the missing evidence layer that converts agent audit logs from operator-controlled narratives into cryptographically verifiable evidence.

Novel contribution

(1) A receipt format whose tamper-evidence holds even when the issuing agent's host is later compromised (the hash chain anchors to an external timestamp authority). (2) A formal treatment of receipt graph consistency under concurrent, distributed, and re-ordered action streams. (3) An empirical demonstration that AAR overhead is below 3% of action latency in a realistic agent workload, removing the performance objection to tamper-evident logging.

Related work (with citations)
  • Toward Cryptographically Verifiable Authorization for Autonomous AI Agents — arXiv:2607.21325 (2026). Establishes that verifiable evidence of agent action is an open problem; AAR is the evidence artifact.
  • SoK: Attack and Defense Landscape of Agentic AI Systems — Kim et al., USENIX Security 2026. Audit-log tampering is listed as a post-compromise defense failure mode.
  • AI Agents Under Threat: A Survey — Deng et al., ACM Computing Surveys 2025. Identifies auditability as a cross-cutting requirement.
  • Certificate Transparency (RFC 9162) — the append-only hash-chain precedent AAR generalizes to agent actions.

Paper 4

Delegation Intersection Semantics: Preventing Privilege Escalation in Multi-Agent Systems

Abstract sketch

When multiple principals delegate overlapping authority to a multi-agent system, the effective permission set is not the union but a carefully defined intersection of principal-granted, host-attested, and protocol-declared scopes. Getting this wrong produces privilege escalation: an agent combines a broad delegation from one principal with a narrow one from another and acts beyond either principal's intent. We formalize delegation intersection as a meet-semilattice over permission sets, prove that the meet operation is the only sound composition under adversarial delegation injection, and show that the AumOS AAE verifier's intersection check is a faithful implementation of the semilattice meet. We extend the recent ICML 2025 work on multi-agent resilience with a cryptographic (rather than statistical) privilege-escalation guarantee, and we demonstrate attack scenarios from the SoK on Agentic AI in which a flawed union semantics leads to demonstrable escalation that the intersection semantics prevents.

Novel contribution

(1) The first formal, lattice-theoretic treatment of multi-principal delegation composition for AI agents. (2) A proof that intersection (meet) is the unique sound composition under a Dolev-Yao attacker with delegation-injection capability. (3) Empirical escalation-attack case studies, drawn from the AumOS red-team harness, that distinguish union-flawed from intersection-sound implementations.

Related work (with citations)

  • SoK: Attack and Defense Landscape of Agentic AI Systems — Kim et al., USENIX Security 2026. Privilege-escalation attack classes this paper formally closes.
  • Agentic AI Security: Threats, Defenses, Evaluation — Chhabra et al., IEEE 2026. Defense-evaluation framework extended with intersection-semantics tests.

Confidential AI Infrastructure

Builds on: C1-1 through C1-5 (confidential core) · F1 fed-core · F2 dp-crate

This thrust covers the systems and cryptography contributions that flow from running AI training and inference inside confidential computing enclaves — CPU TEEs and, critically, NVIDIA Confidential GPUs (H100/N1). The landmark NVIDIA GPU Confidential Computing Demystified (arXiv:2507.02770, 2025) and the Creating the First Confidential GPUs article (Communications of the ACM) establish the hardware substrate; AumOS's C1 components and F1/F2 federated+DP crates provide the software substrate to compose, attest, and privacy-budget that hardware into end-to-end confidential AI pipelines. The four papers below address attested inference, DP-FL with TEE attestation, multi-tenant GPU composition, and the production treatment of the differential-privacy parameter ε.

Paper 5

Attested Inference Pipelines: End-to-End Confidential Computing for LLM Serving

Abstract sketch

Confidential GPUs can now protect model weights and intermediate activations inside an enclave, but a production LLM serving pipeline is more than a single GPU: it spans a model loader, a tokenizer, a KV-cache, a scheduler, a network egress path, and a client attestation handshake. Each hop is a confidentiality boundary that must be independently attested and composed into a single verifiable pipeline attestation. We present an attested inference pipeline architecture built on AumOS's C1 confidential-core components, in which every stage contributes a quote to a composed attestation report that the client verifies before sending a prompt. We extend the recent NVIDIA GPU Confidential Computing Demystified analysis (arXiv:2507.02770, 2025) with the end-to-end composition problem it explicitly leaves open, and we measure the latency, throughput, and attestation-overhead cost of serving a 70B-parameter model on H100 Confidential GPUs with and without the full pipeline attestation.

Novel contribution

(1) A composed-attestation protocol for multi-stage inference pipelines that reduces to per-stage GPU attestation as a special case. (2) An implementation and evaluation on real H100 Confidential GPUs, covering the gap between hardware capability and deployable system. (3) A threat-model refinement showing which pipeline stages require hardware attestation versus software isolation, enabling practical cost reduction.

Paper 6

Differentially Private Federated Training with TEE Attestation

Abstract sketch

Federated learning promises privacy by keeping raw data on clients, but the gradient updates themselves leak membership information absent additional protections. Differential privacy (gradient noise) and secure aggregation are the two standard responses, yet both assume the aggregator is honest-but-curious — an assumption that fails in practice when the aggregator is a cloud operator with root on the training host. We combine AumOS's fed-core (F1) federated-training crate with its dp-crate (F2) differential-privacy crate and the C1 confidential-core attestation, producing a federated-training system in which each aggregator step runs inside a TEE whose measurement is attested to every client before that client submits an update. We extend the NeurIPS 2025 line of work on DP-FL trade-offs (privacy–utility, preference-optimized privacy, and the ε-setting debate) by adding the missing trust anchor: the aggregator is not just honest-but-curious, it is cryptographically constrained to be honest.

Novel contribution

(1) The first federated-training system to combine per-round TEE attestation of the aggregator with end-to-end differential privacy accounting, eliminating the honest-but-curious aggregator assumption. (2) A formal composition theorem for the privacy budget across attested rounds. (3) Empirical accuracy and privacy-budget results on standard FL benchmarks (FEMNIST, Stack Overflow) showing that attested aggregation recovers utility lost to aggressive client-side noise.

Related work (with citations)

Paper 7

Confidential GPU Composition: Multi-Tenant Attestation for AI Workloads

Abstract sketch

A single H100 Confidential GPU can host multiple tenant workloads simultaneously, each with its own attestation domain, key hierarchy, and isolation boundary. Composing these domains correctly — so that tenant A cannot observe tenant B's attestations, keys, or residuals — is an open systems problem that the CACM account of the first confidential GPUs flags but does not solve. We present a multi-tenant attestation composition for confidential GPUs, implemented in AumOS's C1 components, in which each tenant's attestation report is bound to a hardware-enforced domain ID and verified independently of co-tenants. We provide a formal isolation argument, a side-channel evaluation (memory-bus, thermal, timing), and a deployment case study on a shared inference cluster serving four mutually-distrusting tenants.

Novel contribution

(1) A domain-ID-bound attestation protocol for multi-tenant confidential GPUs. (2) The first published side-channel evaluation of multi-tenant confidential-GPU composition under realistic co-residency. (3) A compositional proof framework that lets new tenants be added without re-verifying existing tenants' isolation.

Paper 8

The Privacy Budget Paradox: Rethinking ε in Production AI Systems

Abstract sketch

The differential-privacy parameter ε is conventionally treated as a knob the data owner sets once, trading privacy against utility. The NeurIPS 2025 paper Setting ε Is Not the Issue in Differential Privacy argues persuasively that the real problems are accounting, composition, and adversary modeling — not the choice of ε itself. We extend this argument into the production AI setting, where ε is not set once but evolves over a deployment lifetime, is consumed across heterogeneous subsystems (training, fine-tuning, inference, logging), and is bounded by regulators who treat it as a compliance number rather than a cryptographic quantity. Using AumOS's dp-crate (F2) as the accounting substrate, we present a production ε-accounting system that tracks per-subsystem, per-deployment, per-regulator budget consumption in real time, and we show that the gap between the textbook ε and the production-effective ε is routinely 2–10x in deployed systems.

Novel contribution

(1) A production-grade ε-accounting data model that unifies training, inference, and logging budget consumption. (2) Empirical evidence that the textbook-vs-production ε gap is large, systematic, and currently unaccounted for. (3) A compliance mapping showing how production ε-accounting maps to specific EU AI Act and GDPR articles.

AI Supply Chain Integrity

Builds on: S1 safe-tensors-pp · S2 provena-chain · S4 model-sbom · S5 data-provenance-kit · S7 tamper-scan · S8 train-guard

The AI supply chain — from training data, through base-model weights, fine-tunes, adapters, and deployed artifacts — is the least-mature layer of AI security and the fastest-moving target of regulation. The OpenSSF AI/ML Working Group's Model Signing v1.0 (2025), the OMS Specification, the CoSAI Building Trust in AI Supply Chains guidance, the G7 SBOM for AI Minimum Elements (2026), and CycloneDX's ML-BOM capability together define the standards landscape. The four papers below convert those implementations into research contributions that extend the standards rather than re-derive them.

Paper 9

Safetensors++: Signed Provenance Metadata for Open Model Formats

Abstract sketch

The safetensors format has become the de facto open standard for distributing model weights, but it carries no signed provenance metadata: a consumer cannot verify who produced a weights file, what training data and base model it descends from, or whether it has been tampered with since signing. OpenSSF Model Signing v1.0 (2025) and the OMS Specification define signing at the artifact level but leave the in-format metadata question open. We present safetensors++, a backward-compatible extension to the safetensors header that carries a signed provenance block (issuer identity, base-model hash, training-data manifest hash, training-run attestation, signature) and a reference implementation in AumOS's safe-tensors-pp (S1) component. We show that the extension is parseable by existing safetensors loaders (graceful degradation) and that the signed metadata is sufficient to detect the full class of weight-substitution and provenance-fabrication attacks.

Novel contribution

(1) A backward-compatible, in-format signed-provenance extension to safetensors, designed for adoption by the existing open-model ecosystem. (2) A formal treatment of the weight-substitution attack class and proof that signed provenance detects every member of the class. (3) An interoperability study showing safetensors++ parses cleanly across Hugging Face Transformers, vLLM, and llama.cpp.

Zero-Trust AI: From SPIFFE to Agent Identity

Executive summary

Workload identity solved the service-to-service authentication problem; agent identity is the same problem one layer up, materially harder, and currently unsolved by any standardized mechanism. This whitepaper, for platform engineers already operating SPIFFE/SPIRE, traces the precise evolution from workload identity to autonomous-agent identity: what carries over unchanged, what must be generalized, and how the AumOS I1 component reuses SPIRE's trust-domain and SVID concepts while extending them to bind a delegation, a host attestation, and a capability scope into a single verifiable agent identity. We present the federation model for cross-organization agent identity and an operational deployment guide for the agent-identity control plane.

The practitioner problem

A platform team that has standardized on SPIRE issues X.509-SVIDs to every workload and has clean, mTLS-everywhere, zero-trust service mesh. Then an LLM agent arrives. The agent is not a workload in the SPIRE sense — it has no fixed pod, it acts on behalf of a human principal, its permissions vary per delegation, and it calls APIs in other trust domains. Issuing it a workload SVID conflates the agent's identity with the principal's authority and breaks the zero-trust model the team spent years building. The team needs an identity primitive that is to agents what SVIDs are to workloads: standardized, federation-ready, and bound to the authority it acts under.

What carries over from SPIFFE

The SPIFFE specification (SPIFFE IDs, trust domains, the SVID concept, the workload API, and the federation model) is the right foundation, and AumOS I1 inherits it deliberately rather than reinventing it. Specifically: the trust domain remains the unit of administrative authority; the SVID remains the carrier of identity; the workload API pattern remains the secret-distribution mechanism. A team that understands SPIRE understands 80% of AumOS I1. The remaining 20% is the generalization.

What must be generalized: from workload to agent

Three properties distinguish an agent identity from a workload identity, and each requires an extension to the SPIFFE model.

  • Delegation binding. A workload's authority is static (its service-account role). An agent's authority is dynamic — it is delegated per-task by a human principal. The agent identity must therefore carry (or reference) the delegation envelope (AAE) that authorized it, and the relying party must verify the delegation, not just the identity. AumOS binds the AAE to the SVID as an extension.
  • Host attestation binding. A workload's host is the cluster it runs in. An agent's host may be a TEE whose confidentiality the relying party cares about. The agent identity must therefore bind an attestation document, so that the relying party can refuse to honor an agent running on an unattested host. AumOS composes the SVID with the C1 attestation.
  • Capability scope. A workload's permissions are coarse. An agent's permissions must be fine-grained (per-skill, per-API, per-resource) and intersect with both the principal's grants and the protocol's declarations. AumOS makes the capability scope a first-class field of the identity document, verified by the intersection contract (Paper 4).

Federation across organizations

Workload federation (SPIFFE Federation) lets trust domain A verify workloads from trust domain B by trusting B's bundle. Agent federation adds a wrinkle: trust domain A must verify not only that the agent is from B, but that the principal who delegated to the agent is who B claims, and that the delegation is still valid (not revoked). AumOS P7 (federation protocol) extends SPIFFE federation with a delegation-bundle and revocation-distribution mechanism, so that a relying party in domain A can verify the full chain — agent identity, principal identity, delegation validity, host attestation — without out-of-band coordination.

Deployment sequence (for a SPIRE-experienced team)

  1. Extend the trust domain. Register the AumOS I1 agent-identity CA as an issuer within the existing trust domain, or stand up a dedicated agent trust domain federated with the workload domain. Reuse the existing SPIRE bundle distribution.
  2. Deploy the agent workload API. The agent-runtime retrieves its SVID+AAE via the same workload-API pattern SPIRE uses; the secret never touches disk in plaintext.
  3. Wire the delegation issuer. The principal's identity provider (often the existing corporate IdP) issues AAEs that the agent-identity CA binds into the SVID. This is the human-in-the-loop step that authorizes the agent.
  4. Configure relying-party verification. API gateways and service mesh sidecars verify the SVID (existing SPIRE logic) and the AAE extension (new logic) before honoring an agent request. Verification that fails on either rejects.
  5. Stand up revocation distribution. Deploy the revocation-bundle distribution so that a revoked delegation propagates within the freshness window (target: seconds). This is the operational property that makes the kill switch real.
  6. Federate with partners. Exchange trust bundles with partner organizations per P7; agents acting cross-organization now verify end-to-end.

Evidence & validation

The migration proof: an existing SPIRE deployment can adopt AumOS I1 without forklifting the workload-identity layer. The agent SVID is a SPIFFE SVID with a well-defined extension; SPIRE-verified workloads continue to verify; only the agents and their relying parties adopt the new logic. This is the same incremental-adoption property that made SPIRE itself deployable, and it is the property that makes agent identity deployable on top of it.

The AI Kill Switch Act: Technical Requirements and Reference Implementation

Executive summary

Legislatures on both sides of the Atlantic are converging on a statutory requirement that operators of high-risk AI systems maintain a "kill switch" — the ability to halt, isolate, and forensically preserve an autonomous system that is behaving dangerously. The policy intent is clear; the technical requirements are not. This whitepaper, for policy makers and their technical advisors, translates the statutory language into a concrete engineering specification: what a compliant kill switch must do, what evidence it must produce, how it composes with existing incident-response practice, and how the AumOS R3 reference implementation satisfies the specification. It bridges the policy-engineering gap that, left unclosed, produces either unenforceable law or security theater.

The practitioner (and policymaker) problem

A kill switch sounds simple — "turn it off" — until one tries to specify it for a distributed, long-running, stateful agent system. Off means what, precisely? Halt the inference? Revoke the credentials? Quarantine the state? Preserve the evidence? Each is a different control with a different blast radius. A statute that says "maintain a kill switch" without defining these terms is, in engineering terms, unimplementable; an operator that claims a kill switch without these controls is providing security theater. The gap between legislative intent and engineering reality is where compliance failures — and real harm — live.

The five control objectives a compliant kill switch must meet

From analysis of the emerging statutory landscape and incident-response practice, we derive five control objectives that any defensible kill-switch specification must address. AumOS R3 implements all five; the whitepaper argues these should be the de-facto technical standard against which statutory language is interpreted.

  • 1. Halt — stop the system from taking further autonomous action. R3 revokes the delegation (the AAE), so every relying party rejects the agent within the freshness window. This is the "stop the bleeding" control.
  • 2. Isolate — prevent the system from exfiltrating state or communicating with accomplices. R-pillar egress control and sandboxing quarantine the agent's runtime; no outbound network except to the forensic sink.
  • 3. Preserve — capture forensic state for investigation. R3 triggers forensic-freeze mode: the action-receipt chain (P2) is sealed and anchored, the model and agent state are snapshotted, and the lot is hash-bound into an evidence bundle that cannot be silently altered.
  • 4. Attest — produce evidence that the kill switch was effective. R3 emits a kill-switch receipt proving halt, isolation, and preservation occurred, signed and timestamp-anchored for a regulator or court.
  • 5. Restore — provide a defined, tested path to safe resumption once the incident is understood. R3 supports a quorum-gated restoration with a mandatory post-incident review artifact.

Methodology: from statute to specification to implementation

The whitepaper proceeds in three layers. Layer 1 (statute) quotes the relevant provisions of the emerging laws and extracts their plain-language requirements. Layer 2 (specification) formalizes each requirement as a control objective with a testable success criterion — the "what would a regulator accept as proof" bar. Layer 3 (implementation) maps each control objective to the specific AumOS component and configuration, and presents the reference deployment. The three-layer structure is itself a contribution: it gives policy authors a vocabulary for writing implementable law, operators a target for compliance, and regulators a verification procedure.

Deployment sequence

  1. Define the escalation policy. Who is authorized to throw the kill switch, under what conditions, and with what quorum? This is the human-governance step; R3 enforces it cryptographically (no single party can halt or restore alone).
  2. Wire the halt path. Configure R3 to revoke the AAE on trigger; verify that relying-party rejection propagates within the freshness SLA. Test it on a staging agent.
  3. Wire the isolation path. Configure egress control and the quarantine sandbox; verify the agent cannot reach any network except the forensic sink when isolated.
  4. Wire the preservation path. Configure forensic-freeze mode; verify the evidence bundle (receipt chain + state snapshot + hash binding) is produced and anchored.
  5. Exercise quarterly. Run a tabletop and a live-fire kill-switch drill each quarter; archive the receipts. An untested kill switch is not a control.
  6. Define the restoration path. Configure the quorum-gated restore with the mandatory post-incident review; document the conditions under which restoration is permitted.

Evidence & validation

What a regulator or court receives: a signed kill-switch receipt proving the five control objectives were met, with timestamps, the halted delegation's identity, the preserved evidence bundle's hash, and the restoration record. This is the difference between an operator asserting "we had a kill switch" and an operator demonstrating it worked, on the record, in a form that resists after-the-fact alteration.

Confidential AI on NVIDIA H100: A Deployment Guide

Executive summary

The NVIDIA H100 (Hopper) and the forthcoming N1 are the first broadly available GPUs with hardware-enforced confidential computing, enabling inference and training workloads where the model weights, the prompts, and the outputs are cryptographically protected from the host, the hypervisor, and the cloud operator. This is a structural change in the trust model of AI infrastructure — but the operational reality of deploying it is poorly documented, and most teams that attempt confidential inference stall on attestation-domain setup, multi-tenant composition, or key-release orchestration. This whitepaper is the deployment guide that does not exist in vendor documentation: the attestation-domain model, the handshake, multi-tenant composition, performance tuning, and the day-2 operational runbook, all built on the AumOS C1 components.

The practitioner problem

Confidential computing on a CPU TEE (Intel TDX, AMD SEV-SNP) is a solved operational problem. Confidential computing on an H100 is not, for three reasons. (1) The attestation model is different: the GPU's confidential-computing mode produces an attestation report whose verification requires NVIDIA-specific libraries and a NVIDIA attestation service, and the trust chain runs through NVIDIA's root of trust. (2) Multi-tenant composition is hard: serving several tenants' models on a shared GPU pool without cross-tenant leakage requires careful attestation-domain design and key-release gating. (3) The performance overhead is real and must be tuned: naive confidential-inference deployments leave 20–40% of throughput on the table. Teams need a documented path through all three.

Architecture: the attestation domain

The foundational concept is the attestation domain: a set of GPUs, a set of model keys, and a verification policy, over which a consistent trust decision is made. AumOS C1-1 (binding to NVIDIA NVTrust) establishes the domain; C1-2 (high-level Python attestation client) retrieves and verifies the attestation reports; C1-3 orchestrates the end-to-end attested pipeline inside the TEE; C1-4 terminates TLS inside the enclave so prompts are never in plaintext on the host; C1-5 composes the streams and gates model-key release so that keys are handed to the GPU only after the attestation verifies. The five compose; none is sufficient alone.

The attestation handshake (operator's view)

  • Provisioning. The model owner encrypts weights to a policy that only a GPU meeting the attestation requirements can satisfy. The encrypted weights and the policy are stored in the registry.
  • Request. A tenant requests inference. The serving node brings up the H100 in confidential-computing mode and requests an attestation report.
  • Verification. C1-2 retrieves the report and verifies it against the policy (firmware version, CC mode asserted, debug disabled, measurement values). Verification failure halts the request.
  • Key release. On successful verification, C1-5 releases the model key to the GPU (via the H100's secure key channel); the GPU decrypts the weights inside its protected memory.
  • Inference. C1-4 terminates TLS in the enclave; the prompt traverses the host only as ciphertext; the GPU computes and returns the output through the encrypted channel.
  • Teardown. On session end, the GPU's confidential memory is scrubbed; keys never persisted to host disk.

Multi-tenant composition

The naive anti-pattern is one GPU per tenant — secure but economically fatal. The AumOS pattern is attestation-domain partitioning: tenants sharing a physical GPU are isolated by distinct attestation policies and distinct key-release gates, so that a key released for tenant A's model cannot be consumed by tenant B's context, and a context switch requires a fresh attestation. C1-5 enforces this by binding each key release to both the attestation and the tenant's identity (I1), so a key is never releaseable to a GPU context that does not match both. This is what makes shared-GPU confidential serving defensible.

Deployment sequence

  1. Establish the attestation service. Deploy the NVIDIA attestation components and C1-1; register the GPU fleet. Verify the attestation report for one GPU end-to-end before proceeding.
  2. Encrypt and register the first model. Encrypt weights to a policy (firmware floor, CC mode, debug off); register the encrypted artifact and policy. Verify the key-release path on one inference.
  3. Deploy the in-enclave serving path. Deploy C1-3/C1-4 and the TLS-terminating inference server; verify a prompt traverses the host only as ciphertext.
  4. Define the attestation domains. Partition the fleet into domains by tenant or sensitivity; configure C1-5 key-release per domain.
  5. Tune for throughput. Profile the confidential path vs. the non-confidential baseline; tune batch size, key-caching, and the attestation-cadence (re-attest per-session vs. per-window) to recover throughput.
  6. Operationalize. Wire attestation failures into the alerting pipeline; define the runbook for a failed-attestation event (do not serve; quarantine; investigate).

Evidence & validation

What this delivers, measurably: (a) a verified attestation report for every confidential inference, loggable for audit; (b) zero host-disk plaintext for weights or prompts, verifiable by inspection; (c) a documented and tuned throughput overhead (target ≤10–15% vs. non-confidential baseline after tuning); (d) multi-tenant isolation that is policy-enforced, not merely topology-assumed. This is the difference between claiming confidential AI and being able to show a regulator or customer the attestation trail.

Post-Quantum AI Security: Migrating Agent Infrastructure to NIST FIPS 203/204/205

Executive summary

With NIST's finalization of the first post-quantum cryptography standards in August 2024 — FIPS 203 (ML-KEM, formerly CRYSTALS-Kyber), FIPS 204 (ML-DSA, formerly CRYSTALS-Dilithium), and FIPS 205 (SLH-DSA, formerly SPHINCS+) — the migration of production cryptographic infrastructure from classical to quantum-resistant algorithms is no longer hypothetical. AI-agent infrastructure is a particularly acute migration target: the delegation envelopes, action receipts, and model signatures that an agent system produces today may need to remain verifiable for decades, and "harvest-now-decrypt-later" attacks mean that secrets encrypted under classical schemes are already at risk. This whitepaper, for security architects, presents the migration sequence for AI-agent cryptographic infrastructure — what migrates first, the hybrid (classical+PQC) transition, the performance impact, and the cryptographic-agility design that makes the migration survivable.

The practitioner problem

Security architects are told "migrate to PQC" with little guidance on sequencing for a system as cryptographically diverse as an AI-agent platform. An agent platform uses asymmetric cryptography for at least four distinct purposes — agent identity (SVIDs), delegation envelopes (AAE signing), action-receipt integrity (hash chains + signatures), and model signing (provenance) — each with different freshness, longevity, and interoperability constraints. Migrating them all at once is infeasible; migrating them in the wrong order creates windows of exposure. The architect needs a principled sequence, a hybrid-bridge design, and a cryptographic-agility substrate so that future algorithm rotations (including deprecation of an adopted PQC scheme) are routine rather than traumatic.

The migration sequence (in dependency order)

The whitepaper argues for a four-phase sequence driven by the longevity of the artifacts each cryptographic use protects. Artifacts that must remain verifiable for the longest migrate first.

  • Phase 1 — Model signing (longest-lived). A model signed today may be verified a decade hence. Migrate S-pillar model signing (P4) to ML-DSA first, with a hybrid classical+ML-DSA signature during the transition so that legacy verifiers still function. This is the slowest-rotating artifact and the one most exposed to harvest-now-decrypt-later over decades.
  • Phase 2 — Action-receipt and lineage signatures. Receipts and lineage proofs must remain verifiable for the audit-retention period (often 7+ years under regulations like the EU AI Act). Migrate P2/P5 next, again hybrid during transition.
  • Phase 3 — Delegation envelope signing (AAE). Delegations are short-lived (minutes to hours), so the harvest-now risk is lower, but migrating AAE (P1/T2) to ML-DSA closes the most active signing path and is the highest-volume performance consideration.
  • Phase 4 — Key establishment (agent identity, TLS). Migrate the key-establishment paths (I1 SVIDs, the in-enclave TLS of C1-4) to ML-KEM, completing the migration. This is last because it benefits most from the maturing of PQC TLS and because the hybrid KEM overhead is the most performance-sensitive.

The hybrid bridge

Each phase runs a hybrid classical+PQC transition: every signed artifact carries both a classical signature (Ed25519/ECDSA) and a PQC signature (ML-DSA), and a verifier accepts the artifact if either (or, for high-assurance, both) verifies. The hybrid bridge is not a compromise; it is the structurally correct response to the dual uncertainty of (a) the classical schemes being broken by a future quantum adversary and (b) the PQC schemes being broken by a future cryptanalytic advance. The whitepaper specifies the hybrid container format for each of the four uses, designed for forward compatibility so that adding or rotating algorithms is a metadata change, not a schema change.

Performance: the budget that shapes the sequence

The migration sequence is not arbitrary; it is shaped by the performance characteristics of the new algorithms. ML-DSA signatures are larger (~2.7 KB for security level 2) and signing/verification is slower than Ed25519, which matters most for the high-frequency AAE and receipt paths — hence their placement mid-sequence, after the slow-rotating artifacts and before the latency-critical key-establishment path. ML-KEM key encapsulation is competitive with ECDH in compute but larger in wire size, which affects the TLS path most. The whitepaper provides measured overhead numbers from the AumOS reference implementation for each use, so the architect can budget rather than guess.

Methodology: cryptographic agility as the substrate

The migration is survivable only if the cryptographic layer was designed for agility — the ability to add, rotate, and deprecate algorithms without rewriting the systems that depend on them. AumOS T1 (trust-core) is designed around this: cryptographic primitives are behind a trait/interface with an algorithm identifier in every artifact, so adding ML-DSA or a future scheme is a new implementation of the trait, not a fork of the codebase. The whitepaper presents the agility design and argues that any platform built without it faces a traumatic migration rather than a routine one — and that the NIST PQC migration is, for such platforms, the first of several.

Deployment sequence

  1. Audit the cryptographic surface. Inventory every asymmetric-cryptography use; classify by artifact longevity and frequency. This inventory is the input to sequencing.
  2. Deploy ML-DSA signing in T1. Add ML-DSA as an available algorithm behind the agility interface; do not yet enable it in production paths.
  3. Enable hybrid signing for model artifacts (Phase 1). Begin emitting dual signatures; verify both in the gate; alert on either failing. Run this for a full release cycle.
  4. Roll forward through Phases 2–4. Enable hybrid for receipts/lineage, then AAE, then key establishment, each behind a release cycle of dual verification.
  5. Establish the rotation policy. Define the conditions under which an algorithm is deprecated and the rotation cadence; make rotation a tested, quarterly capability, not a crisis response.
  6. Plan the classical deprecation. Once PQC verification is universal in the relying parties, schedule the classical-signature removal — the final state of the migration.

Evidence & validation

What this delivers, measurably: (a) every long-lived artifact (model signatures, lineage, receipts) carries a quantum-resistant signature within the migration window; (b) measured overhead per phase, published so the migration is budgeted not guessed; (c) a cryptographic-agility substrate that makes the next algorithm rotation (and the eventual classical deprecation) routine; (d) a hybrid-bridge design that closes neither the classical nor the PQC trust window prematurely.
