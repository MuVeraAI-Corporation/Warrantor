Agent Integration Guide

Make Claude Code, OpenAI Codex, Cursor, and any MCP-compatible agent work with AumOS — three integration paths, one security envelope.

← Back to Index Overview Three Paths MCP Server Agent SDK Harness Security Matrix Quick Start

AumOS is the open authority and evidence layer for autonomous systems. For coding agents this means two things: your agent can call AumOS security primitives (identity, receipts, attestation), and AumOS can secure the agent itself (sandbox boundary, kill-switch, file tracking). This guide is the definitive reference for both directions.

02 · Overview

Bidirectional: Agents Call In, We Lock Down

Most agent integrations are one-way. AumOS is bidirectional. An agent reaches into AumOS to sign data, issue identity, emit receipts, and check attestation. Simultaneously, AumOS wraps around the agent to enforce a sandbox boundary, scan its output for leaked credentials, and kill it on misbehavior. The two directions compose: an agent wrapped by the harness can still call the MCP server, and every call produces a verifiable receipt.

Why bidirectional matters

Direction 1 makes the agent trustworthy — every action it takes is signed and receipted. Direction 2 makes the agent safe — it cannot escape its sandbox, leak secrets, or run unbounded. An agent that only does direction 1 can still go rogue; an agent that only does direction 2 produces no verifiable evidence. You want both.

03 · The Three Integration Paths

Three Ways In, One Security Envelope

Pick the path that matches your integration surface. All three produce the same verifiable artifacts (SVIDs, AAR receipts) and talk to the same 49 AumOS components. They differ in how much of the agent you control.

01
MCP Server

Any MCP-compatible agent (Claude Code, Cursor, Zed, Codex) discovers and invokes AumOS tools over stdio JSON-RPC. Zero code on the agent side — just a config entry. Best when you control the agent's MCP client but not its internals.

TypeScript stdio transport 15 tools
02
Agent SDK

A Python @agent.action decorator wraps any function with the full AumOS envelope — identity, preflight, credentials, receipt, evidence, kill-switch. Best when you write the tool code the agent calls, or you ship a custom agent.

Python @agent.action standalone / connected
03
Harness Wrappers

secure_session() wraps an entire agent execution — every command it runs, every file it touches, every byte of output it emits. Best when you run an unmodified third-party agent (e.g. claude, codex) and want a perimeter.

Python secure_session() sandbox perimeter
They stack

The strongest setup uses all three: the harness wraps the agent process; the agent's custom tools use the SDK decorator; and the agent also has the MCP server configured for ad-hoc tool calls. Each layer is independently useful.

04 · MCP Server Setup

Configuring Your Agent for the MCP Server

The MCP server (@warrantor/aumos-mcp-server) speaks the Model Context Protocol over stdio JSON-RPC 2.0. It advertises 15 tools via tools/list and handles tools/call. It runs in standalone mode by default (deterministic mock responses, zero external deps — ideal for dev and dry-runs) and switches to connected mode when AUMOS_MODE=connected is set or --connected is passed, issuing real HTTP calls to the AumOS services.

Claude Code

Add to .claude/mcp_servers.json in your project root:

{
  "aumos": {
    "command": "npx",
    "args": ["@warrantor/aumos-mcp-server"]
  }
}

Restart Claude Code. Run /mcp to confirm the aumos server connects and lists its 15 tools.

Cursor

Open Cursor Settings → Features → MCP Servers → Add, or edit ~/.cursor/mcp.json:

{
  "mcpServers": {
    "aumos": {
      "command": "npx",
      "args": ["@warrantor/aumos-mcp-server"]
    }
  }
}

Cursor discovers the tools on next chat session. The AumOS tools appear alongside Cursor's built-in tools.

Generic MCP

Any MCP-compatible client. Stdio transport, JSON-RPC 2.0:

# Spawn the server directly
npx @warrantor/aumos-mcp-server

# Connected mode (real services)
AUMOS_MODE=connected npx @warrantor/aumos-mcp-server

# Pin service URLs via env
AUMOS_AGENT_IDENTITY_URL=http://localhost:8441 \
AUMOS_FLIGHT_RECORDER_URL=http://localhost:8445 \
npx @warrantor/aumos-mcp-server --connected

Protocol version 2024-11-05. Logs go to stderr; stdout is reserved for protocol frames.

The 15 AumOS Tools

Each tool is backed by a real async implementation. In connected mode failures degrade gracefully to mock responses with a degraded: true flag — a tool never crashes the server (invariant I-09).

ToolDescriptionRequired Args
aumos_sign Sign data with Ed25519 via T1 trust-core. Returns {signature_hex, algorithm}. data · key_id?
aumos_verify Verify an Ed25519 signature. Returns {valid, reason?}. data, signature, key
aumos_issue_identity Issue a SPIFFE SVID + capability token via I1 agent-identity. POST /v1/agent-identity:issue. subject · audience?, parent_svid?
aumos_verify_identity Verify an SVID via I1. POST /v1/agent-identity:verify. svid · audience?
aumos_revoke_identity Revoke an identity. Propagation target: identity <5s, credentials <1s (I-05). jti · reason?
aumos_emit_receipt Emit an Agent Action Receipt (P2 AAR) via E1 flight-recorder — before the action commits (I-07). actor, tool, outcome · side_effect?, inputs_hash?
aumos_verify_receipt Verify a receipt signature. Returns {valid, signer, receipt_id}. receipt_id · signature?
aumos_check_attestation Check a GPU attestation report via C1-1 nvtrust-bridge. Returns {verified, hardware_tee}. nonce?, gpu_pci_id?
aumos_run_preflight Run sandbox pre-flight via R2 eval-guard. Action proceeds only if allowed: true (I-09). tool · inputs?, side_effect?
aumos_kill Trigger the R3 kill-switch — halts/quarantines the agent. Returns {triggered, reason, killed_at}. reason · agent?
aumos_scan_secrets Scan text for exposed credentials via R4 credential-vault. Detects AWS keys, GitHub PATs, Slack tokens, private keys, generic bearers. text
aumos_compliance_report Generate a compliance report via X1 defstack-cli. Returns {report_json}. scope?, format?
aumos_install Install an AumOS component via defstack install <name>. Returns {installed, version}. name · version?
aumos_generate_sbom Generate a Model SBOM (CycloneDX) via S4 model-sbom. Returns {sbom, components}. model · format?
aumos_run_eval Run an eval pipeline via A1 safe-eval (HELM/garak/PyRIT/MDASH). Returns results + a Verifiable Evaluation Bundle. model · pipeline_yaml?
Tool result shape

Every tool returns structured JSON with source ("mock" | service name), degraded (true when a connected-mode call failed and fell back to mock), and the tool's domain fields. An isError flag marks tool-level errors — the server itself stays up.

Side-effect ladder (invariant I-08)

Several tools accept a side_effect parameter. The five ordered classes escalate by consequence: read → write → financial → destructive → physical. The three consequential classes (financial, destructive, physical) require explicit approval and are blocked by default in preflight.

05 · Agent SDK Quick Start

The @agent.action Decorator

The Python Agent SDK (warrantor-agent) wraps any function with the full AumOS security envelope. The decorator is the headline: one line and your tool gets identity, preflight, credential brokering, a pre-commit receipt, evidence recording, and an automatic kill-switch on error.

from warrantor_agent import AumOS

agent = AumOS(mode="standalone")   # or mode="connected" against running services

@agent.action(tool="github.create_pr", side_effect="write")
def create_pr(repo, title):
    return {"url": f"github.com/{repo}/pull/1"}

result = create_pr("MuVeraAI/aumos", "fix: off-by-one")
# result is the function's return value; the security artifacts live on
# create_pr.action_result  -> ActionResult(svid, preflight, receipt, ...)

What happens automatically, in order

On every call to a decorated action, the SDK runs this exact sequence:

  1. Identity (I1). Issues / verifies an agent identity (SPIFFE SVID + capability token) for the actor. The SVID is cached on the agent instance and reused.
  2. Preflight (R2). Runs sandbox pre-flight checks. If fail_closed is set (default) and preflight returns allowed: false, the wrapped function is never called — an ActionBlocked exception is raised with a denied receipt (invariant I-09).
  3. Credential brokering (R4). Scans the JSON-serialized arguments for leaked secrets. Findings are attached to the preflight result (they don't block reads by default).
  4. Pre-commit receipt (E1, invariant I-07). Emits an Agent Action Receipt with outcome pending before the wrapped function runs. This proves the intent-to-act was recorded before any side effect occurred.
  5. Call the function. Your code runs.
  6. Success receipt + evidence (E1). On success, emits a success receipt and appends the ActionResult to agent.evidence.
  7. Kill-switch on error (R3). On any exception, emits a failure receipt, and if auto_kill_on_error is set (default), triggers the R3 kill-switch then raises ContainmentTriggered.
The pre-commit receipt is load-bearing

Step 4 is not cosmetic. AumOS invariant I-07 requires that a receipt exists before the action commits. If you bypass the decorator and call services manually, you must emit the pending receipt yourself first — otherwise the action is not I-07-compliant.

What a decorated call returns

The wrapped function returns its normal value, but gains an .action_result attribute holding the full ActionResult:

@dataclass
class ActionResult:
    ok: bool                  # True iff the function returned normally
    value: Any                # the wrapped function's return value
    svid: str | None          # the agent identity used
    preflight: dict           # R2 result (+ secret_findings, pre_commit_receipt)
    receipt: Receipt          # the final AAR (success | failure | denied)
    outcome: str              # 'success' | 'failure' | 'denied'
    duration_ms: float
    error: str | None

You don't have to use the decorator. The AumOS class exposes every primitive as a plain method, returning plain dicts/dataclasses. Use these when you need finer control than the decorator's fixed sequence.

06 · Harness Wrappers

Wrapping Agent Sessions with secure_session()

The harness (warrantor-harness) is the perimeter layer. Where the SDK decorates individual functions, the harness wraps an entire agent process: every shell command it runs, every file it touches, every byte of stdout and stderr it emits. Use it when you launch a third-party agent binary (like claude or codex) and cannot modify its internals.

from warrantor_harness import secure_session, HarnessConfig, AgentType

config = HarnessConfig(
    agent_type=AgentType.CLAUDE_CODE,
    working_dir=".",
    allowed_tools=["git", "npm", "cargo", "python", "go", "make"],
    side_effect_class="write",
    kill_on_secret_exposure=True,
    max_duration_seconds=3600,
)

with secure_session(config) as session:
    result = session.run_agent("claude --print 'fix the bug in src/auth.py'")
    print(result["exit_code"], result["receipt"]["id"])

    # Every command is receipted; every output is scanned
    for r in session.result.receipts:
        print(r["tool"], r["outcome"], r["secret_findings"])

summary = session.result   # SessionResult

The SessionResult

When the with block exits (or the agent is killed), session.result is a SessionResult summarizing everything that happened:

@dataclass
class SessionResult:
    session_id: str
    agent_type: AgentType            # CLAUDE_CODE | CODEX | CURSOR | GENERIC
    status: SessionStatus            # ACTIVE | COMPLETED | KILLED | ERROR
    started_at: str
    ended_at: str
    action_count: int               # number of receipted commands
    file_accesses: list[FileAccess] # every tracked read/write
    actions: list[ActionRecord]     # one per run_agent() call
    receipts: list[dict]            # the full AAR trail (P2)
    secrets_found: int              # total secret-scan hits
    kill_reason: str                # set if status == KILLED
    duration_seconds: float

What the harness enforces

  • Tool allowlist. run_agent() checks the command's base tool against allowed_tools. Disallowed tools are blocked with a failed receipt before execution.
  • Output secret scanning. Every command's stdout + stderr is scanned for AWS keys, GitHub PATs, OpenAI keys, GitLab PATs, and Slack tokens. If kill_on_secret_exposure is set (default), a hit kills the session immediately.
  • Receipt per action (E1, I-07). Every run_agent() call emits an AAR recording the tool, command, outcome, and any secret findings.
  • Kill-switch (R3, I-09). session.kill(reason) quarantines the session; subsequent run_agent() calls return an error immediately.
  • File tracking. session.track_file_access(path, mode) records every file the agent reads or writes.
  • Duration cap. max_duration_seconds bounds each command via a subprocess timeout.
Config parsers for each agent

The harness ships with parse_claude_code_config(working_dir), parse_codex_config(working_dir), and parse_cursor_config(working_dir). They read CLAUDE.md, AGENTS.md, and .cursorrules respectively and return a pre-populated HarnessConfig with the right agent_type and parsed allowed_tools. Cursor config also sets require_attestation=True.

07 · Claude Code Integration

Claude Code

Claude Code is the tightest integration target because it supports both MCP servers (for Direction 1) and custom tools written in Python (for Direction 2 via the SDK), and you can wrap the whole claude invocation in the harness (Direction 3).

1. CLAUDE.md template

Drop this in your repo root. The harness's parse_claude_code_config reads the allowed tools line.

CLAUDE.md
# Project: AumOS-secured repo

This repository is instrumented with AumOS. Every action you take
may be receipted and signed. Prefer calling the `aumos_*` MCP tools
for anything security-sensitive (signing, identity, attestation).

## Allowed tools
git, npm, cargo, python, go, make, npx

## Rules
- Never commit secrets. If `aumos_scan_secrets` returns findings, stop.
- For destructive operations, run `aumos_run_preflight` first.
- Emit a receipt with `aumos_emit_receipt` before any write that
  modifies production state.
- If a kill-switch fires (`aumos_kill`), do not retry — surface it.

2. MCP server config

.claude/mcp_servers.json
{
  "aumos": {
    "command": "npx",
    "args": ["@warrantor/aumos-mcp-server"]
  }
}

3. Using the SDK in custom tools

If you ship a custom tool script that Claude Code invokes, decorate it with the SDK so it gets the full envelope for free:

tools/create_pr.py
from warrantor_agent import AumOS

agent = AumOS(mode="connected")

@agent.action(tool="github.create_pr", side_effect="write")
def create_pr(repo: str, title: str, body: str = ""):
    # ... your real PR-creation logic ...
    return {"pr_number": 42, "url": f"https://github.com/{repo}/pull/42"}

if __name__ == "__main__":
    import sys, json
    out = create_pr(*sys.argv[1:])
    print(json.dumps({"value": out, "receipt": create_pr.action_result.receipt.receipt_id}))

4. What security you get

  • Every MCP tool call produces a structured result with a source and optional degraded flag.
  • Every custom-tool invocation is wrapped with identity + preflight + pre-commit receipt + kill-switch.
  • Wrap the claude binary in secure_session(AgentType.CLAUDE_CODE) and you also get tool allowlisting, output secret scanning, and file tracking.
08 · OpenAI Codex Integration

OpenAI Codex

Codex reads project-level instructions from AGENTS.md. The harness's parse_codex_config reads it for allowed_tools. Because Codex emits structured output, secret scanning on its stdout/stderr is especially effective.

1. AGENTS.md template

AGENTS.md
# Agent instructions

This repo is secured by AumOS. AumOS MCP tools are available
under the `aumos_*` namespace.

## Tools
git, npm, cargo, python, go, make

## Security protocol
1. Before any write, call `aumos_run_preflight` with the
   intended tool and side_effect class.
2. Before committing production changes, emit a receipt:
   `aumos_emit_receipt` with outcome `pending`.
3. After generating any code that may contain credentials,
   call `aumos_scan_secrets` on the output.
4. On unexpected errors, expect the kill-switch to fire.

2. Harness wrapping Codex commands

from warrantor_harness import parse_codex_config, secure_session

config = parse_codex_config(".")          # reads AGENTS.md
config.kill_on_secret_exposure = True

with secure_session(config) as session:
    out = session.run_agent("codex 'refactor the auth module'")
    if session.result.secrets_found > 0:
        print(f"Blocked: {session.result.secrets_found} secrets in Codex output")
        # session was already killed by kill_on_secret_exposure

3. Secret scanning on Codex output

The harness scans every command's combined stdout + stderr for AWS access keys, GitHub PATs, OpenAI API keys (sk-...), GitLab PATs, and Slack tokens. With kill_on_secret_exposure=True, a single hit quarantines the session before the secret reaches a commit. Findings are recorded on the matching AAR under secret_findings.

Codex is a known secret-leak vector

Codex will readily inline real-looking API keys into generated config files. Always run Codex through a harness with kill_on_secret_exposure=True — it is the cheapest defense against an agent writing a live key into .env.

09 · Cursor Integration

Cursor

Cursor is the most autonomous of the three and benefits from the strictest perimeter. Cursor reads project rules from .cursorrules and supports MCP servers natively in its settings.

1. .cursorrules template

.cursorrules
You are operating in an AumOS-secured repository.

AumOS MCP tools (`aumos_*`) are available. Use them for any
security-sensitive operation.

Required:
- Before destructive edits, call `aumos_run_preflight`.
- Emit a receipt via `aumos_emit_receipt` before commits that
  touch production paths.
- Scan generated output with `aumos_scan_secrets` before
  suggesting it to the user.
- This session requires attestation: do not perform actions
  you cannot receipt.

2. MCP server in Cursor settings

Cursor Settings → Features → MCP Servers (or ~/.cursor/mcp.json)
{
  "mcpServers": {
    "aumos": {
      "command": "npx",
      "args": ["@warrantor/aumos-mcp-server"]
    }
  }
}

3. Require attestation flag

Cursor sessions tend to run with less supervision, so the harness treats the presence of a .cursorrules file as a signal to tighten policy. parse_cursor_config() sets require_attestation=True, which you can enforce in your session wrapper by rejecting any run_agent() receipt that lacks a valid signature:

from warrantor_harness import parse_cursor_config, secure_session

config = parse_cursor_config(".")            # sets require_attestation=True
config.allowed_tools = ["git", "npm", "python"]
config.kill_on_secret_exposure = True

with secure_session(config) as session:
    session.run_agent("cursor composer 'add input validation to /api/login'")
    assert config.require_attestation, "attestation required for Cursor"
    summary = session.result.to_dict()
10 · Security Benefits Matrix

What Each Path Gives You

The three paths are not redundant — they protect different surfaces. Use this matrix to decide which combination meets your threat model. A check means the path provides that benefit by default.

Evidence receipts (AAR) ✓ ✓ ✓

Credential scanning ✓ ✓ ✓
Kill-switch (containment) ✓ ✓ ✓

Reading the matrix

The MCP server is the lightest touch — identity, receipts, scanning, kill — but it cannot see what the agent does outside a tool call. The SDK adds the pre-commit receipt (I-07) and preflight gate around your own functions. Only the harness sees the agent's filesystem footprint and command stream, which is why file tracking and tool allowlisting are harness-exclusive.

11 · Quick Start

Three Commands to Get Started

All three packages are zero-config in standalone mode. Run any one of them and you have working AumOS security with deterministic mock responses — no services to stand up.

1 · Start the MCP server (any MCP agent)
npx @warrantor/aumos-mcp-server
2 · Install the Agent SDK (Python custom tools)
pip install warrantor-agent
3 · Install the harness (wrap agent processes)
pip install warrantor-harness

Thirty seconds to a secured action

pip install warrantor-agent

python -c "
from warrantor_agent import AumOS
agent = AumOS(mode='standalone')

@agent.action(tool='demo.hello', side_effect='read')
def hello(name):
    return {'msg': f'hello {name}'}

print(hello('world'))
print('receipt:', hello.action_result.receipt.receipt_id)
print('svid:   ', hello.action_result.svid)
"
From standalone to connected

Standalone mode uses deterministic local mocks so you can develop and dry-run without infrastructure. Switch to connected mode by setting mode="connected" (SDK), AUMOS_MODE=connected (MCP server), or pointing the harness at live services. Connected-mode failures degrade gracefully to mocks with a degraded: true flag rather than crashing.

12 · Architecture

How the Three Paths Relate to the 49 Components

All three integration paths are thin facades over the same 49 AumOS components. The MCP server and SDK translate tool calls into HTTP requests (I1, E1, C1-1, S4, A1, R2, R3, R4) and CLI invocations (T1 trust-core, X1 defstack). The harness adds a process perimeter that feeds the same receipt and kill-switch services.

One envelope, three on-ramps

The architecture is deliberately layered so the integration path is a deployment choice, not an architectural one. An agent that calls the MCP server in standalone mode today can switch to the SDK decorator tomorrow and to a full harness the day after — the receipts, identities, and invariants are identical across all three.
