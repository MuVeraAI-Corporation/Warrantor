Important Framing

The repo's own docs/final-verification-report.md claims "691 tests passing, feature-complete at v1.0.0". Many of the issues below contradict that claim. Most "implementations" are stubs the report admits are deferred to "task 03" — but the security invariants (I-02, I-05, I-07, I-08, I-09) are advertised as shipping in v1.0.0 and several of them are broken at the cryptographic level. The repo is best understood as a comprehensive architectural specification with reference-shape implementations, not as deployable v1.0 software.

Critical Findings — Security Invariants That Do Not Hold

These are cryptographic-level breaks where the security claim is actively false. They are not "missing features" — they are claims that the code makes but does not deliver.

C1. Canonical CBOR is NOT deterministic — cross-language signing contract is broken

SeverityCritical — blocks production
ComponentT1 trust-core (the "single authoritative implementation of every security invariant")
Filerust/trust-core/src/canonical.rs:26-30 and rust/trust-core/Cargo.toml:20

What's wrong: The doc comment claims RFC 8949 §4.2.2 determinism ("Map keys sorted by length-first then bytewise"). The implementation is serde_cbor::to_vec(value) with no features enabled. Cargo.toml declares serde_cbor = "0.11" with no features = ["deterministic"]. Without that feature, serde_cbor does NOT sort map keys — it serializes in map-iteration order. The library is also unmaintained (deprecated upstream).

Consequence: Two different CBOR encodings (and therefore two different signatures) can be produced for the same logical payload depending on HashMap iteration order. The determinism_same_input_same_output test passes only because it uses a BTreeMap (which is already sorted). The whole T1 cross-language contract advertised in the README ("locks this cross-language contract") is not actually locked.

Fix: Switch to a maintained crate (ciborium with explicit canonicalization, or coset), explicitly enable the deterministic feature, and add a golden vector that uses an unordered map (e.g. an IndexMap or round-tripped Value) so this can't regress.

C2. flight-recorder canonical_bytes is unambiguous-concatenation — signature collision forgery

SeverityCritical — blocks production
ComponentE1 flight-recorder (the AAR issuer — invariant I-07 keystone)
Filerust/flight-recorder/src/lib.rs:160-187

What's wrong: The AAR canonical encoding is out.extend_from_slice(field1); out.extend_from_slice(field2); … with no length prefixes or delimiters. The comment claims this "is just as verifiable cross-language [as CBOR]". It is not — it is ambiguous. Concrete forgery: a receipt with tool_or_api_op = "github.create_pr" followed by approvers = ["abc"] produces the same canonical bytes as tool_or_api_op = "github" followed by approvers = ["create_prabc"]. An attacker who controls any two adjacent variable-length fields can construct a second valid receipt that verifies against the original signature.

The same anti-pattern appears in provena-chain/src/lib.rs:70-84 (Entry::canonical_bytes) and provena-chain/src/lib.rs:250-255 (checkpoint canon).

Fix: Length-prefix every field (TLV) or use real canonical CBOR. Length-prefix is mandatory for any concatenation-based canonicalization.

C3. eval-guard signature does NOT cover actual check results — fail-closed bypass

SeverityCritical — blocks production
ComponentR2 eval-guard (invariant I-09: fail-closed)
Filerust/eval-guard/src/lib.rs:148-153 (signing) and 186-190 (verify)

What's wrong: The signature covers only passed_checks (as proto ints) || nonce — but passed_checks is always the constant BoundaryCheck::ALL (lines 150-152 and 187-189 hardcode the loop over BoundaryCheck::ALL, not over the actual results). The real CheckResults that decided whether to issue the attestation is never bound into the signature.

Consequence: An attacker who obtains one signed attestation can present it as proof that all four checks passed for ANY future sandbox — the attestation carries no binding to the host, the timestamp, or the actual results it represents. A single attestation is a permanent skeleton key.

Fix: The signed message must include (a) the actual per-check results, (b) a fresh timestamp within a tight freshness window, (c) a binding to the target host/agent SVID.

C4. GPU attestation nonce is never verified — replay attack

SeverityCritical — blocks production
ComponentsC1-1 nvtrust-bridge, C1-2 cuda-gram
Filesrust/nvtrust-bridge/src/lib.rs:107-123; python/cuda_gram/src/cuda_gram/__init__.py:122-133

What's wrong: The CLAUDE.md, RFC, and proto comment all say "16-byte nonce used to prevent replay". But neither backend checks that the nonce in the report equals the nonce the verifier sent. nvtrust-bridge MockBackend returns Ok(()) iff attestation_bytes == b"aumos-mock-attestation" — the nonce is ignored entirely. This is the textbook replay attack against challenge-response attestation.

Fix: verify must take the challenge nonce as an argument and reject any report whose report.nonce != challenge. establish_session must require a caller-supplied nonce from os.urandom(16).

C5. agent-identity "audience" check is a no-op — confused-deputy defense is fictional

SeverityCritical — blocks production
ComponentI1 agent-identity (the keystone)
Filego/agent-identity/service.go:127-132

What's wrong: The "confused-deputy defense" code checks strings.HasPrefix(claims.Issuer, "spiffe://"+g.svc.trustDomain). But claims.Issuer is always set to fmt.Sprintf("spiffe://%s/agent-identity", s.trustDomain) at issue time. So this condition is always false — the check literally cannot fail for any token this service issued. Furthermore, the SVID token type has no aud field at all. The audience supplied by the caller is compared to nothing relevant.

Consequence: Any SVID accepted by this service can be replayed against any audience. The P2 spec explicitly lists "Confused deputy — an instance presented to the wrong audience is rejected" as a mandatory adversarial vector; the implementation does not provide this property.

C6. authority-spec AAE validator takes canonical bytes from the caller — signature is meaningless

SeverityCritical — blocks production
ComponentT2 authority-spec (the AAE validator)
Filerust/authority-spec/src/lib.rs:179-197

What's wrong: validate(envelope, unsigned_canonical_cbor, options) verifies the signature over a byte buffer that the caller supplies separately from the envelope. The validator never recomputes the canonical bytes from the envelope's own fields. If a caller passes any bytes that match the signature, the validator will say the envelope is valid regardless of what the envelope actually contains. The signature does not bind to the envelope contents in the validator.

Fix: The validator must reconstruct canonical bytes from the envelope itself (via T1's canonical_cbor) before verifying. The caller must never be allowed to supply the to-be-verified bytes.

C7. kill-switch Government Compliance API silently fakes confirmed: true

SeverityHigh — compliance blocking
ComponentR3 kill-switch
Filerust/kill-switch/src/lib.rs:24 (URL constant), 178-185 (notify_government_api)

What's wrong: GOVERNMENT_API_URL = "https://gov.killswitch.api/v1" is presented as the AI Kill Switch Act endpoint. The implementation returns Ok(GovernmentAck { ack_id: format!("ack-{order_id}"), confirmed: true }) — it never makes any HTTP call, never contacts any government service, and confirmed: true is a literal constant. For a kill triggered by a RegulatoryOrder, the law requires notification; the code reports confirmed: true without doing it.

Fix: Either ship the real call or return confirmed: false / a not-yet-implemented error. Reporting confirmed: true for a stub is the worst of both worlds.

High Findings — Cross-Component Integration & Production Gaps

H1. AAR to_proto swallows malformed hex with unwrap_or_default()

ComponentE1 flight-recorder → P2 proto contract
Filerust/flight-recorder/src/lib.rs:131-155

hex::decode(&self.authority_hash_hex).unwrap_or_default() silently produces bytes {} on malformed hex. Downstream proto consumers see empty signature/authority hash while the Rust-side receipt "verifies" because verify uses the hex strings directly. The proto contract is not what's actually signed.

H2. Go agent-identity JSON wire shape does NOT match the proto

ComponentI1 agent-identity (Go) ↔ proto IssueIdentityResponse
Filego/agent-identity/service.go:29-34 vs proto/aumos/identity/v1/agent.proto:77-83

Mismatches: (a) capability_jti vs capability_token — different field names AND different content. (b) Go adds a verifying_key field absent from the proto. (c) Go omits the timestamp wrapper. Also: the capability token is never actually issued (_ = capJTI).

H3. Cross-language conformance covers only 1 raw-byte Ed25519 vector

ComponentA6 conformance
Filetools/conformance/run.sh:54-128

The entire "cross-language conformance lane" is one Ed25519 signature over the literal bytes "hello aumos conformance". The bytes are verified raw — NOT on canonical_cbor(payload). The conformance does not exercise the canonicalization the actual T1 API uses. The testvectors/README.md promises C1-1/C1-2/R2/R3/R4/I1/P1/P2 vectors — none exist.

H4. No CDDL/JSON-Schema for 11 of the 12 protocols

ComponentProtocol completeness
Filespecs/protocols/ — only P1-aae.cddl and P1-aae.schema.json exist

Each protocol spec file claims "normative schema lives at ... CDDL" but only P1 actually has CDDL + JSON-Schema. P2–P12 each have only a markdown sketch.

What's Actually Solid

To be fair — these things ARE correct
  • #![forbid(unsafe_code)] and #![deny(missing_docs)] are consistently applied across all Rust crates.
  • The domain_matches suffix logic in egress-filter correctly rejects TLD-only patterns and notpastebin.com.
  • The Luhn implementation in exfil-guard is correct and tested.
  • The token-bucket math in inference-proxy is correct.
  • The delegation intersection logic in agent-identity (invariant I-02) is correctly implemented as subset checks.
  • The AAE validator's structural checks (expiry, side-effect-class, I-08 approval, delegation depth) are correct independent of the signature-binding problem in C6.
  • The TRT-LLM v0.16 sampler_type version-detection logic in bridge-rt is correct across 7 version cases.
  • The DPSGD clip-then-noise math and RDP accountant in dp-crate are correct.

Bottom Line

The 49 components are not "feature-complete at v1.0.0" with "security invariants shipping". The cryptographic spine that is supposed to make them trustworthy has multiple independent breaks. The repo is best understood as a comprehensive architectural specification with reference-shape implementations, not as deployable v1.0 software.

Any one of C1–C6 is sufficient to block production deployment of the corresponding security claim. The conformance / "691 tests passing" framing masks the fact that almost every "implementation" is a documented stub. The critical path to production:

  1. Fix canonical encoding (C1) — switch to ciborium with explicit canonicalization. This unblocks every cross-language signing contract.
  2. Fix canonical_bytes in flight-recorder and provena-chain (C2) — length-prefix every field.
  3. Fix eval-guard attestation binding (C3) — include actual results + timestamp + host binding.
  4. Fix nonce verification (C4) — check report.nonce == challenge in all attestation paths.
  5. Fix audience check (C5) — add aud claim, bind at issue, reject at verify.
  6. Fix AAE validator (C6) — reconstruct canonical bytes from the envelope itself.
  7. Fix government API stub (C7) — return confirmed: false until the real call ships.
  8. Expand conformance (H3) — add canonical-CBOR vectors, protocol vectors, adversarial vectors.
