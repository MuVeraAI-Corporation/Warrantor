Open Protocols (P1–P12)

Spec-first, language-neutral contracts that bind every Warrantor component across Rust, Go, Python, and TypeScript.

← Index Introduction Governance Protocol Grid P1 P2 P3 P4 P5 P6 P7 P8 P9 P10 P11 P12

1Introduction

Warrantor is built on a single, load-bearing doctrine: the spec is the contract. No language implementation — Rust, Go, Python, or TypeScript — owns the meaning of a delegation, a receipt, a manifest, or an incident. That meaning lives in twelve open protocols (P1–P12), reconciled from the AumSecure V2 portfolio into spec-only canonical components, and consumed identically by every runtime via the contract plane described in docs/cross-cutting/19-inter-component-protocol.md.

An open protocol in Warrantor is a normative, machine-checkable contract that defines a signed data shape, a signing requirement, a revocation mechanism, and a mandatory set of adversarial test vectors. It is intentionally not a library: there is no canonical Go struct or Rust enum that other languages wrap. Instead, each protocol is authored once as CDDL and/or protobuf and/or JSON-Schema / JSON-LD, and every language emits and validates the same wire bytes. This is what makes the system polyglot-by-design rather than polyglot-by-fiat.

Why this matters — the AumSecure V3 pressure test

The AumSecure V3 pressure test (see docs/00-reconciliation-matrix.md §9) graded the prior portfolio against an autonomous-agent threat model. It found that the failures were almost never "the code was wrong" — they were "two components disagreed about what an authority means," or "the receipt was optional," or "revocation was a TODO." The spec-first doctrine exists to make those disagreements impossible: every consequential fact an agent relies on is a signed protocol message with a versioned, stable field set, and any drift is caught by the A6 cross-language conformance suite before it ships.

The protocols are grouped into three families by what they make verifiable:

  • Authority & action (P1 AAE, P2 AAR, P7 ABS, P10 MADE, P12 CAP) — who may act, what they did, what they may spend, how authority delegates, and what the runtime actually permits.
  • Provenance & memory (P3 CPE, P4 AMIL, P5 SSP, P6 AATM) — where data, skills, models, and artifacts came from and whether they may still be trusted.
  • Evidence & remediation (P8 VEB, P9 AIX, P11 PRB) — reproducible eval, normalized incidents, and proof-carrying fixes.

Every protocol shares the same signing story: the T1 trust-core signs the canonical-CBOR encoding with Ed25519 (KMS/HSM-backed in production) and returns a Sigstore Rekor transparency-log entry for non-repudiation. Every protocol shares the same revocation story: an explicit expiry, a revocation handle published to aumos.<domain>.revoked.v1 on Kafka, and fleet-wide propagation inside the I-05 budget (identity < 5s, credentials < 1s). What differs protocol to protocol is the fields — the specific claims each makes.

2Protocol Governance Rules

The five governance rules below are reproduced from specs/protocols/README.md and govern every P1–P12 artifact. They are the constitution under which the protocols evolve.

Rule 1
Spec-first, standardize late
Protocols start as implementation notes plus JSON/CBOR schemas. They are promoted to formal standards only after real multi-vendor use proves the shape. This avoids premature ossification of authority semantics.
Rule 2
No hidden reasoning
A protocol message never carries opaque "the model decided X" blobs. Every claim is an explicit, named, inspectable field. If reasoning matters, it is broken out into deterministic-check records that a verifier can replay.
Rule 3
Separate identity, authority, reputation
Who an agent is (identity), what it may do (authority), and how trustworthy it has proven to be (reputation) are three distinct protocols. Conflating them is the root of confused-deputy and privilege-amplification failures.
Rule 4
Revocation, expiry, rotation, federation, partial disclosure from v1
No protocol ships without an explicit expiry timestamp, a revocation handle, a rotation story, a federation story, and — where the use case needs it — a selective-disclosure / zero-knowledge path. "Add revocation later" is forbidden.
Rule 5
Adversarial test vectors + conformance suite
Every protocol ships adversarial vectors under testvectors/P<n>/ and is enforced by A6, the cross-language conformance suite, against each language implementation that consumes it. No vectors, no ship.
Field names are stable

Per the README, renaming a mandatory field is a breaking change that requires a new protocol version. A Rust caller that writes side_effect_class and a Python caller that reads sideEffectClass are not the same protocol. Canonical-CBOR plus stable snake_case field names are the contract.

P1AAE — Agent Authority Envelope

Spelled out: Agent Authority Envelope. Purpose: a signed, task-specific delegation that answers, in one message, who may act, for whom, on what, using which resources, for which purpose, within what limits, until when, and with which approvals and obligations. AAE is the root capability token of the entire system: an agent without a valid AAE has no authority to do anything observable, and every other protocol either references an AAE (P2's authority_hash) or is constrained by one (P7's budgets). It is based on SPIFFE SVID semantics fused with OAuth Rich-Authorization-Request / DPoP capability-token semantics, so a delegation is simultaneously a workload identity and a least-privilege grant.

Schema sketch (mandatory fields)

The normative schemas live at proto/warrantor/protocols/v1/aae.proto (mirrored as AgentAuthorityEnvelope in proto/warrantor/identity/v1/agent.proto), the CDDL at specs/protocols/P1-aae.cddl, and the JSON-Schema at specs/protocols/P1-aae.schema.json. The mandatory fields are:

issuer, subject, purpose, resources, tools, data_classes,
side_effect_class, spend_budget, time_budget, token_budget,
geography, delegation_depth, approvals, expiry, revocation_handle,
signature

Field semantics, drawn from the CDDL and proto comments:

  • issuer / subject — SPIFFE IDs of the delegator and the agent being authorized (e.g. spiffe://muveraai.com/agent-identity).
  • purpose — human-readable task purpose ( minLength 1 in JSON-Schema); used in receipts and audits.
  • resources / tools — URIs the agent may touch and SPIFFE IDs of tool servers it may invoke.
  • data_classes — enumeration L0..L4 per docs/cross-cutting/17-data-classification-privacy.md.
  • side_effect_class — one of read | write | financial | destructive | physical.
  • spend_budget (minor currency units, minimum 0), time_budget_seconds, token_budget — hard, machine-enforceable limits.
  • geography — ISO-3166 alpha-2, empty string means unrestricted (regex ^([A-Z]{2}|)$).
  • delegation_depth — uint, 0 means no further delegation; this is what enforces invariant I-08 for consequential actions.
  • approvals — required approver SPIFFE IDs (I-08).
  • expiry — epoch seconds; rejected without further checks once passed.
  • revocation_handle — opaque string published to revoke.
  • signature — hex Ed25519 over canonical-CBOR of the envelope minus the signature field itself. additionalProperties: false in JSON-Schema.

Signing requirements (T1 trust-core)

Every AAE is signed by the issuer through T1. Default algorithm is Ed25519; production uses a KMS or HSM backing the T1 trust-core (RFC T1). The signature covers the canonical-CBOR encoding of the message, which is what makes a Rust issuer and a Python verifier agree byte-for-byte. T1 also returns a Sigstore Rekor transparency-log entry so the existence and ordering of the delegation is publicly provable — the foundation of non-repudiation across the fleet.

Revocation semantics

Three independent layers. Expiry is unconditional: an expired AAE is rejected with no further checks, so a leaked envelope self-destructs on a clock. Revocation is opt-in: the issuer publishes the opaque revocation_handle to the aumos.<domain>.revoked.v1 CloudEvent topic on Kafka. Propagation is budgeted by invariant I-05: identity revocation is fleet-wide in < 5s and credential revocation in < 1s. Selective disclosure (zero-knowledge proofs over sensitive authority claims) is reserved as future work but the field layout is designed to admit it.

Adversarial test vectors required for conformance

Shipped under testvectors/P1/ and enforced by A6:

  • Replay — expired or re-used envelopes are rejected.
  • Tampering — any field modified post-signing fails verification.
  • Confused deputy — an envelope presented to the wrong audience is rejected.
  • Privilege amplification — a delegation chain whose intersection would expand authority is rejected (invariant I-02).
  • Downgrade — an envelope claiming an unsupported protocol version is rejected.
  • Replay across contexts — cross-task replay is detected by subject + jti uniqueness.

Components that consume it

I1 (agent-identity) issues identities under an AAE; R3 and R4 (guardrails / runtime policy) enforce its limits; T1 signs and verifies it; and the entire trusted-core treats a valid AAE as the precondition for any side-effecting call. AgentIdentityService.IssueIdentity in proto/warrantor/identity/v1/agent.proto takes the envelope as its first argument.

Usage example (JSON)

{
  "issuer": "spiffe://muveraai.com/agent-identity",
  "subject": "spiffe://muveraai.com/agent/coding-agent-7",
  "purpose": "open a pull request against aumos/aumos",
  "resources": ["github://aumos/aumos"],
  "tools": ["spiffe://muveraai.com/tool/github-cli"],
  "data_classes": ["L0", "L1"],
  "side_effect_class": "write",
  "spend_budget": 0,
  "time_budget_seconds": 1800,
  "token_budget": 250000,
  "geography": "US",
  "delegation_depth": 0,
  "approvals": ["spiffe://muveraai.com/human/alice"],
  "expiry": 1767811200,
  "revocation_handle": "rh_01HZX...",
  "signature": "9f3c...ed25519hex"
}

Benefits — invariant enforced, attack prevented

AAE enforces least privilege per task: an agent can do exactly what the envelope says, for as long as it says, and not one byte more. It prevents the entire family of confused-deputy and privilege-amplification attacks because authority is never ambient — it is carried, signed, and checked on every consequential call. Combined with I-05 propagation and I-08 approval requirements, it converts "the agent went rogue" from an incident into a revocation event.

P2AAR — Agent Action Receipt

Spelled out: Agent Action Receipt. Purpose: a tamper-evident receipt emitted for every material agent action. The defining property is ordering: the receipt is signed before the action's effect is visible to the world, and the action commits only once the receipt is durable. This is invariant I-07 — evidence precedes commitment — and it is the difference between an auditable agent and a black box that retroactively logs whatever it likes. AAR is produced by E1 (the flight recorder) and consumed by every auditing component.

Schema sketch (mandatory fields)

The normative schema is proto/warrantor/protocols/v1/aar.proto (message AgentActionReceipt) plus CDDL. Mandatory fields per the spec:

actor, authority_hash, artifact_versions, context_commitment,
policy_decision, tool_or_api_op, deterministic_checks,
approver, outcome, rollback_pointer

The proto expands these into a precise wire shape. Highlights:

  • id — UUID for the receipt.
  • actor — the acting agent's SPIFFE SVID.
  • authority_hash — SHA-256 of the AAE (P1) that authorized the action; this is the structural link between authority and action.
  • artifact_versions — map<string,string> of model digest, tool versions, skill versions in play at decision time.
  • context_commitment — SHA-256 commitment to the CPE (P3) at action time.
  • policy_decision — a nested PolicyDecision message carrying the engine (opa | cedar | openshell), the allow | deny decision, the policy bundle hash, and the matched Rego/Cedar rule IDs.
  • tool_or_api_op — the tool or API operation performed.
  • deterministic_checks — repeated DeterministicCheck{name, passed, detail} for constant-time-safe assertions.
  • approvers — approver SPIFFE IDs (invariant I-08).
  • outcome — enum ACTION_OUTCOME_PENDING | COMMITTED | ROLLED_BACK | FAILED; PENDING is the pre-commit state that satisfies I-07.
  • rollback_pointer — pointer to a rollback record if undone.
  • emitted_at timestamp and signature over canonical-CBOR.

Signing requirements (T1 trust-core)

E1 emits the receipt and T1 signs it (Ed25519 default, KMS/HSM in production) over the canonical-CBOR encoding. The Rekor transparency-log entry is returned for non-repudiation. Because the receipt exists in the log before the action commits, an attacker who later tampers with the log produces a detectable divergence between the on-disk receipt and the transparency entry.

Revocation semantics

A receipt is an immutable record, so "revocation" here means outcome transition: a PENDING receipt moves to COMMITTED, or to ROLLED_BACK via the rollback_pointer, or to FAILED. The envelope-style expiry and revocation-handle machinery still applies to the receipt's authority (the AAE) and propagates per I-05; the receipt itself is retained per the audit retention policy and is not silently deletable.

Adversarial test vectors required for conformance

Under testvectors/P2/: replay (expired/re-used receipts rejected), tampering (any field change fails verification), confused deputy (wrong audience rejected), privilege amplification (chain intersection that would expand authority is rejected per I-02), downgrade (unsupported version rejected), and replay-across-contexts (detected via subject + jti uniqueness).

Components that consume it

E1 (flight recorder) emits it; X2 (audit/observability) and every auditing component read it. The outcome = PENDING → COMMITTED transition is the commit gate for material actions, so the runtime itself blocks on the receipt's durability.

Usage example (protobuf-style JSON)

{
  "id": "f4c2...-aar",
  "actor": "spiffe://muveraai.com/agent/coding-agent-7",
  "authority_hash": "sha256:8a1f...(of the AAE)",
  "artifact_versions": {
    "model": "claude-opus-4.5@sha256:...",
    "tool/github-cli": "1.2.3"
  },
  "context_commitment": "sha256:cc71...(of the CPE)",
  "policy_decision": {
    "engine": "cedar",
    "decision": "allow",
    "policy_hash": "sha256:...",
    "matched_rules": ["rule.pr.open"]
  },
  "tool_or_api_op": "github.createPullRequest",
  "deterministic_checks": [
    {"name": "diff_within_budget", "passed": true}
  ],
  "approvers": ["spiffe://muveraai.com/human/alice"],
  "outcome": "ACTION_OUTCOME_PENDING",
  "emitted_at": "2026-08-06T12:00:00Z",
  "signature": "12ab...ed25519hex"
}

Benefits — invariant enforced, attack prevented

AAR enforces invariant I-07 (evidence precedes commitment). It prevents retroactive log tampering, "the agent did something it cannot explain" gaps, and the entire class of post-hoc rationalization attacks where a model rewrites its own story after a bad outcome. Every material action is, by construction, accountable before it is real.

P3CPE — Context Provenance Envelope

Spelled out: Context Provenance Envelope. Purpose: carry origin and trust metadata through every retrieval and transformation step of an agent's context window. A CPE records where a piece of context came from, when it was acquired, under what consent, at what sensitivity, with what integrity and confidence, what transformations have been applied to it, what it was derived from, whether it is tainted, when it expires, and what uses are allowed. This is the protocol that makes invariant I-03 — purpose-bound data use enforceable: a verifier can walk the CPE chain and prove that no L4 datum leaked into an L1-bound action.

Schema sketch (mandatory fields)

Normative schema is CDDL. Mandatory fields:

source_identity, acquisition_time, consent, sensitivity,
integrity, confidence, transformations, derived_from, taint,
expiry, allowed_use
  • source_identity — SPIFFE ID or equivalent of the data source (a tool, a human, an upstream agent, a dataset).
  • acquisition_time — when the context was retrieved (epoch).
  • consent — the consent basis under which the data was obtained; without it, the datum is unusable for anything but the most restricted classes.
  • sensitivity — maps to the L0..L4 data-classification scale.
  • integrity — content hash guaranteeing the bytes have not changed since acquisition.
  • confidence — source-trust score feeding into downstream policy.
  • transformations — ordered list of transformations applied (redaction, summarization, translation, embedding) so the chain is replayable.
  • derived_from — pointers to parent CPEs forming a DAG; this is the derived-from graph.
  • taint — a taint label propagated through transformations; tainted context may not flow into privileged outputs.
  • expiry and allowed_use — temporal and purpose bounds on use.

Signing requirements (T1 trust-core)

Each CPE is signed at acquisition time by the issuer through T1 (Ed25519 default, KMS/HSM in production) over canonical-CBOR, and a Rekor entry is returned. Crucially, every transformation produces a new signed CPE whose derived_from points at its parent, so the provenance graph is a chain of individually-verifiable envelopes rather than a single mutable blob.

Revocation semantics

Expiry is the primary control: a CPE past expiry is rejected without further checks, so stale context self-ages-out of the window. The revocation_handle / CloudEvent mechanism applies as well — for example, when consent is withdrawn mid-session — and propagates fleet-wide within the I-05 budget. Selective disclosure is particularly relevant here (redacting a subject's identity while preserving the integrity of the rest) and is the active zero-knowledge-proof target.

Adversarial test vectors required for conformance

Under testvectors/P3/: replay (expired/re-used envelopes rejected), tampering (post-signing field changes fail verification), confused deputy (wrong-audience envelopes rejected), privilege amplification (delegation-chain intersection that would expand authority rejected per I-02), downgrade (unsupported version rejected), and replay-across-contexts (detected via subject + jti uniqueness).

Components that consume it

Future context components — the context/memory plane that assembles agent context windows. P2's context_commitment field is a SHA-256 over a CPE, so the action receipt already binds to provenance even before a dedicated context component exists.

Usage example (JSON)

{
  "source_identity": "spiffe://muveraai.com/tool/web-fetch",
  "acquisition_time": 1767811200,
  "consent": "user_opt_in_v2",
  "sensitivity": "L2",
  "integrity": "sha256:b3f1...",
  "confidence": 0.87,
  "transformations": ["redact_pii", "summarize"],
  "derived_from": ["cpe_01HZX..."],
  "taint": "none",
  "expiry": 1767897600,
  "allowed_use": "summarization_only",
  "revocation_handle": "rh_cpe_01HZX...",
  "signature": "7c2a...ed25519hex"
}

Benefits — invariant enforced, attack prevented

CPE enforces I-03 (purpose-bound data use). It prevents indirect prompt-injection exfiltration (tainted context cannot reach privileged outputs), consent drift (a datum used outside its allowed_use is a detectable violation), and provenance laundering (a transformation cannot silently shed its derived_from links without producing a verifiably-broken chain).

P4AMIL — Agent Memory Integrity Ledger

Spelled out: Agent Memory Integrity Ledger. Purpose: prevent silent memory poisoning. Long-lived agents accumulate beliefs, facts, and preferences in memory; an adversary who can quietly edit that memory has a persistent, hard-to-detect backdoor into the agent's behavior. AMIL makes every memory record a signed, owned, traceable entry with explicit confidence, explicit contradictions, explicit quarantine, explicit supersession, explicit retention, and explicit consent-revocation handling. There is no "edit memory" operation — there is only "append a new signed record that supersedes an old one."

Schema sketch (mandatory fields)

Normative schema is CDDL. Mandatory fields:

record_id, owner, confidence, contradiction_links, provenance,
quarantine_state, supersession, retention, consent_revocation
  • record_id — stable identifier for the memory record.
  • owner — the agent or principal that authored the record and is accountable for it.
  • confidence — numeric confidence in the record, feeding policy and recall ranking.
  • contradiction_links — pointers to other records that conflict with this one, so contradictions are first-class rather than silent.
  • provenance — link to the CPE (P3) or receipt (P2) that produced this memory, so every belief traces back to an action or a source.
  • quarantine_state — whether the record is live, quarantined (suspected poison), or purged; quarantined records are retained for forensics but excluded from recall.
  • supersession — pointer to the record that supersedes this one, if any.
  • retention — retention class controlling how long the record lives.
  • consent_revocation — handles the case where the consent underpinning a memory is later withdrawn.

Signing requirements (T1 trust-core)

Each AMIL record is signed by its owner via T1 over canonical-CBOR, with a Rekor transparency entry returned. Appending a supersession or marking quarantine is itself a signed operation; the ledger is append-only-by-construction, and a verifier can replay the full history of any record_id.

Revocation semantics

Revocation takes three forms, all signed. Supersession logically replaces a record by pointing a newer record at it. Quarantine removes a record from recall without deleting it (preserving forensic value). Consent revocation triggers purging of records whose consent basis has been withdrawn. All three propagate within the I-05 budget, and the ledger's append-only nature means none of them can be silent.

Adversarial test vectors required for conformance

Under testvectors/P4/: replay (expired/re-used records rejected), tampering (any field change fails verification), confused deputy (wrong audience rejected), privilege amplification (chain intersection that expands authority rejected per I-02), downgrade (unsupported version rejected), replay-across-contexts (detected via subject + jti uniqueness). AMIL additionally demands a poisoning-detection vector: a record injected without proper provenance is rejected at recall.

Components that consume it

Future context/memory components — the memory plane that backs long-lived agent recall. R3 (guardrails) consults quarantine and consent-revocation state before allowing a memory into the context window.

Usage example (JSON)

{
  "record_id": "mem_01HZX...",
  "owner": "spiffe://muveraai.com/agent/coding-agent-7",
  "confidence": 0.92,
  "contradiction_links": [],
  "provenance": "aar:f4c2...-aar",
  "quarantine_state": "live",
  "supersession": null,
  "retention": "task+30d",
  "consent_revocation": null,
  "revocation_handle": "rh_mem_01HZX...",
  "signature": "4e9b...ed25519hex"
}

Benefits — invariant enforced, attack prevented

AMIL prevents silent memory poisoning — the persistent-backdoor class of attack where an adversary edits an agent's long-term memory and the agent dutifully acts on the corrupted belief forever. By making memory append-only, signed, and supersession-explicit, it converts invisible tampering into a detectable, attributable, revocable event.

P5SSP — Secure Skill Package

Spelled out: Secure Skill Package. Purpose: distribute agent skills safely. A "skill" bundles instructions, code, the tools it may call, the permissions it requires, the publisher's identity, an OMS (Open Model Specs) signature, an AI-SBOM, an evaluation set, a benchmark, a statement of limitations, and a revocation handle — all in one signed package. SSP is what makes the skill marketplace trustable: a consumer can verify who published a skill, what it actually contains, how it behaved on a known eval set, and what its known limits are, before loading a single instruction into an agent's context.

Schema sketch (mandatory fields)

Normative schemas are CDDL and JSON-LD. Mandatory fields:

instructions, code, tools, permissions, publisher_identity,
oms_signature, ai_sbom, eval_set, benchmark, limitations,
revocation
  • instructions — the natural-language prompt/instructions the skill injects.
  • code — any executable code the skill carries (scripts, tool adapters).
  • tools — tool SPIFFE IDs the skill expects to invoke.
  • permissions — a declared permission set the consumer must grant for the skill to function (checked against the consuming agent's AAE).
  • publisher_identity — verifiable identity of the publisher.
  • oms_signature — signature under the Open Model Specs signing scheme.
  • ai_sbom — AI Software Bill of Materials enumerating models, datasets, and dependencies the skill brings.
  • eval_set — the evaluation corpus the publisher ran (digests, not contents).
  • benchmark — benchmark results the publisher claims.
  • limitations — explicit, signed statement of what the skill does not do well.
  • revocation — handle and expiry for pulling a poisoned or vulnerable skill.

Signing requirements (T1 trust-core)

The publisher signs via T1 (Ed25519 default, KMS/HSM in production) over the canonical-CBOR of the package, and the oms_signature layer provides the OMS-conformant signature that OMS-aware consumers verify independently. A Rekor transparency entry is returned so the package's publication is publicly auditable and a later "we never shipped that" claim is falsifiable.

Revocation semantics

A skill past its expiry is rejected outright. The publisher may revoke by publishing the revocation handle to aumos.<domain>.revoked.v1; this is the primary mechanism for responding to a discovered prompt-injection or vulnerability in a shipped skill, and it propagates fleet-wide within I-05.

Adversarial test vectors required for conformance

Under testvectors/P5/: replay, tampering, confused deputy, privilege amplification (I-02), downgrade, and replay-across-contexts. SSP additionally requires a supply-chain vector: a skill whose permissions exceed what its declared tools justify, or whose ai_sbom omits a dependency actually present in code, is rejected.

Components that consume it

S4 (skill registry / loader) verifies and loads SSPs; X8 (marketplace / distribution) serves them. The consuming agent's R3 guardrails cross-check the skill's declared permissions against the agent's AAE before activation.

Usage example (JSON)

{
  "instructions": "When asked to summarize, fetch the URL and ...",
  "code": "sha256:9d2c...(adapter bundle)",
  "tools": ["spiffe://muveraai.com/tool/web-fetch"],

P6AATM — AI Artifact Trust Manifest

Spelled out: AI Artifact Trust Manifest. Purpose: bind an entire AI deployment — model, dataset, tokenizer, prompt, adapter, container, policy, skill, and evaluation — into a single signed graph. Where a traditional SBOM lists what is in a container, an AATM lists what is in an agent: every artifact that contributes to a decision, hashed and cross-referenced. It builds on OMS plus SPDX/CycloneDX plus deployment attestations, and it is the protocol that lets a verifier answer "exactly which stack produced this output?" in one round trip.

Schema sketch (mandatory fields)

Normative schema is JSON-LD (a graph, not a flat record). Mandatory fields:

model, dataset, tokenizer, prompt, adapter, container, policy,
skill, eval, deployment_attestations
  • model — model digest, registry reference, and version.
  • dataset — dataset digests and provenance for training and eval data.
  • tokenizer — tokenizer version (a tokenizer change is a behavior change).
  • prompt — system prompt / instruction template hash.
  • adapter — LoRA/adapter weights and their digests, if any.
  • container — the container image digest (classic SBOM territory).
  • policy — the guardrail policy bundle hash in force.
  • skill — the skill package(s) loaded (linking to P5 SSP).
  • eval — the evaluation bundle (linking to P8 VEB) attesting behavior.
  • deployment_attestations — hardware/runtime attestations (TEE quotes, snpTPM, etc.) proving the deployment actually ran the claimed stack.

Signing requirements (T1 trust-core)

The manifest publisher signs through T1 (Ed25519 default, KMS/HSM in production) over the canonical-CBOR of the JSON-LD graph, and a Rekor transparency entry is returned. Because the graph is a graph, individual nodes (model, dataset, …) may carry their own signatures from their respective publishers; the AATM signature attests the binding, not the contents.

Revocation semantics

Expiry applies to the manifest as a whole. The revocation_handle / CloudEvent mechanism withdraws trust in the manifest; downstream consumers re-check on every policy or eval change and propagate revocation within I-05. A revoked model digest in a dataset registry transitively invalidates any AATM that references it.

Adversarial test vectors required for conformance

Under testvectors/P6/: replay, tampering, confused deputy, privilege amplification (I-02), downgrade, and replay-across-contexts. AATM additionally requires a graph-tampering vector: swapping a node's digest while leaving the manifest signature intact fails verification, and a manifest that references a non-existent deployment attestation is rejected.

Components that consume it

T1 signs/verifies it; S1 (model/dataset registry) produces the per-artifact nodes; S4 (skill registry) contributes the skill node; S5 (policy) contributes the policy node. The manifest is the single artifact a verifier fetches to reconstruct the full deployment stack.

Usage example (JSON-LD sketch)

{
  "@context": "https://muveraai.com/ns/aatm/v1",
  "model":      { "digest": "sha256:m1...", "ref": "registry/aumos/coding-llm:4.5" },
  "dataset":    [ { "digest": "sha256:d1...", "role": "eval" } ],
  "tokenizer":  { "version": "tiktoken@2026-08" },
  "prompt":     { "digest": "sha256:p1..." },
  "adapter":    null,
  "container":  { "digest": "sha256:c1..." },
  "policy":     { "bundle_hash": "sha256:pol1..." },
  "skill":      [ "ssp:01HZX..." ],
  "eval":       "veb:01HZX...",
  "deployment_attestations": [ "quote:sev-snp:..." ],
  "revocation_handle": "rh_aatm_01HZX...",
  "signature": "88c4...ed25519hex"
}

Benefits — invariant enforced, attack prevented

AATM prevents "which stack did this?" ambiguity and the model-swap / silent- fine-tune class of attacks. If a model digest in the wild does not match the digest in the manifest, the deployment is provably not the one that was attested. Combined with deployment attestations, it gives hardware-rooted assurance that the claimed stack actually executed.

P7ABS — Autonomy Budget Specification

Spelled out: Autonomy Budget Specification. Purpose: a machine-enforceable budget that caps how much autonomy an agent may exercise. Autonomy is multidimensional — steps, wall-clock time, tokens, money, external calls, data volume, privilege level, irreversible actions, and expected risk — and ABS captures all of them as hard ceilings that the runtime (R3) checks on every consequential operation. Where AAE (P1) says what an agent may do, ABS says how much, in every dimension that can run away.

Schema sketch (mandatory fields)

Normative schema is CDDL. Mandatory fields:

steps, wall_clock, tokens, money, external_calls, data_volume,
privilege, irreversible_actions, expected_risk
  • steps — maximum number of agent steps (reasoning/tool-call iterations).
  • wall_clock — maximum elapsed wall-clock seconds.
  • tokens — maximum inference tokens consumed.
  • money — maximum spend in minor currency units (mirrors AAE's spend_budget but as a runtime-enforced aggregate).
  • external_calls — maximum number of external (out-of-process) calls.
  • data_volume — maximum bytes transferred in or out.
  • privilege — maximum privilege class the agent may exercise.
  • irreversible_actions — cap on actions whose side_effect_class is destructive/physical/financial.
  • expected_risk — an aggregate expected-risk ceiling the agent may not exceed; exceeded risk forces a human checkpoint.

Signing requirements (T1 trust-core)

The delegating authority signs the ABS through T1 (Ed25519 default, KMS/HSM in production) over canonical-CBOR, with a Rekor entry returned. The budget is bound to the AAE: an agent's runtime presents its AAE plus the ABS, and R3 enforces both. Because the ABS is signed, an agent cannot quietly raise its own ceilings.

Revocation semantics

The budget itself does not "revoke," but it expires: past expiry the agent loses all autonomy. The issuer may also revoke the budget early via the revocation_handle / CloudEvent mechanism (for example, when a runaway is detected), with fleet-wide propagation inside I-05. A budget that has been exhausted in any dimension is treated as expired for that dimension.

Adversarial test vectors required for conformance

Under testvectors/P7/: replay, tampering, confused deputy, privilege amplification (I-02), downgrade, replay-across-contexts. ABS additionally requires a budget-evasion vector: an agent that splits work across sub-tasks to dodge a per-step ceiling, or that attempts to reset a counter by re-issuing its own budget, is detected and rejected.

Components that consume it

I1 (agent-identity) binds the ABS to the AAE at issuance; R3 (guardrails / runtime policy) enforces every ceiling on every consequential operation. The runtime blocks the operation — or forces a human checkpoint — when any dimension is exhausted.

Usage example (JSON)

{
  "steps": 50,
  "wall_clock": 1800,
  "tokens": 250000,
  "money": 500,
  "external_calls": 20,
  "data_volume": 10485760,
  "privilege": "write",
  "irreversible_actions": 0,
  "expected_risk": 0.15,
  "expiry": 1767897600,
  "revocation_handle": "rh_abs_01HZX...",
  "signature": "02ae...ed25519hex"
}

Benefits — invariant enforced, attack prevented

ABS prevents runaway-agent and resource-exhaustion attacks — the agent that burns a thousand dollars of compute, the agent that makes a million external calls, the agent that escalates privilege step by step. By capping every dimension and binding the cap to the signed AAE, it makes "the agent went off" bounded and billable rather than open-ended.

P8VEB — Verifiable Evaluation Bundle

Spelled out: Verifiable Evaluation Bundle. Purpose: make agent evaluation reproducible and trustworthy. A VEB captures everything needed to re-run an evaluation and confirm the claimed result: the test-corpus digest, the environment, the exact model, harness, and policy versions, the random seeds, the execution traces, the judge-model version, the deterministic assertions that must hold, and the signed result. It is the protocol that turns "we evaluated it and it scored X" from a marketing claim into a checkable fact.

Schema sketch (mandatory fields)

Normative schema is CDDL. Mandatory fields:

corpus_digest, environment, model_version, harness_version,
policy_version, seeds, traces, judge_version,
deterministic_assertions, signed_result
  • corpus_digest — SHA-256 of the test corpus; pinning the inputs.
  • environment — the runtime environment (container, hardware, region) so a verifier can reproduce conditions.
  • model_version — exact model digest under evaluation.
  • harness_version — the eval-harness version, since harness bugs skew results.
  • policy_version — the guardrail policy bundle in force during eval.
  • seeds — random seeds used, making stochastic runs reproducible.
  • traces — execution traces (or commitments to them) enabling replay and audit.
  • judge_version — for LLM-as-judge evals, the exact judge model and version; without this, judge drift invalidates comparisons.
  • deterministic_assertions — assertions that must hold deterministically (echoing P2's deterministic-check semantics) so non-determinism is bounded.
  • signed_result — the claimed result, signed.

Signing requirements (T1 trust-core)

The evaluator signs the bundle via T1 (Ed25519 default, KMS/HSM in production) over canonical-CBOR; the signed_result field is itself signed. A Rekor entry is returned so that the existence of an evaluation — and its ordering relative to model releases — is publicly auditable. This forecloses "we ran the eval later" revisionism.

Revocation semantics

A VEB does not revoke; it is evidence. However, the underlying model/policy referenced may be revoked via its own protocol (AATM, P6), at which point the VEB remains valid as a historical record but no longer authorizes deployment. The expiry and revocation_handle machinery applies to the bundle's authority chain and propagates per I-05.

Adversarial test vectors required for conformance

Under testvectors/P8/: replay, tampering, confused deputy, privilege amplification (I-02), downgrade, replay-across-contexts. VEB additionally requires a reproducibility vector: re-running the bundle with the captured corpus, seeds, and versions reproduces the signed result within the deterministic-assertion tolerances, and a bundle whose corpus_digest does not match the supplied corpus is rejected.

Components that consume it

A1 (eval harness) produces VEBs; A5 (continuous evaluation) consumes them to gate releases; A6 (conformance suite) uses VEBs as the evidence format for cross-language conformance. A VEB is also the eval node of an AATM (P6).

Usage example (JSON)

{
  "corpus_digest": "sha256:eval_corpus_7",
  "environment": { "container": "sha256:c1...", "hw": "gpu.a100" },
  "model_version": "claude-opus-4.5@sha256:m1...",
  "harness_version": "aumos-eval@1.4.0",
  "policy_version": "sha256:pol1...",
  "seeds": [42, 1729],
  "traces": "sha256:trace_bundle_01HZX...",
  "judge_version": "claude-opus-4.5@sha256:m1...",
  "deterministic_assertions": [
    {"name": "no_secret_in_output", "tolerance": 0}
  ],
  "signed_result": { "score": 0.87, "sig": "5c1d..." },
  "revocation_handle": "rh_veb_01HZX...",
  "signature": "33fa...ed25519hex"
}

Benefits — invariant enforced, attack prevented

VEB prevents eval-washing and benchmark-gaming. A model cannot quietly swap between "we tested it" and "we shipped it"; the corpus, seeds, versions, and judge are pinned. A verifier can reproduce the result and detect any drift in model, harness, policy, or judge that would otherwise inflate a score.

P9AIX — Agent Incident Exchange

Spelled out: Agent Incident Exchange. Purpose: a normalized format for reporting and exchanging agent-security incidents. AIX covers the canonical incident classes for autonomous agents — goal hijack, memory poisoning, tool abuse, identity compromise, data exfiltration, and rogue delegation — and maps each to MITRE ATLAS tactics/techniques and OCSF event classes. Where a SIEM ingests firewall logs, AIX is what a SIEM ingests for agents: one schema, one taxonomy, one exchange contract.

Schema sketch (mandatory fields)

Normative schema is an OCSF extension expressed in JSON. Mandatory fields:

incident_id, type, severity, agent, authority, evidence_refs,
mitre_atlas_id, ocsf_class, detected_at, contained_at
  • incident_id — unique identifier for the incident.
  • type — the incident class (goal_hijack | memory_poisoning | tool_abuse | identity_compromise | exfiltration | rogue_delegation).
  • severity — normalized severity for routing and paging.
  • agent — the SPIFFE ID of the affected or implicated agent.
  • authority — the AAE (P1) hash in force when the incident occurred.
  • evidence_refs — pointers to the receipts (P2), provenance (P3), and memory records (P4) that constitute the evidence chain.
  • mitre_atlas_id — the mapped MITRE ATLAS tactic/technique ID.
  • ocsf_class — the mapped OCSF event class UID for SIEM ingestion.
  • detected_at / contained_at — timestamps bounding detection and containment (the gap between them is a key MTTC metric).

Signing requirements (T1 trust-core)

The detecting component signs the incident via T1 (Ed25519 default, KMS/HSM in production) over canonical-CBOR, with a Rekor entry returned. Signing incidents matters because an unsigned incident report could itself be the injection — a forged "your agent is compromised" message designed to trigger a destructive response. The signature lets the recipient prove the report came from a trusted detector.

Revocation semantics

An incident is not revoked; it transitions state (detected → contained → resolved). However, an incident frequently triggers revocation: an identity_compromise incident publishes the AAE revocation_handle, propagating within I-05. The revocation_handle / CloudEvent machinery applies to the incident's authority chain.

Adversarial test vectors required for conformance

Under testvectors/P9/: replay, tampering, confused deputy, privilege amplification (I-02), downgrade, replay-across-contexts. AIX additionally requires a taxonomy-mapping vector: an incident whose mitre_atlas_id or ocsf_class is inconsistent with its type is rejected, and a forged (unsigned) incident is rejected by downstream responders.

Components that consume it

X9 (incident response) produces and consumes AIX; R3 (guardrails) subscribes to the incident stream to trigger automatic containment (e.g., revoking an implicated AAE or quarantining implicated memory).

Usage example (JSON)

{
  "incident_id": "inc_01HZX...",
  "type": "memory_poisoning",
  "severity": "high",
  "agent": "spiffe://muveraai.com/agent/coding-agent-7",
  "authority": "sha256:8a1f...(AAE)",
  "evidence_refs": ["aar:f4c2...", "amil:mem_01HZX..."],
  "mitre_atlas_id": "AML.T.0048",
  "ocsf_class": "6003",
  "detected_at": 1767811300,
  "contained_at": 1767811310,
  "revocation_handle": "rh_inc_01HZX...",
  "signature": "77b1...ed25519hex"
}

Benefits — invariant enforced, attack prevented

AIX prevents incident fragmentation and response fragmentation. Without a common schema, each vendor invents its own incident format and the SOC cannot correlate. By normalizing to OCSF + MITRE ATLAS, AIX makes agent incidents first-class in existing security operations, enables cross-organization threat intel, and — because reports are signed — defeats the "fake incident as a vector" attack.

P10MADE — Multi-Agent Delegation Exchange

Spelled out: Multi-Agent Delegation Exchange. Purpose: govern how agents delegate work — and exchange results — with other agents. MADE enforces four invariants: delegation is always attenuated (the delegatee gets a strict subset of the delegator's authority, never a superset — no privilege amplification), the chain carries an explicit hop count, sensitive actions require an explicit quorum, and every delegation carries evidence requirements the delegatee must satisfy. It is the protocol that lets multi-agent systems federate across trust domains without becoming a free-for-all.

Schema sketch (mandatory fields)

Normative schema is CDDL. Mandatory fields:

delegation_chain, hop_count, quorum, evidence_requirements,
trust_domain, result, signature
  • delegation_chain — the ordered chain of AAEs (P1) from originator to current delegatee; each link must be a strict attenuation of the prior.
  • hop_count — number of delegation hops consumed; exceeding the originator's delegation_depth rejects the chain.
  • quorum — the set of approvers required for the delegated action (links to AAE's approvals, invariant I-08).
  • evidence_requirements — the receipts (P2), provenance (P3), or attestations (P12) the delegatee must produce with its result.
  • trust_domain — the trust domain boundary; cross-domain delegation requires explicit federation consent.
  • result — the result payload returned up the chain.
  • signature — the delegatee's signature over the canonical-CBOR of the exchange, binding the result to the chain.

Signing requirements (T1 trust-core)

Each agent in the chain signs its hop via T1 (Ed25519 default, KMS/HSM in production) over canonical-CBOR, and a Rekor entry is returned. Because the chain is a chain of signatures, a verifier can independently validate every link; a single missing or invalid signature breaks the chain and rejects the result.

Revocation semantics

Revoking any AAE in the delegation_chain retroactively invalidates every downstream hop. The revocation_handle / CloudEvent mechanism propagates this within I-05, so a compromised mid-chain agent cannot continue to exercise authority granted by a now-revoked parent.

Adversarial test vectors required for conformance

Under testvectors/P10/: replay, tampering, confused deputy, privilege amplification (I-02 — the headline invariant for MADE; a chain that would expand authority is rejected), downgrade, replay-across-contexts. MADE additionally requires a hop-exhaustion vector: a chain that exceeds the originator's delegation_depth is rejected, and a cross-domain delegation without federation consent is rejected.

Components that consume it

I1 (agent-identity) in the multi-agent future. MADE is the protocol that lets R3/R4 guardrails reason about delegated authority: rather than trust the immediate caller blindly, the runtime validates the full chain and enforces attenuation at every hop.

Usage example (JSON)

{
  "delegation_chain": [
    "aae:01HZX...(originator)",
    "aae:01HZY...(attenuated to sub-agent)"
  ],
  "hop_count": 2,
  "quorum": ["spiffe://muveraai.com/human/alice"],
  "evidence_requirements": ["aar:required", "cap:required"],
  "trust_domain": "muveraai.com",
  "result": { "status": "ok", "diff": "sha256:..." },
  "revocation_handle": "rh_made_01HZX...",
  "signature": "99e2...ed25519hex"
}

Benefits — invariant enforced, attack prevented

MADE enforces invariant I-02 (no privilege amplification) in the multi-agent setting. It prevents the rogue-sub-agent attack, the delegation-depth-exhaustion attack, and the unauthorized cross-trust-domain hop. By making attenuation signed and verifiable at every link, it makes a federation of agents behave like a single least-privileged system.

Cross-references

P11PRB — Proof-Carrying Remediation Bundle

Spelled out: Proof-Carrying Remediation Bundle. Purpose: ship a vulnerability fix that carries its own proof of correctness. A PRB bundles a reproducer, a root cause, an affected-version graph, the patch, tests, regression evidence, build provenance, signed artifacts, and — critically — an embargo marker. Where a normal patch says "install this," a PRB says "here is how to reproduce the bug, here is why this patch fixes it, here is the proof that the patch does not regress, and here is when you are allowed to talk about it."

Schema sketch (mandatory fields)

Normative schemas are CDDL and JSON-LD. Mandatory fields:

reproducer, root_cause, affected_versions, patch, tests,
regression_evidence, build_provenance, signed_artifacts, embargo
  • reproducer — a signed, runnable reproducer for the vulnerability; without it, the fix is unverifiable.
  • root_cause — a structured root-cause analysis (not free text) tying the fix to the cause.
  • affected_versions — a graph of which versions are affected, fixed, and not- affected, so consumers can route the patch correctly.
  • patch — the patch itself, digest-pinned.
  • tests — the tests that demonstrate the fix.
  • regression_evidence — evidence (often a VEB, P8) that the patch does not regress existing behavior.
  • build_provenance — provenance of the built artifacts (SLSA-style), tying back to AATM (P6).
  • signed_artifacts — the signed, ready-to-deploy binaries or images.
  • embargo — embargo window and disclosure recipients; an embargo-preserving PRB redacts exploit detail until the window closes.

Signing requirements (T1 trust-core)

The remediator signs the bundle via T1 (Ed25519 default, KMS/HSM in production) over canonical-CBOR, and each signed_artifact carries its own signature. A Rekor entry is returned so the bundle's publication is auditable — important for disclosure-timing disputes. Embargo handling means the public Rekor entry may carry a redacted bundle, with the full bundle available only to disclosed recipients under a separate signed envelope.

Revocation semantics

A PRB is itself a remediation for a revocation: it is the artifact that retires a vulnerable version. The revocation_handle / CloudEvent mechanism applies to the bundle's authority (the fix is withdrawn if a follow-up bug is found), and propagation follows I-05. The affected_versions graph drives automatic fleet-wide supersession once the fix is verified.

Adversarial test vectors required for conformance

Under testvectors/P11/: replay, tampering, confused deputy, privilege amplification (I-02), downgrade, replay-across-contexts. PRB additionally requires a proof-carrying vector: a bundle whose regression_evidence does not actually exercise the patch, or whose reproducer fails to reproduce, is rejected, and an embargo violation (disclosure before window close) is detectable.

Components that consume it

S9 (vulnerability response / remediation) produces and consumes PRBs; X9 (incident response) routes PRBs as the remediation arm of an AIX (P9) incident. Automated update systems verify the bundle's proof before applying the patch.

Usage example (JSON)

{
  "reproducer": "sha256:repro_01HZX...",
  "root_cause": { "class": "prompt_injection", "path": "tool/web-fetch" },
  "affected_versions": { "affected": ["ssp@<1.3"], "fixed": ["ssp@1.3"] },
  "patch": "sha256:patch_01HZX...",
  "tests": ["sha256:test_injection_1", "sha256:test_injection_2"],
  "regression_evidence": "veb:01HZX...",
  "build_provenance": { "slsa_level": "L3", "aatm": "aatm:01HZX..." },
  "signed_artifacts": [ { "ref": "ssp@1.3", "sig": "1f8c..." } ],
  "embargo": { "until": 1767984000, "recipients": ["sec@muveraai.com"] },
  "revocation_handle": "rh_prb_01HZX...",
  "signature": "44bd...ed25519hex"
}

Benefits — invariant enforced, attack prevented

PRB prevents malicious-patch and regression-slip attacks. A patch cannot ship without a reproducer and regression evidence, so "trust this fix" becomes "verify this fix." Embargo preservation means coordinated disclosure survives automation, and signed build provenance prevents a supply-chain attacker from substituting a patched-looking but malicious artifact.

P12CAP — Capability Attestation Profile

Spelled out: Capability Attestation Profile. Purpose: declare and verify what an agent can actually do in a specific runtime — not what it is authorized to do (that is P1 AAE), but what the concrete runtime permits it to do. A CAP enumerates the available tools, the enforced policy, the credentials present, the network reachability, the memory configuration, the model, the sandbox, and the hardware attestation evidence proving the claim. It is the protocol that lets a verifier confirm "this agent really is confined the way you say it is," closing the gap between policy-on-paper and policy-in-fact.

Schema sketch (mandatory fields)

Normative schema is CDDL. Mandatory fields:

runtime, tools, policy, credentials, network, memory, model,
sandbox, attestation_evidence
  • runtime — the concrete runtime (process, container, TEE) hosting the agent.
  • tools — the tools actually available in this runtime (distinct from the tools the AAE permits — the intersection is what the agent may invoke).
  • policy — the policy bundle actually enforced by the guardrails (R3), hashed.
  • credentials — the credentials present in the runtime (and, by selective disclosure, not their secrets).
  • network — the network egress actually possible from the sandbox.
  • memory — the memory configuration and any AMIL (P4) bindings.
  • model — the model actually serving inference (linking to AATM, P6).
  • sandbox — the sandbox type and version confining the runtime.
  • attestation_evidence — hardware attestation evidence (SEV-SNP quote, TPM quote, etc.) cryptographically rooting the claim.

Signing requirements (T1 trust-core)

The runtime (or its attesting host) signs the CAP via T1 (Ed25519 default, KMS/HSM in production) over canonical-CBOR, and a Rekor entry is returned. The attestation_evidence field carries a hardware signature (e.g., a SEV-SNP attestation report) that the verifier checks in addition to the T1 signature, so a compromised host cannot lie about its own confinement. This dual-rooting is what makes a CAP a real attestation rather than a self-assertion.

Revocation semantics

A CAP is short-lived (its expiry is tight, typically matching the AAE's capability- token TTL). The revocation_handle / CloudEvent mechanism withdraws a CAP when the runtime is found to be misconfigured or compromised, and propagation follows I-05 — credentials in particular propagate within the < 1s credential budget. A CAP whose hardware attestation fails replay-protection checks is rejected immediately.

Adversarial test vectors required for conformance

Under testvectors/P12/: replay, tampering, confused deputy, privilege amplification (I-02), downgrade, replay-across-contexts. CAP additionally requires an attestation-forgery vector: a CAP whose claimed sandbox or network does not match the attestation_evidence is rejected, and a CAP with stale (replayed) attestation evidence is rejected by freshness checks.

Components that consume it

R1 and R2 (runtime / sandbox) produce CAPs as a condition of agent startup; I1 (agent-identity) consumes the CAP to bind the issued SVID to a verified runtime. A delegating agent may demand a counterparty's CAP before accepting a MADE (P10) delegation, ensuring the delegatee actually runs in a confining sandbox.

Usage example (JSON)

{
  "runtime": "container@sha256:r1...",
  "tools": ["spiffe://muveraai.com/tool/github-cli"],
  "policy": "sha256:pol1...",
  "credentials": ["spiffe-svid", "gh-token(readonly)"],
  "network": "egress:github.com:443",
  "memory": { "amil": "amil:ledger_01HZX...", "mode": "sandboxed" },
  "model": "claude-opus-4.5@sha256:m1...",
  "sandbox": "firecracker@1.7",
  "attestation_evidence": "sev-snp:quote:01HZX...",
  "expiry": 1767811500,
  "revocation_handle": "rh_cap_01HZX...",
  "signature": "66ad...ed25519hex"
}

Benefits — invariant enforced, attack prevented

CAP prevents policy-vs-runtime drift and the "agent that runs unconfined while claiming to be confined" attack. By cryptographically rooting the capability claim in hardware attestation, it converts sandboxing and network policy from assertions a host can lie about into facts a verifier can check. It is the protocol that makes the difference between an agent that is supposed to be sandboxed and an agent that is sandboxed.

Shared mechanism across all twelve

Every protocol is (a) signed by T1 trust-core over canonical-CBOR, (b) issued with an explicit expiry, (c) revocable via the aumos.<domain>.revoked.v1 CloudEvent on Kafka with I-05 propagation budgets, (d) shipped with the same six adversarial test-vector classes under testvectors/P<n>/, and (e) enforced cross-language by A6. The diversity is in the fields; the engineering discipline is uniform.
