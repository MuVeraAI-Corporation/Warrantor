## 1.5 What is still open in engineering, and why each is where it is

### §3.1 — bounds are weaker than they read *(still the one that matters; half of it now exists)*

`write_paths` and `budget_cents_observed` are **Observed**, not enforced. There is no netns, no
seccomp and no firewall.

**What was built** (`e2da595`): `warrantor sandbox <id> [--kind bubblewrap|firejail]` derives a
confinement profile from a warrant's bounds and — the part that took the work — names every bound
a sandbox *cannot* express, and every bound where the profile would be **stricter than the
warrant**. A no-egress warrant gets `--unshare-net`, which is the one genuine upgrade. A warrant
permitting hosts gets none, because a namespace is all-or-nothing and emitting one would deny
egress the warrant grants — the agent then fails at its first fetch in a way that looks nothing
like Warrantor.

**What you have to do, and it is the important half.** Nothing here has executed `bubblewrap`; this
branch had no Linux host. `bound_strengths()` is untouched and a test asserts a profile cannot move
it. On a Linux box:

```bash
warrantor grant --goal "tidy the docs" --tools read_file --write 'src/**' --repo .
```

```bash
warrantor sandbox <that-warrant-id>
```

Then launch an agent under the printed prefix and confirm a write outside the worktree fails at the
syscall. That is what closes §3.1. Until then the profile is a well-tested derivation of an
untested claim.

Note the command refuses on this machine, correctly: a store created on Windows has a worktree path
that cannot exist under `bwrap`, and a command that cannot work must not be printed as though it
could.

### §3.2's remainder — email and mobile push *(the only untouched item, and it needs a decision)*

A webhook can front both and nothing here speaks them directly. Two ways to close it, and both are
trades worth stating before making:

- **An SMTP client** adds a dependency to a crate whose seven-dependency, tokio-free posture is a
  security property.
- **A command transport** — `notify.json` naming a program to exec — adds no dependency and lets
  you front anything with a script. But it hands *anything that can write `notify.json`* a
  code-execution primitive, and per §2.4 the supervised agent shares this UID. That turns a config
  write into persistence. If you want it, it should be armed at the command line so a config-only
  write cannot enable it.

I did not pick for you.

## 3. The one thing to carry forward

**The failures in this repository cluster in the claims, not the code.** Eight defects this session
were statements rather than branches, and every one was invisible to a 600-test suite:

1. an error message naming a flag that did not exist;
2. a generator writing `CLAUDE.md` files asserting protections that were not in force;
3. a recall figure quoted for a configuration that was not running;
4. a warrant id that silently destroyed its predecessor;
5. a tray that never appeared in a packaged build;
6. a `--from` flag named in a refusal I had just written;
7. a config comment asserting *"Windows and macOS … were unaffected"* while Windows was installing
   to a directory named after the Linux fix (§1.1);
8. a `SIGNING.md` status table saying *"never built by CI"* two days after CI built all four
   platforms — found while editing that same file to correct a **different** false claim.

The last one is worth its own sentence: **the correction nearly introduced its own error.** Writing
"never built by CI" into the table felt like tightening it, and the roadmap two directories away
recorded run `31875701622` building every platform. A document can be stale in the direction of
*understating* and still be a document nobody can trust.

Three cheap checks now catch these classes, and all three were built *because* of the first few:

- **`tests/instructions.rs`** — every flag and command the binary names in its own output must be
  real. It caught four changes made after it existed, including one on the day it was written.
- **`tests/guard_parity.rs`** — the two implementations of the guard must agree knob for knob, read
  from each other's source.
- **Launching the packaged app** — the gap between what the packager copies and what the process
  opens has no representation in either artifact. Only starting it finds that.

Before merging anything, run the first two. Before cutting a release, do the third.

**And a fourth, learned on the push (§4–§5): run the gate for every language you touched, not the
ones you were thinking about — and when a tool reports a problem, sweep for the whole class rather
than fixing what it named.** Both CI failures and all three rounds of the Node 20 fix were the same
mistake in different clothes: trusting a report that only covered what happened to run.

## 5. Node 20, and why it took two attempts

GitHub annotated the run: `actions/setup-python@v5` and `actions/upload-artifact@v4` target Node 20
and were being **forced** onto Node 24. Nothing was broken, which is the hazard — the forcing is
temporary, and when it stops these jobs fail on a schedule nobody here sets.

**Attempt one cleared the two actions the annotation named, went green, and the annotation moved** —
to `bufbuild/buf-setup-action`. The inventory had been wide and the fix narrow.

### What could not be fixed by pinning

`bufbuild/buf-setup-action` declares `using: "node20"` at `v1` **and** at `v1.50.0`, its latest
release — checked at both refs rather than assumed. No tag clears it, so the only fix available here
was to stop using the action. It only ever installed a CLI; doing that directly is four lines and
buys two things the floating `@v1` did not: the version is **pinned** (1.72.0) instead of whatever
`v1.x` resolves to on the day, and the download is **verified** against buf's published sha256. The
check fails the job rather than warning — a wrong `buf` lints nothing and reports success, which is
the exact failure that gate exists to prevent.

### Final versions

| Action | Was | Now |
|---|---|---|
| `actions/upload-artifact` | v4 | **v7** |
| `actions/setup-python` | v5 | **v7** |
| `actions/download-artifact` | v4 | **v8** |
| `actions/checkout` | v4 (2 sites) | **v7** |
| `docker/setup-buildx-action` | v3 | **v4** |
| `docker/login-action` | v3 | **v4** |
| `docker/metadata-action` | v5 | **v6** |
| `docker/build-push-action` | v6 | **v7** |
| `bufbuild/buf-setup-action` | v1 | **removed** — pinned, checksum-verified install |

`download-artifact@v8` makes **hash mismatches error by default** rather than warn. If a release
download has been silently corrupting, that is where it starts saying so — the right direction for a
repository about tamper-evident evidence, and much better found on a deliberate bump than during an
incident. v6+ of upload/download need Actions Runner ≥ 2.327.1; GitHub-hosted runners are past it,
a self-hosted one would need updating first.

### The pattern, which is the actual lesson

**Three times in two commits, the annotation described the jobs that HAPPENED to run rather than the
repository.** `download-artifact` never warned because the release workflows had not run. The four
Docker actions never warned for the same reason. `checkout@v4` sat in a composite action nobody
edits, four majors behind 28 other call sites.

The same shape as Coverage and SBOM rotting because they only fire on push-to-main. So the fix
ended with a **sweep** rather than a reading — every `uses:` in `.github/`, resolved to its
`action.yml` at the pinned ref, checked for a `node16`/`node20` runtime:

```bash
for spec in $(grep -rhoE 'uses: [a-zA-Z0-9._/-]+@[a-zA-Z0-9._-]+' .github/ | sed 's/uses: //' | sort -u); do
  a=${spec%@*}; t=${spec##*@}
  gh api "repos/$a/contents/action.yml?ref=$t" --jq '.content' 2>/dev/null | base64 -d 2>/dev/null \
    | grep -oE 'using: *"?node[0-9]+' | grep -q 'node20' && echo "STILL NODE20: $spec"
done
```

Verified clear: **zero Node 20 annotations across CI, Coverage and SBOM** on `0edd869`.

## 6. Environment notes that cost real time

- **Never pipe cargo through `head`.** SIGPIPE orphans rustc and corrupts `target/`. Write to a log
  and grep it after.
- **Use `-j 2`.** `clippy` and the NSIS icon step both died with Windows resource-exhaustion errors
  at higher parallelism.
- **Windows fork exhaustion corrupts the build cache.** It presents as nonsense: *"only metadata stub
  found for `rlib` dependency `std`"*, `STATUS_STACK_BUFFER_OVERRUN`, crates that cannot be found.
  Targeted `cargo clean -p` does not clear it once it has cascaded; a full `cargo clean` does.
- **`gh pr merge` is blocked on this repository.** Use
  `gh api --method PUT repos/MuVeraAI-Corporation/Warrantor/pulls/<N>/merge -f merge_method=squash`.
- **The merge doctrine still stands** for anything that comes next: rebase, verify, merge **one at a
  time**. Batch-merging five green PRs broke `main` five ways once, because PR CI tests the branch
  against *old* main. This merge was safe only because `main` sat at exactly the branch base.
